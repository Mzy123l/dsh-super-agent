# 安全边界

> 原始十个问题的第 8 条。长文 §8.4 只提了三层，这里补全成一张可执行的威胁表。
> **原则：能解决的写清楚解法，解决不了的诚实标注为"接受的风险"，不假装。**

## 1. 先明确信任边界

整套系统里，能"信任"的东西极少：

| 可信 | 不可信 |
| --- | --- |
| 你自己的代码（插件、Engine） | **所有消息、评论、引用的文档** |
| 部署配置（预声明的外部目标） | Worker 的 Report（自述） |
| OS 账号的隔离（若已配置） | 设备上报的负载（可伪造，但伪造无利可图） |
| git 对象（内容） | 日志里的 `note` 字段 |
| | 模型输出的任何自然语言 |

**注意第二列里有一条容易被忽略的**：`worker_report` 是不可信的。它不是恶意的，但它是**自述**——"着急"会让模型跳过验证然后报 ready。所以 [52-file-warden.md](52-file-warden.md) §8 才要用三方证据交叉校验。

## 2. 威胁表

### T1 提示词注入（传播面被放大）

| | |
| --- | --- |
| **攻击面** | 邮件、IM 消息、PR 评论、Issue 正文、仓库文件、只追加日志的 `note` 字段 |
| **为什么比单 Session 更危险** | 单 Session 时一封恶意邮件只影响一次会话；现在它进 Thread → 订阅扇出 → 影响**所有订阅 Worker** |
| **已被挡住的** | 权限污染。原型的「扇出不赋予权限」+ Mandate 不可变，让注入无法扩大授权 |
| **挡不住的** | **判断污染**。Worker 可能在授权范围内做出错误的判断和行动 |
| **对策** | ① 输入一律标记为不可信数据（官方 `admission.md` 已有这条）<br>② 日志 schema 只允许结构化字段，自由文本封在 `note` 里<br>③ 外部路径必须预声明，运行时不能新增<br>④ 不可逆操作（merge、删除）永远需要人 |
| **残余风险** | 在授权范围内的错误判断。**接受**——这是"给 Agent 授权"的固有代价 |

### T2 凭据泄漏

| | |
| --- | --- |
| **攻击面** | Worker 能 `cat` 任何文件、能 `env` 看变量、能跑任意命令 |
| **原型现状** | 只是"删了已知的变量名"（`GH_TOKEN`/`GITHUB_TOKEN`）+ `PATH` 垫片。文档自认「垫片不是安全边界，Worker 仍可用绝对路径执行任何程序」 |
| **对策** | 见 [20-design.md](20-design.md) §3.3 的凭据代理：模型只见 `CapabilityHandle`；注入发生在子进程创建瞬间；输出过三层脱敏（精确匹配 + 熵检测 + **金丝雀**）；租约 60 秒自动过期 |
| **为什么金丝雀是关键** | 它把"泄漏了但没人知道"变成"必然被发现"。已知 secret 值匹配只能防已知的，熵检测有误报，金丝雀是**确定性**的 |
| **残余风险** | daemon 以操作员身份运行，恶意命令仍可能通过侧信道（时序、`/proc`、系统调用）拿到信息。**接受**——目标不是抵御被攻破的 Agent，而是让正常路径不产生泄漏机会 |

### T3 任意代码执行

| | |
| --- | --- |
| **攻击面** | Worker 以操作员 OS 用户身份、`danger-full-access`、无需审批执行命令 |
| **组合的危险性** | **输入来自不可信网络 + 拥有本机任意代码执行**。这个组合在安全上不成立 |
| **对策（按强度）** | ① **独立 OS 账号**：只装 Agent 凭据，不含用户私人数据（官方推荐）<br>② 容器 / microVM<br>③ `workspace-write` 沙箱（**但 Windows 上是 partial**）<br>④ 命令垫片（**最弱，只是默认值**） |
| **诚实结论** | **这一条本设计没有彻底解决。** 单机形态下，如果 Agent 以用户自己的身份跑，它就是用户的完整权限。 |
| **建议的最小前提** | 至少做到 ① 独立 OS 账号。做不到就要接受"Agent 与用户同权限"这个事实，并据此决定它被允许接触什么数据 |

### T4 成本拒绝服务

| | |
| --- | --- |
| **攻击面** | 一条精心构造的消息触发超长 assessment / 死循环 / 巨型上下文 |
| **原型现状** | 只有 eval timeout，**没有 token 预算** |
| **对策** | 三重预算硬停（token / 墙钟 / 工具调用），见 [60-model-cost.md](60-model-cost.md) §3 |
| **降级策略** | 超预算 → 降级为 `observe`（继续工作但不主动），而不是直接停 |

### T5 供应链（Agent 自己的输出）

| | |
| --- | --- |
| **攻击面** | Worker 可以 push 分支、开 PR、改依赖 |
| **对策** | ① 用独立 Agent 账号（不是用户的）<br>② **禁止直推主分支**，只能开 PR<br>③ 依赖变更单独成 PR，不与其他改动混合<br>④ auto-merge 默认关，且默认不允许 Agent 自己 enable（GitHub 会把 merge 归因给 enable 的人） |
| **官方原型已有** | "默认 Executor 绝不 enable auto-merge"——理由是 GitHub 会把 merge 归因给 enable 的那个人 |

### T6 跨信道身份混淆

| | |
| --- | --- |
| **攻击面** | 同一个人在不同 Source（GitHub / IM / 邮件）身份不同；Agent 需要判断"是不是同一个人" |
| **原型的处理** | 明确**不做跨 Source 身份映射**，把责任推给 flag text（`identities` skill） |
| **我的判断** | 这是**最弱的一环**，而且是刻意选择的弱。**不要假装能解决** |
| **对策** | ① 保持"不映射"的立场（映射错了比不映射更糟）<br>② 把判定责任写进 skill 并**明确标注"这是约定不是校验"**<br>③ 高权限操作（stop、改权限）只认 Source 内的身份 |

### T7 relay 被攻破（集群才有）

| | |
| --- | --- |
| **攻击面** | relay 转发所有帧，如果它能看到明文就等于控制了全部 |
| **对策** | **端到端加密**。relay 只看到 `to`/`from`/`kind`/长度 |
| **推论** | 因为解不开 payload，relay **不可能做智能调度**——"哑"不是设计选择，是加密的必然结果 |

### T8 设备失联导致的状态分歧（集群才有）

| | |
| --- | --- |
| **攻击面** | 控制面与设备各有状态，网络分区时可能各自推进 |
| **对策** | **不做自动脑裂**。降级为只读 + 排队；转本地是**人的显式决定** |

### T9 本地文件的越界访问

| | |
| --- | --- |
| **攻击面** | Worker 想读写自己目录之外的东西 |
| **对策** | enforcement 在 `ctx.fs` provider 里——**公共区域和外部路径在这个 provider 里根本不存在**，所以越界不是"被拒绝"，是"不存在" |
| **必须堵的洞** | `processPathFromHostPath()` 会把绝对宿主路径映射进执行世界。**显式让它返回 `undefined`** |
| **注意** | 这一条与"读工作区内继承 dsh 会话权限"（D15）并存：读是宽松的，但**写**严格 |

## 3. 安全机制与决策的对应

| 机制 | 挡住哪个威胁 | 代价 |
| --- | --- | --- |
| 凭据代理 + 金丝雀 | T1 后果、T2 | 中（要写 broker + daemon 配合） |
| 独立 OS 账号 | T3 | 部署复杂度（官方也建议） |
| 预算硬停 | T4 | 低 |
| 独立 Agent 账号 + 禁直推 | T5 | 低（主要是运维） |
| 输入标为不可信 + 结构化日志 | T1 | 低 |
| 端到端加密 | T7 | 中（首版就要做，后加改协议） |
| 不做自动脑裂 | T8 | 低（少做一件事） |
| provider 层越界即不存在 | T9 | 低 |

**注意"低"占了一半以上。** 安全的大头不在难做的那些机制，在**不要偷懒**：

- 不要把用户账号给 Agent 用
- 不要在 prompt 里塞自由文本
- 不要为省事允许运行时新增外部目标
- 不要做"自动恢复"的静默决策

## 4. 优先级

按"投入产出比"和"被攻击的可能性"排序：

| 序 | 做什么 | 理由 |
| --- | --- | --- |
| 1 | **预算硬停** | 最便宜，挡住 T4 |
| 2 | **provider 层越界即不存在** | 最便宜，挡住 T9，且它让"文件调度者是唯一入口"这句话成立 |
| 3 | **独立 Agent 账号 + 禁直推** | 纯运维，挡住 T5 |
| 4 | **输入标为不可信 + 结构化日志** | 便宜，缩小 T1 |
| 5 | **凭据代理 + 金丝雀** | 贵，但 T2 是最现实的泄漏路径 |
| 6 | **端到端加密** | 贵，但必须在协议定型前做，后加=重写 |
| 7 | **独立 OS 账号** | 部署复杂度高，但 T3 没有别的彻底解法 |

## 5. 明确接受的风险

写下来，避免以后假装解决了：

| 风险 | 为什么接受 |
| --- | --- |
| Agent 在授权范围内的错误判断 | 这是"给 Agent 授权"的固有代价；只能靠证据校验缩小，不能消除 |
| 同 OS 账号下的侧信道泄漏 | 彻底解决需要 OS 级隔离，不在插件能力范围 |
| 跨 Source 身份无法可靠判定 | 映射错了比不映射更糟；保持"约定不是校验"的诚实 |
| 模型可能没注意到文件被并发改动 | D17 的选择；有日志可发现，但无强制 |
| Windows 上 `workspace-write` 是 partial | 官方现状；要强隔离就得换平台或独立账号 |
| Watchdog 误判 | 有打扰预算与精确率自动降级，但不可能零误报 |

## 7. 一句话

安全这一章里，**难做的机制只占少数，大部分是"不要偷懒"**。而系统里最大的风险不是"Agent 被攻破"，是**"Agent 是好人，但它错了，而没人发现"**——所以防糊弄（问题 1）本质上是安全问题，不是质量问题。
