# 设计：跨时间召回——「早说过的话」如何在长会话里活下来

> **⧉ 2026-11-15 修订：本设计的四个决策已被用户改定，落地形态见 [9O](9O-memory-plugin-spec.md) 与 `memory-plugin/` 实现。**
> 修订要点：①思考不进关键词索引、只向量化；②**不启用 dsh 内置 session-query**，自建存储复制数据；
> ③搜索全量（不管压缩/摘要状态，搜原始日志），**压缩声明不再保全待办**；
> ④**不做轮末自动触发**——未来由 Router 提醒，现阶段模型不知道待办可接受（用户记得）。
> 本文 §3 的部分设计与修订冲突，以 [9O](9O-memory-plugin-spec.md) 为准；§1 场景解剖仍然有效。

> 场景（用户原话要点）：**在很早的地方说「这里记成待办，先干完手头上的要紧事，再回头干这个待办」，
> 经过长时间工作后**，原始消息被压缩吞掉，模型既不记得有这个待办，也没有任何机制提醒它。
>
> 用户提出的解法方向：**关键词搜索 + 向量化搜索**。
>
> 本文档把这个场景拆成三段：**说的那一刻 → 长时间工作 → 回头的时候**，
> 每一段分析现有机制在哪里断裂，然后给出设计。

---

## 1. 场景解剖：为什么现在的系统一定会丢

用真实链路走一遍：

### 1.1 说的那一刻

```
user: 这个日志时间戳不对，记成待办，先干完手头上的要紧事，再回头修它
```

**此刻的信息状态**：
- 这句话完整存在于上下文（未压缩）
- 模型的 reasoning 里可能判断了"先做什么"
- **但没有任何结构把它标记为"待办"**——它只是 10 万字符历史里的普通一条

### 1.2 长时间工作

几轮之后，压缩触发（实测阈值在窗口 67.85%–80% 浮动，[98](98-compaction-findings.md) §3）：

```
selectCompactableRange()：跳过 node 0 → 保留尾部 → 其余遮蔽
```

**那句"记成待办"在遮蔽范围内**。它去了哪里？

| 去处 | 状态 |
| --- | --- |
| 原始事件 | ✅ **还在日志里**（`.jsonl.zstd`，逐字） |
| `<compacted-summary>` | ⚠️ **看运气**——摘要模型的 8 小节里有 `Pending Jobs`，但它要**自己意识到**这句是待办并写进去；prompt 里没有"待办必须保留"的义务 |
| 模型的 reasoning | ❌ 摘要输出**明确排除推理**（9M 实测「推理与工具调用都会被排除」） |
| 模型的可见上下文 | ❌ 遮蔽 |

**断裂点 1**：摘要模型没有义务保留待办。`Pending Jobs` 一节的指令是
"[explicitly requested work not yet completed]"——取决于摘要模型对"explicitly"的判断。
一句夹在报错排查中间的"记成待办"，很容易被判成"上下文细节"而丢弃。

**断裂点 2**：即使摘要有运气写进去了，**模型不知道它在**。
摘要是一条不可索引的文本，模型不会知道"我的待办清单在摘要第 3 节"。

**断裂点 3**：没有检索通道。`session-query` 三层链路默认全关（9B §3.3.3：
`openAt: never`、`tool-session-query` 未挂载），模型**没有工具**能回到日志里找那句话。

**三条断裂相乘：说过的待办 → 大概率丢 → 丢了没人知道 → 丢了找不回。**

### 1.3 回头的时候

工作完成，用户问：「那个日志时间戳的待办呢？」

模型的处境：
- 上下文里没有那句话（被遮蔽）
- 摘要里可能有也可能没有
- 没有工具能查
- **且它不知道自己丢了**——这正是 97 文档的核心结论「我以为我记得」

最可能的失败回答：「我没有记录这个待办」（因为它真的看不到）——
**而用户记得自己说过。信任裂痕就是这么产生的。**

## 2. 用户的解法方向：关键词搜索 + 向量化搜索

两个都要，但它们解决的是**召回的不同阶段**：

| | 关键词搜索 | 向量化搜索 |
| --- | --- | --- |
| 找什么 | **精确的词**：「待办」「时间戳」「回头修」 | **语义相近**的内容：「日志日期好像有点怪」「先处理紧急的」 |
| 何时可靠 | 用户明说关键词时 | 换了措辞时 |
| 何时失效 | 用户换了说法（"那个日期问题"） | 语义漂移太远、专业术语、人名文件名 |
| 成本 | 极低（SQLite FTS5 原生支持） | 需要 embedding 模型 + 向量库 + 增量索引 |
| 结论 | **底座，必须先有** | **增强，在关键词之上** |

**这个顺序是重要的工程判断**：关键词搜索是 dsh **已经内置但被关闭**的能力
（`searchSessions` / `searchEvents`，SQLite FTS），打开它几乎零成本；
向量检索是**全新建设**，应该第二步做。

### 2.1 但检索解决不了全部——还差一个"触发"

关键洞察：**检索是 pull 模式，前提是模型知道该查。**

即使搜索通道全开，模型在"干完手头要紧事"之后，**为什么会去搜"待办"？**
它可能根本不记得说过这话——这正是 97 的核心结论。

**所以完整解法 = 存储（搜索）+ 记录（结构化待办）+ 触发（轮次结束时的显式提醒）**。三者缺一不可：

```
说的那一刻   → ① 结构化记录（写进一个"待办层"，独立于会话历史）
长时间工作   → ② 检索可用（关键词 + 向量，保底能找回）
回头的时候   → ③ 主动浮现（轮次结束/压缩时，显式提醒未回收的待办）
```

## 3. 设计

### 3.1 记录层：`Commitment`（承诺）——第一种一等公民的跨时间记录

**待办不是普通历史，是"对未来的一句话承诺"。** 它需要自己的聚合：

```ts
interface Commitment {
  readonly id: string
  readonly kind: 'todo' | 'constraint' | 'deferred-decision' | 'promise'
  //  ↑ 待办 / 硬约束 / 搁置的决定 / 对用户的承诺——四类都是"跨时间必须活着"的话
  readonly text: string              // 用户的原话（逐字，不转述）
  readonly saidAt: { seq: number }   // 说的位置（可回溯原文）
  readonly status: 'open' | 'done' | 'dropped'
  readonly openedAt: string
  readonly closedAt?: string
  readonly closedReason?: string     // 谁关的：模型完成 / 用户确认 / 用户放弃
}
```

**谁创建**：模型。在对话中识别到"记成待办/先别/回头再/等一下再"这类承诺语句时，
通过一个工具（`commitment_record`）落一条。**创建是模型自主的，不是强制的**——漏记的风险在（模型可能没识别出来），由下面的兜底缓解。

**关键属性**：
- **`text` 存原话**，不是转述——转述会丢语义，检索要靠原话
- **`saidAt.seq` 指回原始位置**——压缩后仍可 `session_event_read` 回原文
- **独立于会话历史存储**——它不依赖"那条消息在不在上下文里"

### 3.2 存储层：打开关键词搜索（第一步，近零成本）

把 dsh 已内置但关闭的通道打开（[9B](9B-dsh-source-findings.md) §3.3.3 的三重关闭）：

```yaml
# profile patch：打开全文搜索后端 + 挂载模型工具
- id: session-query-sqlite
  config:
    path: <stateDir>/session-search.sqlite   # 不再是 :memory:
    openAt: startup                          # 不再是 never
- insert:
    - id: tool-session-query
      name: '@deepseek-ai/dsh-tool-session-query'
```

打开后模型立刻获得 5 个工具（9B §3.3.1 层 2）：`session_search` / `session_event_search` /
`session_trace` / `session_event_trace` / `session_event_read`。

**这步是纯配置**，dsh 代码零改动。**没有它，后面一切检索都是空谈。**

### 3.3 存储层：向量化检索（第二步，有条件做）

**前提**：关键词先落地并跑一段时间——用真实查询日志判断关键词的失效率，再决定要不要向量。

实现选项（按依赖排序）：

| 方案 | 组成 | 代价 |
| --- | --- | --- |
| **A. SQLite + 本地 embedding** | `sqlite-vec` / `VSS` 扩展 + 本地 embedding 模型（如 bge-small） | 无新服务；增量索引在写入时做 |
| B. 外部向量库 | Qdrant / chroma | 新服务，违反"小部署"原则（9G 集群形态 1C1G） |
| C. 复用 provider embedding API | 调 DeepSeek/其他家 embedding，存 SQLite | 每条一次 API 调用；断网不可用 |

**推荐 A**：与 9G 的集群形态（1C1G VPS）一致，无外部依赖。

**索引什么**（重要——9M 实测的一个坑）：
**reasoning 块不进语义索引**（`session-query` 的已知限制：reasoning 块不纳入语义文本）。
所以向量化索引的对象是：user 消息、assistant 可见文本、工具结果的 spill 摘要。
**模型的思考若要可检索，依赖 turn-summary 落盘**（[9L](9L-tool-call-summary-design.md) §2.7）——
这是两个设计的一次耦合。

### 3.4 触发层：Commitment 的主动浮现

检索解决"能找到"，触发解决"会去找"。两个触发点：

**触发 1：轮次结束扫描**

`agent/turn-stopping` 时点，系统（非模型）查询 `open` 状态的 Commitment，
若有，注入一条 `<system-reminder>`：

```
[open commitments: 1] "这个日志时间戳不对，记成待办…"（said at seq 412, 3 days ago）
— 原文: session_event_read(seq=412)；完成后 commitment_close(id)
```

**规则式、零模型调用、每轮一次查询**。**这是"回头"能发生的关键**：
模型不需要记得说过——**系统记得，并在合适的时机递到它面前**。

**触发 2：压缩前保全**

压缩触发前，把 `open` 状态的 Commitment **逐字写进压缩声明区**（与 9G S1 的
`[compaction-declaration]` 同一位置）：

```
[compacted: ... · open commitments preserved:
  #1 todo "日志时间戳不对" (seq 412)
  #2 deferred-decision "先不做暗色模式" (seq 988)]
```

**这样即使原文被遮蔽，待办清单本身在压缩后的上下文里仍然可见。**

### 3.5 与 self-gist / turn-summary 的关系

| 机制 | 对象 | 谁写 | 生命周期 |
| --- | --- | --- | --- |
| **Commitment**（本节） | 用户的跨时间指令 | 模型识别后记录 | **直到关闭**——不受压缩影响 |
| self-gist（9L §2.3） | 工具结果的要点 | 主模型同帧 | 随历史衰减，可检索 |
| turn-summary（9L §2.7） | 一轮思考的总结 | 主模型自选 | 随历史衰减，压缩时强制保留 |

**三者不重叠**：Commitment 管的是"对未来的承诺"，
self-gist 管"这次结果的要点"，turn-summary 管"这轮想了什么"。
它们共同构成"跨时间记忆"的三条腿。

### 3.6 为什么这个场景值得单独设计

回看整个记忆线，问题可以按"丢失后的后果"分级：

| 级别 | 场景 | 丢了的后果 |
| --- | --- | --- |
| 轻 | 某次 grep 的细节 | 展开 spill 就回来 |
| 中 | 某轮思考的结论 | 重新推理一遍，费 token |
| **重** | **用户明确交代的事** | **用户信任受损——"我说过的话你都不记得"** |

**Commitment 针对的是"重"级。** 它是唯一一个"丢失即事故"的场景，
所以值得给它单独的聚合、单独的触发、单独的保全机制。

## 4. 验收标准

| # | 标准 | 测法 |
| --- | --- | --- |
| 1 | **核心场景**：早说待办 → 压缩发生 → 完成手头工作 → 问"那个待办呢"，模型能答出内容 | 端到端构造（9I 方法） |
| 2 | Commitment 跨压缩存活 | 压缩后检查声明区的 preserved 清单 |
| 3 | 关键词搜索命中原始消息 | 用原话关键词搜，`session_event_read` 回原文 |
| 4 | 换措辞的召回（若做向量）：「那个日期问题」能命中「日志时间戳不对」 | 人工构造 10 组换说法样本 |
| 5 | 触发不烦人 | open 待办 ≤1 条时不注入；完成后立即停止 |
| 6 | 误识别率 | 模型把普通语句误记为待办的比例 < 10%（抽样） |

## 5. 实施顺序与依赖

| 步 | 内容 | 依赖 | 对应 9G 编号 |
| --- | --- | --- | --- |
| 1 | **打开关键词搜索**（纯配置） | 无 | S3 |
| 2 | **Commitment 聚合 + 触发扫描** | 1（触发时给 `session_event_read` 句柄） | 新增，建议 S5.5 |
| 3 | 压缩前保全 open Commitments | 2 | 并入 S1 声明区 |
| 4 | 向量化检索 | 1 跑出失效率数据后决策 | S3 之后独立项 |

**最小可用**：步 1+2 就能覆盖核心场景——**待办被记下来 + 轮次结束被提醒**，
关键词搜索保底换措辞时也能手动找回。

## 6. 诚实标注

- **模型漏记的风险**：Commitment 靠模型识别承诺语句，**它可能漏**。兜底是压缩声明的 preserved 清单 + 检索。漏记率未测。
- **误记录的风险**：普通语句被误记为待办，会造成"幽灵待办"反复提醒。验收 6 设了 <10% 的上限，但判据是人工的。
- **向量检索未做实验**：换措辞召回的准确率是业界常识推断，本机没有对照数据。
- **触发频率的调参**：每次轮末都提醒可能烦（尤其多条 open 时）；注入策略（几条以上折叠成一行）要实测调。
- **reasoning 不进语义索引**是 dsh 的已知限制，turn-summary 落盘可绕过，但依赖 9L 先落地。
