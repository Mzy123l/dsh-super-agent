## 1. A 类：待你决策（28 条）

### 1.1 R 系列 — 文件与执行（10 条，来自 [50](50-file-model.md) / [52](52-file-warden.md)）

| # | 问题 | 我的推荐 | 不定的后果 |
| --- | --- | --- | --- |
| R1 | 文件调度者是确定性服务，还是也带模型？ | **确定性服务**，只在语义冲突时升模型 | 每次读写都过模型 = 延迟秒级 + token 成本跳一个量级 |
| R2 | 发租约让 worker 直连，还是转发所有字节？ | **发租约直连** | 全转发会成瓶颈，大文件堵死 |
| R3 | 公共目录拆成 `inputs/` 与 `outputs/`？ | **拆** | 读写权限规则会变糊 |
| R4 | 托管根整组原子、外部路径只保证单文件原子？ | **是** | 假装外部路径能整组原子，会做出"看起来原子其实不是"的东西 |
| R5 | 版本号用调度者单调计数还是内容哈希？ | **计数** | 哈希方案大文件每次写要全量算 |
| R6 | 公共数据拷进私有目录，还是直连读？ | **拷** | 直连省磁盘，但读中可能被换 |
| R7 | 日志 append 同步还是异步？ | **异步 + 崩溃可恢复** | 同步会阻塞 worker；丢意图不丢正确性 |
| R8 | Worker 强制统一模型？ | **是** | 分模型导致前缀分裂，缓存全废 |
| R9 | 重任务（需求 > 预算 40%）串行还是并发？ | **串行** | 一律并发会导致集体 swap，比串行慢得多 |
| R10 | 允许从 Super-agent 退回普通会话？ | **允许**（反向不许） | 双向锁死会让用户不敢点，功能就死了 |

## 2. B 类：技术未解（9 条）

这一类**不是"等你点头"**，是我确实不知道答案，需要实验、外部资料或实测数据。

| # | 未解的问题 | 为什么难 | 靠什么才能解决 |
| --- | --- | --- | --- |
| B1 | **Watchdog 的 `stalled()` 阈值多少才对** | "什么叫有进展"没有客观定义；四个条件的阈值是我凭直觉给的 | **标注过的误报回放集**（精确率 ≥0.8、召回 ≥0.6 才算达标）；见 [80](80-others.md) §5.3 |
| B2 | **单 Worker 的内存峰值分布** | 内存账本要靠历史峰值算下一次的 reservation，但没有实测数据 | 跑真实任务采集 cgroup `memory.peak` / Job Object 峰值，按任务类型建表 |
| B3 | **缓存命中率实际能到多少** | 架构上"应该"高，但没有实测；官方只给了"Super-agent 比单 Session 更贵"这一句 | 灰度上线后测命中率对比；这是 M4 指标存在的意义 |
| B4 | **跨月长程记忆怎么检索** | 官方明确列为开放问题；链式召回只解决近期多跳 | 需要新的检索结构（语义 + 图），且要能遗忘。见 [20](20-design.md) §3.6 |
| B5 | **Router 何时该水平切分** | 官方说"当前团队规模够用"，但没给判据 | 压力测试出批处理的拐点；拐点前不切分（切分牺牲上下文连续性） |
| B6 | **非文件工作区怎么办** | 若任务是"改数据库""调 API""发邮件"，没有文件可 git | 需要重新定义"改动"这个概念。见 [50](50-file-model.md) §4 的推广 |
| B7 | **模型会不会注意到文件被并发改动** | D17 把一致性责任推给了模型，但模型默认假设文件是当前版本 | 实测：构造并发改动场景看它是否去查日志。若不会，升到 R6 |
| B8 | **Windows 的 `partial` 隔离实际漏多少** | 官方只说 Windows ACL 档是 partial，没说漏什么 | 需要实测具体哪些操作不被管辖 |
| B9 | **强制 git 在大目录上的实际代价** | 我知道会慢，但不知道多慢、多大目录开始不可接受 | 实测 1GB / 10GB / 100GB 目录的 init + status 耗时 |

**B1、B2、B3、B7 是最要命的四条**——它们直接影响三个核心模块（Watchdog、OOM 调度、成本、文件一致性）是否正确。

## 3. 三条阻塞项

如果只决定三件事，就决定这三条：

| # | 问题 | 为什么阻塞 |
| --- | --- | --- |
| **S1** | 独立 OS 账号 | 决定整个安全模型能承诺到什么程度。不接受就要承认"Agent 与用户同权限"，并据此限制它接触的数据 |
| **C1** | 首版 E2E 加密 | 决定 relay 能不能托管给第三方。后加 = 改协议 |
| **C3** | 服务器不可达时是否自动转本地 | 决定会不会脑裂。这是数据一致性问题，不是产品偏好 |

这三条的共同点：**都是"以后改代价极高"的决定**，不是功能取舍。

## 4. 已明确接受的风险（不算开放问题）

这些已经决定了"接受"，列表是为了以后不假装解决了：

| 风险 | 为什么接受 | 出处 |
| --- | --- | --- |
| Agent 在授权范围内的错误判断 | 给 Agent 授权的固有代价 | [70](70-security.md) §2 T1 |

| Watchdog 不可能零误报 | 有打扰预算与自动降级 | [20](20-design.md) §3.4 |

| 单机形态无持久性 | 机器休眠 = 全停，这是固有代价 | [55](55-cluster.md) §7 |

## 5. 问题里还有一类：这个问题本身可能问错了

值得单独记一笔，因为它会影响后面所有讨论。

| 原问题 | 为什么可能问错了 | 现在怎么看 |
| --- | --- | --- |
| "手动开关如何解决操作成本" | 原以为要在"手动/自动"之间选，其实该分开：**场景级一次决定 + 任务级由架构保证** | 闪电图标 = 创建时选会话类型，不是运行时逐条选 |
| "如何把控 Worker 细节" | 原以为要靠审阅，其实**审阅不可扩展**（Router 被告知不许看细节） | 改为可判定谓词 + 三方证据交叉 |
| "如何让用户按习惯定制" | 原以为要大幅 settings，其实**每个 setting 都是一次认知负担 + 一个测试维度 + 一个升级兼容成本** | Few settings；三层（代码强制/提示词/枚举）+ 从行为推断 |
| "多设备如何协调 key 池开销" | 只要**模型调用不出控制面**，key 池问题就不存在 | 这是存算分离被低估的副产品 |

这四条都是"问题在提出时假设了一种架构，而那种架构被后面的决策排除了"。
