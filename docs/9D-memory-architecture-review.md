## 一、当前架构是什么

### 1.1 一次请求的上下文装配

```
request/header（配置 + 工具 schema，日志态）
        +
Session.deriveMessages()（有序 surface 投影）
  ├─ node 0: system prompt（一个 system/message 事件，不是请求字段）
  ├─ developer 工具增删通告
  ├─ 用户/harness 注入消息（含 runtime context，包在 <system-reminder> 里）
  ├─ assistant 消息
  └─ 工具结果
```

**关键结构事实**：system prompt **不是请求参数**，而是日志里的 surface 节点 0。
这决定了三件事：

| 后果 | 说明 |
| --- | --- |
| 压缩永不碰它 | `selectCompactableRange()` 从第 1 号节点起才算候选 |
| 改提示词 = 换节点 | KV cache 从该点起失效 |
| 重注入是天然免疫的 | AGENTS.md / skill 走这条路，压缩影响不到 |

### 1.2 五种注入源，四种存活语义

这是源码调研最意外的发现（缺陷 4 修正版）：

| 注入源 | 载体 | 压缩后是否存活 | 契约是否明确 |
| --- | --- | --- | --- |
| system prompt 段 | node 0 | ✅ 永不被压 | 明确 |
| AGENTS.md | 系统段 | ✅ 遮蔽后从磁盘重建自愈 | 隐含（靠 surface 可见性） |
| goal | 系统段 | ✅ | 明确 |
| 普通历史 | surface 节点 | ❌ 会被压缩 | 明确 |
| runtime context | user 消息尾部 | ⚠️ 内容不变则不重复注入 | 不明确 |
| **工具 schema** | request/header | ✅ 永不压缩 | 但**恒定占 12,139 tokens** |

**没有统一契约**：新插件作者无法从 API 上知道"我的注入会不会活过压缩"。

### 1.3 记忆机制的实际状态

| 机制 | 存在 | 默认启用 | 模型能否感知 |
| --- | --- | --- | --- |
| 压缩 compaction | ✅ | ✅ | **仅"有检查点"**，无量化 |
| 裁剪 prune | ✅ | ✅（随压缩） | 只有一个 `[... pruned ...]` 标记 |
| 跨会话检索 `session-query` | ✅ | ❌ **三层链路默认全关** | 不可用 |
| `tool-session-query` | ✅ | ❌ **未挂载** | 不可用 |
| AGENTS.md | ✅ | ✅ | 仅超预算时告知 |
| spill（大内容落盘） | ✅ | ✅ | ✅ **有路径、可取回** |

## 二、不合理处在哪

### 不合理 1：压缩按位置剪切，不按重要性

`selectCompactableRange()` 只做三件事：

1. 跳过 node 0（system prompt）
2. 按 `retainTokens` 保留尾部
3. 保证 tool-call / result 不拆对

**它不看内容重要性。** 第 1 轮用户说的硬约束，和第 1 轮 grep 的噪音，在算法眼里**等价**。

唯一补偿是摘要 prompt 的 8 个固定小节，质量全靠那一次调用。而 `compactionRetries: 1` 意味着最多压两轮，然后继续往前削。

**实测印证**：17 次压缩合计遮蔽 **15,768 个节点 / 4,228,403 tokens**。单次最重 479,142 tokens / 1,602 条事件。

### 不合理 2：系统主动压制"记忆完整性自描述"

两句原文（`dsh-compaction-basic`）：

```markdown
# 摘要指令
- Do NOT mention this summarization request or that the context was compacted.

# 检查点前导
…without acknowledging this checkpoint.
```

而 `shadowedTokenCount` / `shadowedSeqs` / 第几次压缩 / 摘要模型与成本——**全在 log-only 事件里**，模型看不到。

**这是全仓库最刺眼的一处不对称**：同一系统里，`dsh-spill-policy` 会明确说
`Omitted 48392 bytes. Full result at: /path，用 read/grep 取回`，
`dsh-agent-instructions` 会指名被省略的路径——
**证明"告知规模 + 给可操作路径"完全做得到**，只是压缩这条路径没有做。

### 不合理 3：prune 是没有出口的信息黑洞，且与 spill 冲突

工具结果中段被换成 `[... tool result middle pruned ...]`：

- 不给字符数
- 不给路径
- **不落 spill 文件**

压缩至少还有摘要，**prune 是纯丢弃**。

而 `dsh-base` **同时挂载了 pruner 和 spill-policy**：

| 路径 | 模型知道 | 能否取回 |
| --- | --- | --- |
| spill（结果太大） | ✅ 有路径 | ✅ |
| prune（压缩触发后） | ❌ 只有标记 | ❌ |

> **同样"结果太大"，走哪条路取决于是否触发压缩阈值，而不取决于哪个更安全。**

**实测数据**：59 次 prune，原文 1,166,597 → 304,427 字符（砍掉 62.3%），固定裁到 5,159 字符，**59/59 无回源句柄**。

### 不合理 4：唯一能补救的通道默认全关

`session-query` 三层链路默认全关、`tool-session-query` 未挂载、`openAt: never`。

**原始事件全部完好躺在 `.jsonl.zstd` 里**（我这次亲自解压了 243 个文件，223,513 条记录条条可读）。

数据没丢，**出口被关上了**。

### 不合理 5：五种注入源没有统一存活契约

见 §1.2。这不是"某个功能缺失"，是**架构层面缺少一个契约**：
插件作者无法表达"我的注入必须在压缩后存活"，系统也无法保证。

### 不合理 6：工具 schema 的恒定开销无人治理

实测：工具 schema 平均 **12,139 tokens**，系统提示仅 1,682。
某短会话（`你好，你是谁`）：**tools 14,904 vs msg 2,307**——工具是对话的 6.5 倍。

源码明确「无法缩减系统提示词、工具或会话前缀」。**为做一件小事，先付 1.2 万 token 的入场费。**

## 三、导致的问题（含我的亲历）

### 问题 1：三个缺陷相乘 = 不可见且不可救

> **压缩丢了东西 → 模型不知道丢了 → 也没有手段找回。**

而原始数据全都还在。**这个落差就是全部补救空间。**

### 问题 2：我亲历的三次失效

这是本文最硬的一部分，因为**有审计记录**（[9A](9A-self-audit.md)）。

| # | 我以为 | 实际 | 类型 |
| --- | --- | --- | --- |
| 1 | 我在讨论单会话记忆 | 我在讨论用户习惯 | 混淆对象 |
| 2 | 用公式推出"压缩 0 次" | 全库 20 次；本会话 0 次但**理由完全不对** | 用模型替代观测 |
| 3 | 大量输出被裁、我看不见 | **一个都没被裁**（本会话压力仅 36.4%） | 把机制存在当成已发生 |

**三次错误的共同点：都没有察觉。**

更关键的是审计给出的定量结论：

> **本会话中，我看不见的部分，100% 来自我自己的读取选择，0% 来自系统压缩。**

我漏读了 **496 行 / 716 行**（69.3%）的子代理报告，却以为问题是"被静默遗忘"。

**这个反转很重要**：它说明**当前的失效不只来自架构，也来自我自己的行为**。
所以解法必须同时覆盖"系统层面"与"用法层面"。

### 问题 3：检索救不了它（这是一条已被业界证实的原理）

> **检索的前提是「我知道该检索」，而遗忘恰好摧毁了这个前提。**

忘了某条约束，就不会去搜「为什么当初这么定」，因为它以为自己知道。

`memory-survey` 给出了一个更硬的数据支撑：

- **Cursor 官方承认 `@file` 不会内联进 prompt** → 把"必须始终生效"的约束寄托在指针上，等于不存在
- **白盒 context rot 研究：相关与无关的长上下文失败率相同（各 3/10，对比干净上下文 8/10）**
  → 伤害来自**长度本身**，不是"相关性不够"

所以「反正都相关，全塞进去」在数据上被证伪。

### 问题 4：业界出现了反向证据，说明没有银弹

`memory-survey` 发现一个反直觉事实：

> **ChatGPT 在 2026-06 把离散记忆条目退回为可编辑摘要**，方向与"结构化更抗压缩"相反。
> 原因是**结构化条目抗压缩但不抗矛盾累积**，摘要抗矛盾但不抗压缩。
> **选哪个取决于主要失败模式是「忘」还是「错」。**

这修正了我此前的一个隐含假设（"结构化一定更好"）。

## 四、解决方案

### 4.1 三条最该做的（按投入产出比排序）

#### 方案 A：给 prune 和压缩补上"指针"，而不是补上"告知"

**这是收益最高、成本最低的一条。**

业界证据（`memory-survey` §4.5）：MemGPT 的 70% 压力警告、Claude Code 的 `Referenced file`，
**都采用「指针」形式而非「你被裁了」的自我告知**——同样的 token 预算，前者买到能力，后者只买到焦虑。

具体：

```
# prune 现在
[... tool result middle pruned ...]

# 应该
[已移出 12,847 字符 · 完整内容在 spill 文件 /path · 用 read 取回]
```

```
# 压缩现在
<compacted-summary>…</compacted-summary>

# 应该（在摘要末尾加一行）
[本次压缩遮蔽 2,143 条事件 / 479,142 tokens（seq 1000–3143）
 · 原始内容可用 session_query 按 seq 读取]
```

**关键点**：不是"告诉模型你丢了东西"（这只会产生焦虑），
而是**"告诉模型丢了什么、怎么取回"**（这产生能力）。

**代价**：几乎为零——`shadowedSeqs` 已经在事件里，只需多写一行。

#### 方案 B：把"必须存活"的东西从可压信道移出

业界共识（`memory-survey` §4.1）：

> Claude Code 的 `What survives compaction` 表证明：CLAUDE.md、auto memory、skill 描述
> 全部从磁盘**重新注入**，而路径作用域规则会被摘要掉。
> **官方因此明确要求：「必须跨压缩存活的规则就去掉 `paths:`」。**

dsh 的 AGENTS.md / skill 天然满足这一点。**缺的是两件事**：

1. **给重注入集合设硬预算**（业界在 200 行到 12k 字符之间）
2. **给插件一个显式契约**：`persistence: 're-injected' | 'compactable'`，
   让作者能声明"我的注入必须存活"，系统据此保证

第 2 条正是 §2 不合理 5 的解法。

#### 方案 C：把检索通道打开，并改变"谁决定拉取"

当前 `session-query` / `tool-session-query` 默认全关（不合理 4）。

但**只打开还不够**——`memory-survey` 的关键洞察：

> **关键在于谁来决定拉取。系统替模型猜测相关性时，猜错的那次没有任何信号。**

所以正确做法是：

| 谁决定 | 场景 | 设计 |
| --- | --- | --- |
| **系统保证在场** | 违反一次就出事、且每轮都相关 | 重注入池（方案 B） |
| **模型主动拉** | 需要时才相关的细节 | 给**明确的指针**（方案 A）+ 打开检索（方案 C） |

**绝不做"系统自动猜相关性然后塞进去"**——context rot 研究证明了它无效。

### 4.2 中期：把原始层做成只追加、事实带有效期

业界主流（`memory-survey` §4.3/4.4）：

- Zep 的 episode **non-lossy**，事实只置 `t_invalid`
- Mem0g 明确「**标记失效而非物理删除**」

**理由**：这是"抽取策略可以迭代"的前提——换模型、改 prompt 时，派生层可以重算，基底不会毁掉。

dsh 落地成本极低：`.jsonl.zstd` 本身已经是只追加的，
缺的是一层**派生视图**（结构化条目 + `superseded_by` / `valid_from`），不需要图数据库。

### 4.3 长期：按"失败模式"而非"技术先进性"选形态

这是 `memory-survey` 最重要的提醒，也是对我此前设计的修正：

| 你的主要失败模式 | 选什么 | 理由 |
| --- | --- | --- |
| **忘**（丢了约束、丢了结论） | 结构化条目 + 只追加 | 抗压缩 |
| **错**（矛盾累积、过时事实） | 可编辑摘要 | 抗矛盾 |

**诚实标注**：`memory-survey` 明确说明「结构化更抗压缩」目前是
**机制推理 + 间接证据**，没有找到"同一信息两种存储形态经过 N 轮压缩后的保真度"对照实验。
**应当把它当作假设，不是既定事实。**

### 4.4 对我自己：加校验动作

架构解决不了"我没去读"，这部分只能靠纪律：

| 场景 | 校验动作 |
| --- | --- |
| 引用统计数字 | **这个数字属于哪个范围？** 本会话还是全库？ |
| 描述机制 | **它是"存在"还是"发生了"？** 查事件，别查文档 |
| 转述子代理结论 | **它回答的是我问的那个问题吗？** |
| 报告"我做了什么" | **这件事有外部记录吗？** 没有就标注"推断" |
| 读长文 | **我读了多少？** 716 行只读 220 行时，必须知道这是 30.7% |

## 五、一句话总结

> **当前架构的问题不是"记不住"，而是三件事叠加：**
> **压缩按位置剪切（不知道什么重要）× 系统禁止模型知道丢了什么 × 检索通道默认关闭。**
> **原始数据全都完好，缺的只是出口。**
>
> **而解法也不是"记得更多"：**
> **把必须活着的移出可压信道；把丢了的东西给一个指针；把检索的主动权交给模型而不是系统的猜测。**
