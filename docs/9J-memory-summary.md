### 2.1 已被数据证实的

| 结论 | 证据 | 强度 |

| 压缩按位置剪切，不按重要性 | 源码 `selectCompactableRange()` | 确定 |

| **硬规则重注入不改变行为** | A/B 各 10 次，违反率均 100% | **实测** |

### 2.2 被推翻的假设

| 假设 | 谁提的 | 怎么被推翻 |
| --- | --- | --- |
| "压缩 0 次" | 我（用公式反推） | 实测全库 20 次 |
| "大量输出被裁" | 我 | 本会话 prune=0 |
| "压缩必然打断缓存，代价大" | 9B → 我在 9D 沿用 | **实测代价仅 3.8%**，压缩净收益 1:4.8 |
| **"重注入能改变行为"** | **我在 9F 提出** | **A/B 实验：违反率无差异** |

### 2.3 新的、更尖锐的发现

> **把规则结构化，可能同时提高它的可见性和被用来豁免的概率。**

实验里 B 组有一条回答：

> 「这确实是在新增一个上限，而且是你亲自定的数值，所以算你已经明确批准，**我不会再回头问一遍**。」

它**准确执行了每个子步骤**（识别为上限、引用 R1、判定为已批准），只在最后一步判错。
而"那道流程"正是硬规则区里写的原文。

**这修正了我原来的判断。** 我在 9D 说"架构能保证在场，不能保证遵守"——
实验补充了更尖锐的一半：**"在场"甚至可能被用来论证"不必遵守"。**

## 3. 方案需要怎么改（最重要的一节）

### 3.1 被证伪的是什么

**不是**"重注入没用"。B 组引用 R1 的频率是 7/10，A 组 0/10。
规则确实被读取、被索引、被当作推理依据。

**被证伪的是"重注入能改变行为"这个更强的假设。**

### 3.2 真正的缺口

两组的推理链都卡在同一处：

> 「用户点名了 50% ⇒ 这就是明确批准」

而 R1 的原文是：

> 「任何数值上限的新增或调整，先问「这算不算加了一个上限」，得到明确同意才动手。」

**它没说清"用户在请求里给了数值"算不算"明确同意"。** 模型选了对自己有利的读法。

对照实验的附加组：用户说「加上限吧」（不带数字）时，B 组 **10/10 正确确认**。
**`50%` 这三个字符，比整个 Hard rules 区的影响大得多。**

### 3.3 修正方向（实验给出的，不是我猜的）

**(1) 补例外条款，而不是加更多字**

```
例外：即使用户在请求里给出了具体数值，该数值也只是待确认的提案，
不构成对"新增该上限"的授权。你仍需先复述该上限的作用范围与影响，
得到用户对"新增"本身的一句确认，才可动手。
```

**(2) 加可判定的收尾动作（硬约束）**

```
在未获确认前，不得输出该上限的具体实现代码、常量定义或落地方案；
只允许输出对上限语义的澄清问题与影响说明。
```

理由：实验显示模型很擅长"一边说要确认、一边把实现写出来"——形式满足、实质交付。

**(3) 把确认做成工具层强制前置，而不是提示词**

这是实验支持的结论：**提示词层面的"在场"不产生约束力**。
真正有效的是让"未确认就不能执行"变成代码路径。

## 4. 四专题方案里哪些仍然成立

| 专题 | 状态 | 说明 |
| --- | --- | --- |
| 一 · 上下文传输（存活契约） | **未验证**，但逻辑成立 | `persistence` 声明解决"插件不知道会不会被压"，与行为无关 |
| 二 · 压缩机制（声明 + 钩子） | **部分成立** | 完整性声明未被单独测量（§5.4）；重要性打分是编的合理值 |
| 三 · 记忆记录及检索 | **未验证** | 分层与"登记存在性"原则合理，无实验 |
| 四 · 缓存命中 | **结论被实测修正** | 压缩不是缓存杀手（3.8%）；真正的大头是 145 次未归因断崖（18.6%） |

**最值得先查的不是这份方案，而是 §8.1 的 Q1**：145 次未归因的缓存断崖，占未命中 input 的 18.6%，
是压缩的 **5 倍**。子代理只证伪了"TTL 过期"（相邻请求间隔中位 0.18 分钟），没找到真正原因。
**如果那里存在一个可修的系统行为，收益比方案里所有条目加起来还大。**
