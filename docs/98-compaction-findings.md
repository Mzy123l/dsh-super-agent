## 2. 自动压缩的真实阈值

### 2.1 阈值公式（与实际数字完全吻合）

设上下文窗口 `W`、生效请求输出上限 `O`（即 `request/header.config.maxTokens`，缺省回退适配器默认值）、余量 `B = 65,536`：

```
阈值 thresholdTokens = floor(min(W × 0.8, W − O − B))
```

数据侧验证方法：压力 = `totalTokens − outputTokens`（= `inputTokens + cacheReadTokens + cacheWriteTokens`）。
该等式在全部 **31,256 / 31,256** 条 `assistant/message.usage` 上成立（覆盖率 100%，等价形式为 `totalTokens = input + cacheRead + cacheWrite + output`）。

> ⚠️ 重要陷阱：`usage.inputTokens` 单独看只有几百到几千（如 147、622、9977），**不是**请求的真实尺寸。真实请求几乎全部命中 KV cache，压力体现在 `cacheReadTokens`（几十万）。只看 `inputTokens` 会得出"上下文才用了 0.01%"的错误结论。

### 2.2 各自动压缩的触发前数据

| 会话 | 轮次 | 触发前压力 | 窗口 W | 输出预留 O | 0.8×W | W−O−B | **阈值** | 阈值/窗口 | **压力/阈值** | 压力/窗口 | 类别 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| `7f8d9d53` | 4 | 196,563 | 262,144 | **0** | 209,715 | **196,608** | **196,608** | 75.00% | **99.98%** | 74.98% | 阈值（先 prune） |
| `7d95060d` | 7 | 196,475 | 262,144 | **0** | 209,715 | **196,608** | **196,608** | 75.00% | **99.93%** | 74.95% | 阈值（先 prune） |
| `c8dfb160` | 21 | 676,907 | 1,000,000 | 256,000 | 800,000 | **678,464** | **678,464** | 67.85% | **99.77%** | 67.69% | 阈值 |
| `69cd6cb9` | 9 | 726,636 | 1,048,576 | 256,000 | 838,860 | **727,040** | **727,040** | 69.34% | **99.94%** | 69.30% | 阈值 |
| `9ecf69ac` | 20 | 664,174 | 1,000,000 | **0** | **800,000** | 934,464 | 800,000 | 80.00% | 83.02% | 66.42% | **溢出恢复** |
| `9ecf69ac` | 52 | 659,859 | 1,000,000 | **0** | **800,000** | 934,464 | 800,000 | 80.00% | 82.48% | 65.99% | **溢出恢复** |

> `O = 0` 的含义：这些路由的 `request/header.config.maxTokens` **完全没有设置**（`7f8d9d53`、`7d95060d`、`9ecf69ac`、`120809f4` 的 header 里都查不到该字段），故回退为 0，阈值由另一项决定。
> `9ecf69ac` 两行是**溢出恢复**，它们**根本没到阈值**（83.02%、82.48%，且远低于 80% 窗口线），所以"压力/阈值"这一列对它们没有判定意义，仅列出以便对照。

### 2.3 结论：比例**不稳定**，但公式稳定

- **"恒定某个比例"是错的。** 实测阈值占窗口的比例从 **67.85% 到 80.00%** 不等，取决于该路由是否设了 `maxTokens`。
  - `maxTokens` 未设置（O=0）且窗口大时，容量项 `W − 0 − 65536` 比 `0.8W` 更宽松，**比例项胜出**：1,000,000 → **800,000（80.00%）**；1,048,576 → 838,860（80.00%）。
  - `maxTokens = 256,000` 时，容量项 `W − 256000 − 65536` **小于** `0.8W`，**容量项胜出**：1,000,000 → **678,464（67.85%）**；1,048,576 → **727,040（69.34%）**。
  - 窗口 262,144 且 O=0 时，`0.8W = 209,715` 但 `W − 65536 = 196,608`，**容量项胜出**：→ **196,608（75.00%）**。余量 65,536 在这个窗口下占了整整 25%。
- **公式是稳定的。** 4 次非溢出自动压缩中，触发前压力全部落在阈值的 **99.77%–99.98%**（676,907/678,464 = 99.77%；726,636/727,040 = 99.94%；196,563/196,608 = 99.98%；196,475/196,608 = 99.93%）。
  这不是巧合，而是"上一步刚记录压力 → 本步新增一点 tool 往返 → pre-step 检查时越过阈值"的必然结果：差额分别只有 1,557 / 404 / 45 / 133 tokens。
- **窗口越小，比例越畸形。** `W = 262,144` 时余量 65,536 占窗口 25%，把阈值压到 **196,608（75%）**——所以这两个会话"在第 4、第 7 轮就用掉 3/4 窗口"时才被判定为"刚越过阈值"。
- **上游真实上限可能与声明不符（重要发现）。** `9ecf69ac` 的 `request/context` 声明 `contextWindow: 1000000`，自动阈值因此算作 800,000，**永远等不到**；实测上游在压力 ≈ 664K / 660K 时就返回 `400 / prompt is too long (upstream code 11115)`。也就是说：
  - 自动阈值这条路径**从未在这两个会话上触发过**；
  - 真正救场的是 **`CONTEXT_WINDOW_EXCEEDED` 溢出恢复**（2 次），它**绕过阈值与尾部保留策略**，直接做"最大头部缩减"。
  - 后果：声明窗口（1,000,000）比上游真实容量（≤664K）大约 **50%**，导致**每次都先撞墙一次、浪费一次完整请求**，再靠溢出恢复补救。

## 3. 早期压缩的成因（第 4 轮就压缩是怎么回事）

**结论：不是"单条消息极大"，而是"窗口小 + 余量固定"，加上早期轮次本身就积累了大量内容。**

### 3.1 真相：轮次号小 ≠ 内容少

`7f8d9d53` 在第 4 轮触发，但它的第 1 轮就已经产生 **725 个事件 / 158 次工具调用 / 482,345 字符内容**（≈150,733 tokens）。

| 会话 | 第 1 轮事件数 | 第 1 轮工具结果数 | 第 1 轮内容字符 | 第 1 轮估算 tokens |
|---|---:|---:|---:|---:|
| `7f8d9d53` | 725 | 158 | 482,345 | ≈150,733 |
| `7d95060d` | 951 | 191 | 178,422 | ≈55,757 |

`7f8d9d53` 仅第 1 轮就吃掉了 262,144 窗口的 **57.5%**（482,345 字符 ≈ 150,733 tokens）；到第 4 轮时累计压力 196,563——**轮次 4 是"第 4 个用户回合"，而模型在此期间已经往返了 700+ 个 step**。轮次是用户的计数单位，与上下文消耗无关。

### 3.2 单条最大消息（证明不是"一条巨型消息"的锅）

| 会话 | 全会话最大单条 | 大小 | 位置 |
|---|---|---:|---|
| `7f8d9d53` | `tool/result` | **55,770 字符**（≈17,428 tokens，按 /3.2 估） | turn1 / seq174 |
| `7d95060d` | `tool/result` | **14,898 字符**（≈4,656 tokens） | turn1 / seq187 |

- 55,770 字符 ≈ 17,428 tokens，**只占 262,144 窗口的 6.6%**，远不足以"一条就超阈值"。
- 该条在第 1 轮就出现了，但压缩直到第 4 轮才发生，**间隔了 3 个完整回合**——这说明是渐进累积而非单条爆破。
- 这两条巨型结果后来都被 `compaction/prune` 裁到 5,159 字符（见第 6 节），说明它们是"被治理对象"而非"触发器"。

### 3.3 为什么压缩"晚"了

- **阈值被余量条款从 209,715 砍到 196,608。** `0.8 × 262,144 = 209,715`，但 `W − O − B = 262,144 − 0 − 65,536 = **196,608**`，容量项胜出。余量 65,536 在 1M 窗口下只占 6.6%，显得无害；在 262K 窗口下占 **25%**——这才是"第 4 轮就压"的数学根源。
- **触发时机是"下一个 pre-step"**：压缩不是压在上一步请求上，而是在**下一步请求派生前**检查。所以日志里最后一条 `usage` 的压力总是恰好贴着阈值下方（99.93%–99.98%），压缩发生在它之后 1–2 个 step（含一次工具往返）。
- 时间线实证（`7f8d9d53`）：`step19 @seq1011` 记录 P=196,563（距阈值仅差 45）→ 两次 `tool/call` + `tool/result`（seq1012–1015）→ 新 step 开始 → `compaction/start@1017`。**越过阈值的是工具往返新增的那部分（几十~几百 token），不是任何一条历史消息。**

## 4. 压缩遮蔽了什么（shadowedSeqs / shadowedTokenCount 统计）

### 4.1 字段确认

`compaction/summary` 确实携带 `shadowedSeqs`、`shadowedRange`、`shadowedTokenCount`（17 次全有）。
`compaction/prune` 也带同样三字段（59 次全有）。
两者都**不进入 surface**（log-only），真正的替换由紧随其后的一条 `user/message`（summary）或 `tool/result`（prune）完成——**该相邻性是契约性的**。

### 4.2 17 次成功压缩的遮蔽量

| 指标 | 数值 |
|---|---:|
| 遮蔽 surface 节点总数 | **15,768** |
| 遮蔽 token 总数 | **4,228,403** |
| 单次遮蔽节点数 min / 中位 / max | 25 / 920 / 2,143 |
| 单次遮蔽 token min / max | 26,478 / 479,142 |
| 摘要消息（注入的 `user/message`）长度合计 | 242,339 字符 |
| 摘要消息长度 min / max | 7,283 / 24,930 字符 |
| 摘要模型调用用量 | 输入 391–619,982，输出 2,333–4,348 tokens |

**压缩增益**：17 次压缩合计用 **242,339 字符**的摘要，替换掉 **4,228,403 tokens** 的原文历史。
按 "1 token ≈ 3.2 字符" 粗估，摘要本身约占 **75.7K tokens**，净释放约 **4.15M tokens**，单次净释放量在 **22,461 – 473,411 tokens** 之间。

**摘要的 `shadowedRange` 起始恒为 8–10**（surface 位置 0 是系统提示词，**永不被遮蔽**；`system/message` 节点 0 被明确排除在可选范围之外）。`end` 则停在压缩点前若干节点（例如 `9ecf69ac/5671` 的 range 是 `{start:10, end:5643}`，而 start 在 seq 5671）——说明**近端尾部被逐字保留**，保留量按 `0.16 × (W − O)` 计算。

### 4.3 压缩后模型看到的下一条消息

**17 / 17** 次压缩中，`compaction/summary` 的下一个事件**必定**是 `user/message`，且其 `data.source.compactionId` 与 summary 的 `compactionId` **完全一致**（17/17 匹配）。消息内容形如：

```
This is an automatically generated checkpoint condensing an earlier span of the conversation
to free up context. Treat the captured context as established background and build on it without
restating it. Continue the task directly from the messages that follow, without acknowledging
this checkpoint.

<compacted-summary>
## Primary Request and Intent
...
</compacted-summary>
```

- `<compacted-summary>` 开闭标签 **17/17 都存在**。
- `data.source.kind` = `"compact-checkpoint"`（手动压缩时额外带 `sourceCommandId`）。
- **原始内容确实不可见**：`<compacted-summary>` 之内只有模型重写的摘要文本，没有任何原始消息、原始工具结果或引用指针。被遮蔽的 15,768 个节点在模型可见层**没有留下任何可回溯句柄**。

## 5. 模型是否被通知（关键结论）

### 5.1 有"通用告知"，无"量化告知"

**存在一条固定前言（17/17 次都注入）**，明确告知模型："这是一段被折叠的早期对话，把它当作既定背景，不要复述、不要确认这个检查点"。

**但是：不存在任何形如"你丢失了 N 条消息 / 遮蔽了 N 个 token"的量化提示。**

对全部 17 条注入消息做了正则扫描（`丢失|discarded|dropped|lost|omitted|no longer available|\d+ (messages|items|entries|条)`）：

| 检查项 | 结果 |
|---|---|
| 前言里出现 "N 条消息" 之类计数 | **0 / 17** |
| 前言里出现 "shadowed / pruned / compacted 了多少" | **0 / 17** |
| 注入文本中命中 `丢失/discarded/dropped/lost` 等字样 | 8 / 17，**但全部是用户在原始对话里自己说的话**（如"别丢三落四的"、"loss"一词出现在摘要正文的需求描述里），**不是系统提示** |
| 是否携带 `shadowedSeqs` 给模型 | **否**（该字段只在日志事件里，从不进 surface） |

### 5.2 结论

> **DSH 的压缩给了模型"发生了什么"的定性说明，但没有给"丢了多少"的定量说明。**
> 模型知道"前面被折叠成摘要了"，但**无从知道**折叠掉了 2,143 个事件还是 25 个，也无从知道释放了 479K 还是 26K token。
> 更关键的是：**摘要一旦漏掉某个事实，模型没有任何机制察觉"这里原本有东西"**——没有"你丢失了 N 条消息"的提示，也没有被遮蔽节点的 seq 列表。

这带来一个具体风险：模型无法对自己的记忆完整度做校准。它会像对待完整历史一样对待摘要，而摘要是一次**有损、单次、模型重写**的投影（`maxTokens` 上限 65,536，实测输出仅 2,333–4,348 tokens，压缩率超过 99%）。

### 5.3 对照：prune 反而**有**提示

与 summary 相反，`compaction/prune` 的替换文本里**保留了显式标记**：

```
[... tool result middle pruned ...]
```

59 / 59 次 prune **全部**包含该标记（位于替换后第 4,098 字符处）。也就是说：**工具结果被裁剪时模型看得见"中段被裁"，但历史被摘要时模型看不见"少了多少"。** 这个不对称值得注意。

## 6. 工具结果裁剪（prune）的实测

### 6.1 发生时机

59 次 prune 分布在 **5 个会话、7 个轮次**。它们聚合为 **7 个"簇"**（连续发生的 prune 为一个簇）。**prune 只在压缩触发条件已满足后才会运行**——下表中每一簇的裁剪前压力都已达到或超出阈值，或已触发溢出。

| 会话 | 轮次 | prune 次数 | 裁剪前压力 | 裁剪后首个记录压力 | 阈值 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| `7f8d9d53` | turn **1** | **10** | 196,498 | **135,912** | 196,608 | 降到阈值下 → **该轮未压缩**（下一次压缩晚到 turn 4） |
| `7f8d9d53` | turn 4 | 2 | 196,133 | 191,045 | 196,608 | 也降到阈值下，但**仍压缩了**（turn4@1017） |
| `7d95060d` | turn 7 | 4 | 195,337 | 190,083 | 196,608 | 降到阈值下，**但仍压缩**（turn7@1396） |
| `9ecf69ac` | turn 20 | 7 | 664,174 | **28,693** | 800,000 | 溢出恢复路径；仍压缩（turn20@5671） |
| `9ecf69ac` | turn 52 | 10 | 659,859 | **38,335** | 800,000 | 溢出恢复路径；仍压缩（turn52@12159） |
| `c8dfb160` | turn **18** | **14** | 678,134 | 637,426 | 678,464 | 降到阈值下 → **该轮未压缩**（下一次压缩晚到 turn 21） |
| `0b28de6a` | turn **28** | **12** | 677,043 | **543,416** | 678,464 | 降到阈值下 → **该轮未压缩，且此后全程再未压缩** |

**关键发现：7 个 prune 簇里，5 个（42/59 次 = 71.2%）在裁剪后并没有立即压缩。**

| 簇 | prune 次数 | 裁剪后是否紧接 `compaction/start` |
|---|---:|---|
| `7f8d9d53` turn1 | 10 | **否** |
| `7f8d9d53` turn4 | 2 | **否** |
| `7d95060d` turn7 | 4 | **否** |
| `0b28de6a` turn28 | 12 | **否** |
| `c8dfb160` turn18 | 14 | **否** |
| `9ecf69ac` turn20 | 7 | **是** |
| `9ecf69ac` turn52 | 10 | **是** |

严格判据：从簇的最后一个 `compaction/prune` 往后扫描，**在遇到下一个 `assistant/message`（即下一次真实请求返回）之前**是否出现 `compaction/start`。

解读：

- **5 个"否"说明裁剪经常就够了。** 最典型的是 `0b28de6a`：12 次裁剪把压力从 677,043 拉到 543,416，全程**再没有任何压缩**——这是 prune 独立解决压力问题的完整案例，**省掉了一次完整的摘要模型调用**。
- **"否"不等于"该轮一定不压缩"，而是"延迟了"。** `7f8d9d53/turn1` 裁剪后压力 135,912 远低于阈值，直到 **turn 4** 才又压；`c8dfb160/turn18` 裁剪到 637,426，直到 **turn 21** 才又压。也就是说裁剪买到的只是"几轮喘息时间"，不是"永久解决"。
- **2 个"是"全部来自 `9ecf69ac`，且都是溢出恢复路径。** 这两次（压力 664K / 660K）先做 prune 把压力降到 28,693 / 38,335，**依然**继续摘要压缩——因为 `CONTEXT_WINDOW_EXCEEDED` 恢复路径**绕过阈值判定与 16% 尾部保留策略**，只执行一次"最大头部缩减"，不以"降到阈值下"为停止条件。
- 结论：**prune 与 summary 不是"二选一"，而是"先试零成本的 prune，够就收工，不够再付费摘要"**；但溢出恢复是例外，它不管够不够都要压。

### 6.2 裁剪前后字符数

| 指标 | 数值 |
|---|---:|
| prune 次数 | **59** |
| 每次遮蔽节点数 | **恒为 1**（59/59 都是单个 `tool/result`） |
| `shadowedTokenCount` 合计 | **292,140** |
| 单次 `shadowedTokenCount` min / max | 2,082 / 13,951 |
| 原文合计字符 | **1,166,597** |
| 替换后合计字符 | **304,427** |
| 平均削减比例 | **62.3%**（单条 37.8% – 90.7%） |

替换后的长度高度集中在 **5,159 字符**（52/59 次精确等于 5159，其余 5,160/5,161/5,167/5,173/5,176 是各行尾换行差异）：

```
4,096（head）+ 35（"[\n\n[... tool result middle pruned ...]\n\n]"）+ 1,024（tail）≈ 5,159
```

即默认配置 `thresholdChars: 8192 / headChars: 4096 / tailChars: 1024`——**保留头部 4KB、尾部 1KB，砍掉中间**。

典型例子：

| 会话/seq | 原字符 | 替换后 | 削减 |
|---|---:|---:|---:|
| `7f8d9d53` seq578 | 55,770 | 5,159 | **90.7%** |
| `0b28de6a` seq1854 | 49,930 | 5,159 | 89.7% |
| `c8dfb160` seq3397 | 21,691 | 5,159 | 76.2% |
| `9ecf69ac` seq5659 | 8,333 | 5,159 | **38.1%**（最小） |

注意：即使原文只有 8,333 字符（刚过 8,192 阈值），也会被裁到 5,159，**净省仅 38%。说明裁剪对小结果性价比很低**——但阈值 8,192 是硬门限，超过就裁。

### 6.3 被裁掉的内容模型还能不能取回？

**不能，且没有任何回源句柄。**

- `compaction/prune` 的 `data` 只有 `{shadowedRange, shadowedSeqs, shadowedTokenCount}` 三个字段，**没有内容副本**。
- 替换后的 `tool/result.data` 只有 `{turn, step, message}`（部分带 `meta`），`message.source` 仍是原始 `{kind:"tool", callId:"..."}`——**callId 指向的是调用，不是结果内容**。
- 替换事件里**没有** `sourceEventSeqs` 之类的回溯指针（实现里虽有该字段概念，但实测 59/59 未落到事件数据中）。
- `meta` 字段（50/59 条有）存的是**原始工具调用的参数元信息**，不是结果内容：
  - 读文件类：`{path, offset, lines, totalLines, lang}` — 有路径和行号，**理论上模型可以重新 read 一次把内容读回来**（前提是文件未变、且模型知道该重读）。
  - 抓网页类：`{url, statusCode, truncated}` — 同样可以重新 fetch。
  - 搜索类：`{shape:"matches", files:[...], truncated, total}` — 信息不足以还原结果。
- **但模型完全不知道发生过裁剪之外的任何事**：它只看到 `[... tool result middle pruned ...]` 这个标记，标记里**没有路径、没有行号范围、没有"原长多少"**。要重新取回，模型必须自己意识到"这个结果被裁了，我该按 meta 里的 path 重读"——而 meta 是否进入模型可见层，取决于投影实现，实测日志中无法证明它被呈现。

**结论：被裁内容对模型而言实质不可取回。** 标记告知了"有东西没了"，却没给出"去哪找回来"的任何线索。

## 7. 结论与设计含义

### 7.1 一句话结论

> **DSH 的自动压缩不是"窗口满了才压"，而是在每次请求派生前检查"上一次请求的真实尺寸 + 本步新增"是否越过 `floor(min(W×0.8, W−O−65536))`；因此它表现为"一越过阈值就在下一个 step 立刻压缩"，4 次阈值触发实测都落在阈值的 99.77%–99.98%。**

### 7.2 五条可操作的事实

1. **阈值不是一个比例，是一个公式。** `min(0.8W, W − maxTokens − 65536)`。占窗口比例实测在 **67.85%–80.00%** 之间浮动：`maxTokens` 设了 256,000 的路由取容量项（67.85%–69.34%），没设的路由取比例项（80.00%）。
2. **`headroomTokens=65536` 是隐藏的杀手。** 在 1M 窗口下它只占 6.6%，几乎无害；在 262K 窗口下它占 **25%**，把阈值从 209,715 砍到 196,608（75%），这才是"第 4 轮就压缩"的唯一数学原因。
3. **早期压缩 ≠ 单条消息爆炸。** 实测最大单条只有 55,770 字符（≈17,428 tokens，占窗口 **6.6%**）。真正的成因是**早期轮次本身就极长**：`7f8d9d53` 的第 1 轮有 725 个事件、158 次工具调用、482,345 字符（≈150,733 tokens），单轮就吃掉 **57.5%** 窗口。
4. **声明窗口可能大于上游真实容量。** `9ecf69ac` 声明 1,000,000 但上游在 ~664K 就 400 拒绝，导致自动阈值（800K）**永远等不到**，只能靠 `CONTEXT_WINDOW_EXCEEDED` 溢出恢复兜底——每次都先浪费一次完整请求。
5. **模型被定性告知、但被定量蒙蔽。** 17/17 次注入都有固定前言与 `<compacted-summary>` 标签，但 **0/17** 次包含"遮蔽了多少事件/token"的计数，也不提供被遮蔽的 seq 列表。摘要是一次有损重写（4.23M tokens → 约 76K tokens），模型却无法校准自己的记忆完整度。

### 7.3 设计含义（供后续决策）

| 观察到的问题 | 设计含义 |
|---|---|
| 阈值在压缩时已消耗 67%–80% 窗口 | 上下文"安全余量"实际只剩 20%–33%，对长工具链任务偏紧。若要更保守，应下调 `thresholdRatio`（如 0.6）而非调 `headroomTokens` |
| 小窗口被 `headroomTokens` 放大惩罚 | `headroomTokens` 应随窗口缩放（如 `min(65536, W×0.05)`），否则 262K 窗口下它独占 25%，阈值被压到 75% 而非设计的 80% |
| prune 阈值固定 8,192 字符 | 对 8–12K 的结果净省仅 38%–50%，性价比低；可考虑按窗口动态设定阈值，或对"刚好超线"的结果跳过 |
| prune 族里 5/7 簇（42/59 次 = 71.2%）未立即摘要 | 这是**好设计**：先用零成本手段（不调模型）试，`0b28de6a` 的 12 次裁剪把压力从 677,043 拉到 543,416 并**彻底避免**了摘要调用。但代价是被裁内容永久丢失 |
| 裁剪只买"几轮喘息" | `7f8d9d53/turn1` 裁到 135,912（远低于阈值）仍在 turn 4 再压；`c8dfb160/turn18` 裁到 637,426 仍在 turn 21 再压。裁剪不是終局解 |
| 摘要无量化告知 | 建议在注入的 `<compacted-summary>` 前追加一行：`[已折叠 N 个事件 / 约 M tokens，原内容不可访问]`，让模型能对自身记忆做校准 |
| prune 有标记、summary 无计数 | 两者提示强度不对称。工具结果被裁时模型看得见标记与位置，历史被摘要时却看不到规模 |
| 溢出路径绕过阈值 | 这是必要的兜底，但暴露了"声明容量不可信"的问题。应让 `request/context` 的上游拒绝反馈回写 `contextWindow`，避免重复撞墙 |

### 7.4 未找到 / 无法确认

- **`compaction/summary` 的 `shadowedSeqs` 与最终 `user/message` 的节点对应关系**：日志里 `shadowedSeqs` 是 surface 位置 seq 列表，但注入消息只有一条 `user/message`，无法逐条验证"每个被遮蔽节点确实不在模型可见层"。只能确认注入内容中不含原文。
- **prune 的 `meta` 是否进入模型可见层**：日志记录的是事件数据，投影规则需读代码确认，本次未验证。
- **`e795c865` 的 3 次失败**：`402 status code (no body)` 无进一步原因，无法判定是额度还是计费问题。
- **是否有会话做了压缩但日志丢失**：无法排除，但 `compaction/start` 与 `compaction/end` 成对出现（20/20），未见悬挂。
- **非溢出簇上"裁剪后压力"的判定基准**：本文的"裁剪后首个记录压力"取自该簇之后的第一次 `assistant/message`，它已经包含了一次全新请求，**不等于**压缩引擎内部重测量得到的值；因此不能据此断言"引擎认为已达标"。这也是为什么 5 个"否"簇里有个别（如 `7d95060d/turn7`、`7f8d9d53/turn4`）在后继轮次仍有压缩。
