# 模型与成本

> 你要求"也多想一想其他方面"。成本这一章此前只有零散结论，这里收拢成可执行的模型。
> 本章的结论会反过来约束前面的设计选择，所以放在文件与集群之后、安全之前。

## 1. 先把成本拆成四个池

混在一起谈会找不到杠杆。实际有四个独立的成本池：

| 池 | 谁在花 | 杠杆 | 单机是否可优化 |
| --- | --- | --- | --- |
| **A. 模型调用** | 控制面（Router / Worker / Watchdog / Assessment） | 前缀缓存、模型选择、预算 | 是 |
| **B. 本地算力** | Worker 的命令执行 | 并发、内存、串行策略 | 是 |
| **C. 存储** | Session Log、git 对象、日志段、工件 | 归档、遗忘、压缩 | 是 |
| **D. 传输** | 集群形态下的 relay 流量 | 密文压缩、近端 relay、批次 | 集群才有 |

绝大多数讨论会盯着 A，但**单机部署里 B 和 C 更容易失控**：一个失控的构建进程能吃光内存，一个不归档的 Session Log 能吃掉 10GB 磁盘。

## 2. 模型成本：缓存是主战场

长文自己承认："Super-agent 整体比单会话消耗更多缓存读 token，效率是用 token 换来的。"所以问题不是"要不要多花"，而是"花在哪儿值"。

### 2.1 前缀稳定化（最高杠杆）

KV cache 按**前缀**复用。前缀里有一处不同，整条缓存作废。决定前缀的三样东西必须**在创建时绑定**（D3 的收益）：

| 因素 | 规则 |
| --- | --- |
| 模型 | Worker 统一模型（R8）；混用 = N 条独立前缀 |
| 工具 schema | 同一角色的 preset 固定 |
| 提示词顺序 | **易变内容往后放** |

第三条是官方原型最精妙的一手：

> `runtime/policy` 放在 prompt 最末尾，理由是 "so a Policy change leaves the preceding prompt text unchanged"

推理：**把易变的东西放到最后，以至于它变了也不影响前面**。推广开来，提示词应该按"变化频率"排序：

```
1. 共享指令 + 角色            几乎不变
2. 团队三个 section           人改才变
3. 订阅与回复规则              不变
4. 分派/工作指令              不变
5. admission 指令（仅 Router） 不变
6. handoff 指令               不变
7. environment                部署时变
8. policy                     每次设置变都可能变   ← 最后
```

### 2.2 复用率优先于单次单价

一个反直觉的结论：**便宜的模型 + 差的前缀，可能比贵的模型 + 好的前缀更贵。**

粗估（前缀 8k tokens、并发 10）：

| 场景 | 每轮 prefill |
| --- | --- |
| 前缀分裂、零命中 | 80k |
| 同模型同前缀，命中 | 接近 0（只有新增部分） |

所以"给简单任务配便宜模型"这个直觉，在**多 Session 场景下经常是负收益**：省下的单价被废掉的缓存吃回去。

**判断规则**：只有当"便宜模型省下的单价 > 前缀分裂损失的缓存"时才分模型。小团队通常不成立。

### 2.3 少开 Session，多恢复

官方原型已经做对了这一点：**结束的 Ticket 保留订阅，人一句话恢复它而不是新建**。

新建 = 一整条新前缀；恢复 = 沿用旧前缀。这个杠杆比任何 prompt 优化都大，而且**它是架构决策，不是调优**。

### 2.4 四个角色的成本占比

| 角色 | 频率 | 单次成本 | 优化 |
| --- | --- | --- | --- |
| Router | 每条消息 | 长输入短输出 | 批处理（见 §2.5），轻量模型够用 |
| Worker | 每个 Ticket 多轮 | 最高 | 统一模型 + 缓存 + 压缩 |
| Assessment | 仅 proactive | 中 | 只在需要规则评估时调 |
| Watchdog | 定期 | 低（多数判定是规则） | 规则层零 token，模型层罕见 |

**Watchdog 的成本必须控制住**：它的第一级判定（`stalled()` 谓词）是纯规则、零 token。如果让它每 30 秒调一次模型，"监控"本身就成了成本大户。

### 2.5 Router 批处理：已知的免费午餐

长文的数据：待决定 Trigger 从 1 条/分钟升到 40 条/分钟时——

| 指标 | 低负载 | 高负载 |
| --- | --- | --- |
| 平均 batch | 1.0 | 2.8 |
| 单次请求耗时 | 2.5s | 3.9s |
| 单个决定分摊推理时间 | 6.4s | **1.6s** |

**积压越多，单个决定越便宜。** 所以不要为"降低延迟"去做逐条立即处理——那正好放弃了这套架构最划算的部分。

推论：**Router 的"不等待"约束（`noWait` 守卫）不只是延迟优化，也是成本优化。**

## 3. 预算硬停：防止成本拒绝服务

这是安全问题，但机制在成本侧。

一条精心构造的消息可以触发超长 assessment 烧掉大量 token。官方原型只有 eval timeout，**没有 token 预算**。

```ts
interface Budget {
  tokens: number
  wallClockMs: number
  toolCalls: number
}
```

三重任一超限立刻停。作用点：

| 对象 | 预算范围 |
| --- | --- |
| 单次 Assessment | 小（几万 token） |
| 单次 Speculation | 中（见 20 章 §3.5） |
| 单 Ticket | 大，但不无限 |
| 单日全局 | 硬上限，超了降级为 `observe` |

**"超预算降级为 observe"比"直接失败"好**：系统继续工作，只是不再主动，人仍然在环里。

## 4. 存储成本：单机真正的隐形杀手

官方原型在 `docs/007` 明说："Nothing deletes old records yet, so these grow without bound"——`trigger`、`disposition`、`decision`、结束的 Ticket 与 Thread、outbox 收据、每个 Session 用过的 prompt 版本，全部只增不减。

在 1C1G 的小 VPS 上，这会直接撑爆磁盘。**所以遗忘/归档不是"未来优化"，是部署前置条件。**

### 4.1 四层的保留策略

| 数据 | 保留 | 之后 |
| --- | --- | --- |
| Session Log（JSONL） | 30 天热 | 压缩归档，保留索引 |
| git 对象 | Ticket 结束后 90 天 | `git gc --aggressive` 后打包 |
| 只追加日志段 | 封印后 90 天 | 保留 `.summary`，正文归档 |
| 工件（artifact） | 按声明 | 大件移冷存储，保留引用 |

### 4.2 逐出必须可审计

遗忘动作本身记一条 `memory.forgotten` / `storage.evicted` 事实。**"删了什么"也要能被回答**，否则审计链断了。

### 4.3 压缩的时机

`git gc` 会抢 `.git` 的锁（见 [50-file-model.md](50-file-model.md) §5.3）。所以：

- `gc.auto 0` 关掉自动 gc
- 只在**明确的静默窗口**（无活跃 worker、无排队任务）执行
- 执行前记一条事实，执行后记一条

## 5. 本地算力：不是"用得越多越好"

单机的目标函数不是利用率，是**不让用户的机器变得不可用**（见 [20-design.md](20-design.md) 的 OOM 讨论）。

| 原则 | 含义 |
| --- | --- |
| 串行优于集体 swap | 需求总和超预算时排队，不削减每个的额度 |
| 响应性优先 | 用户开视频会议时让位 |
| 内存账本只追加 | grant 是事实，effective limit 是派生值 |
| 结构化升配 | worker 说要跑重活就申请，不靠 OOM 反推 |

## 6. 传输成本（集群才有）

| 优化 | 说明 |
| --- | --- |
| 密文压缩 | AEAD 之前压缩（注意不能压缩密文） |
| 近端 relay | 大工件不走公网 |
| 批次 | 多个小 fs 调用合并（但要小心延迟） |
| 不搬字节 | 发租约让 worker 直连（R2），根本不过 relay |

最后一条最重要：**文件调度者发租约而不是转发内容**，这个设计让大文件天然不经过控制面——单机与集群都受益。

## 7. 成本可观测性

没有度量就无法优化。要做的最小集：

| 指标 | 粒度 | 用途 |
| --- | --- | --- |
| 每 Ticket 的 token 消耗 | Ticket | 发现异常任务 |
| **缓存命中率** | 进程 | 前缀策略是否生效 |
| 每决定分摊推理时间 | Router | 批处理是否在工作 |
| 每 Ticket 的墙钟 / 工具调用数 | Ticket | 空转检测输入 |
| 磁盘占用（按数据类别） | 全局 | 归档是否及时 |
| 峰值内存（按任务类型） | 任务类型 | 下一轮 reservation 的依据 |

**"每决定分摊推理时间"这个指标值得单列**：它是判断 Router 是否健康的唯一信号。如果它上升，说明要么批处理失效，要么单条消息变重了，两者处理方式完全不同。

## 8. 三条约束性的结论

这三条会反向约束其他设计，所以单独列出来：

1. **模型调用必须在控制面**（不在设备上）。这同时给出：key 池集中、限流统一、账单可归因、缓存可复用。任何"Session 搬到端侧跑"的方案都会毁掉这四条。
2. **模型与预设创建时绑定**。这是缓存能工作的前提，也是 D3 的直接推论。
3. **预算必须硬停**。没有预算的系统在遇到恶意输入时会自我了断。
