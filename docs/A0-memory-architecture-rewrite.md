# 记忆架构重构

> **本文推翻了之前的 9L / 9N / 9O 的优先级排序。**
>
> 之前那些文档里 90% 的篇幅在讲检索，而检索是**最后一道兜底**。
> 你原话是：**「近几步全量+总结，再前面的只有总结」**——这才是主体。
>
> 本文不用 dsh 官方的 `ctx.compaction`、不用 `session-query`，全部自建。

---

## 一、先承认：之前的错在哪

| 我做的 | 你的原话 | 差距 |
|---|---|---|
| 2047 行索引 + 检索 | 「近几步全量+总结，再前面的只有总结」 | **一个字都没实现** |
| 32 份设计文档 | — | 检索占了 9O 全文，梯度记忆只有一句话 |
| 一个能搜 86,034 条的库 | — | 模型不调它 = 0 收益 |

**根本错误：我把「能搜到」当成了「不会忘」。**
而你的方案是**让忘不掉的东西根本不离开上下文**，压根不依赖搜索。

---

## 二、你的方案拆成三个动作

原话：「**近几步全量+总结，再前面的只有总结**」。逐字拆开：

```
第 1 步：近几步      → 保留【全量原文】+【总结】   （两者并存）
第 2 步：再前面的     → 只保留【总结】，原文移出上下文
第 3 步：（隐含）     → 被移出的原文去哪？→ 存起来，需要时能取回
```

**关键点：三步里前两步都不需要检索。** 检索只在第三步兜底。

| 步 | 需要什么能力 | 现有系统有吗 |
|---|---|---|
| 1 | 保留近期 + 让模型写总结 | ❌ 完全没做 |
| 2 | 把旧历史替换成总结 | ❌ 完全没做（dsh 的压缩是它自己做的、按位置切的） |
| 3 | 原文可取回 | ✅ 做了（但优先级排错了） |

---

## 三、核心难点：在哪个时机做这三步

这是整个架构的技术核心。候选时机：

| 时机 | 能改什么 | 问题 |
|---|---|---|
| `agent/pre-step` | **能增删本步进入的 messages** | 只看到本步新增，看不到完整历史 |
| `llm/stream` | 只读，不能改 | 只能观测 |
| 自己接管压缩 | 需要替换官方 compaction | 你说不用官方包 |
| **自己写 `session/message` 投影** | — | 需要 dsh 内部 API |

**结论：`agent/pre-step` 是唯一能改上下文的公开接缝。**

但它有个限制：`decision.messages` 只是**本步新增**的批次，不是完整历史。
要看完整历史并从里面"替换掉旧的"，需要另外拿到**当前的 surface 投影**。

---

## 四、架构：三层，每层职责单一

```
┌──────────────────────────────────────────────────────────┐
│  L1  保留层（近 N 轮）                                    │
│  近几次的 messages 原样保留，一个字不改                     │
│  → 这是"全量"的那一半                                     │
└──────────────────────────────────────────────────────────┘
                          ↓ 超出 N 轮的
┌──────────────────────────────────────────────────────────┐
│  L2  总结层（更早的轮次）                                  │
│  每一轮替换成该轮的 turn-summary（模型自己写）              │
│  → 这是"只有总结"的那一半                                  │
└──────────────────────────────────────────────────────────┘
                          ↓ 总结也放不下了
┌──────────────────────────────────────────────────────────┐
│  L3  归档层（原文）                                       │
│  原文留在日志里，可检索（已实现，但降级为兜底）              │
└──────────────────────────────────────────────────────────┘
```

**与之前设计的根本差别**：之前是「L3 检索为主」，现在是「L1 + L2 为主，L3 兜底」。

## 五、L1 + L2 怎么实现（不用官方包）

### 5.1 模型写总结：靠工具，不靠特殊 API

你不让用官方的机制，那模型写总结只有一个办法：**让它调用一个工具**。

```ts
// 新增工具：让模型主动结束一个"话题段"并留下总结
memory_seal({
  summary: string,        // 这段做了什么、结论、未完成的事
  reason: string,         // 为什么这段可以封存了
})
```

模型在完成一件事、切换话题、或用户说"先这样"时调用它。
**这不是自动触发**（符合你的决策④），而是模型自己的判断。

### 5.2 上下文替换：在 pre-step 里做

```
pre-step 触发
  ↓
拿到当前 session 的完整 surface（需要解决"怎么拿"）
  ↓
按轮次分组：近 N 轮 = 原文；更早的 = 已封存的 summary
  ↓
构造新的 messages 批次：summary 在前，近 N 轮原文在后
  ↓
通过 decision.messages 注入
```

**这一步的难点是"怎么拿到完整 surface"**。`decision.messages` 只有本步新增。

三条可能的路：
- **A. `ctx.sessions.get(id)` 上的 Session 实例有没有暴露 surface/deriveMessages**
- **B. 自己维护一份**：插件自己持久化每轮的 summary 和 seq 范围，构造时按 seq 从日志读
- **C. 用 `session/event` 事件流自己重建**（插件已订阅，能拿到全部事件）

**推荐 B + C 组合**：插件自己记账（哪几轮已封存、summary 是什么、对应哪个 seq 范围），
需要原文时按 seq 从日志读。不依赖 dsh 内部投影 API。

### 5.3 数据模型（最小）

```ts
/** 一个被封存的话题段 */
interface SealedSegment {
  id: string
  sessionId: string
  /** 覆盖的 seq 范围（闭区间） */
  fromSeq: number
  toSeq: number
  /** 模型写的总结 */
  summary: string
  /** 封存理由 */
  reason: string
  /** 封存时的轮次 */
  turn: number
  at: string
}
```

存 SQLite。`pre-step` 时读出来，决定哪些段该被替换成 summary。

## 六、L3 归档层（已实现，但要改两处）

现有的 `memory-plugin` 保留，但：

| 问题 | 现状 | 要改成 |
|---|---|---|
| **索引时机** | `agent/disposed`（会话结束才索引） | **每轮结束就索引**，否则当前会话搜不到自己刚说的话 |
| 定位 | 主要能力 | **兜底层**，只在 L2 也放不下时才用 |

## 八、最小可行实现（按依赖排序）

| 步 | 做什么 | 依赖 | 能否独立验证 |
|---|---|---|---|
| **1** | `memory_seal` 工具 + SealedSegment 存储 | 无 | ✅ 模型调一次能存下 |
| **2** | `pre-step` 里按 seq 范围构造替换后的 messages | 1 | ✅ 采集插件能对比 before/after |
| **3** | 自己记账"哪些轮已封存"（B 方案） | 1 | ✅ |
| **4** | 索引时机改成每轮结束 | 无 | ✅ |
| 5 | 向量检索接真模型 | 4 | 需要外部服务 |

**第 1-3 步完成后，「近几步全量+总结」就成立了。**

## 九、还必须解决的技术问题（诚实列出）

| # | 问题 | 影响 |
|---|---|---|
| 1 | **怎么拿到完整 surface 做替换** | 决定 L2 能否实现。`decision.messages` 只有本步新增 |
| 2 | 替换会不会破坏 KV cache | 会。但摘要本来就在压缩时破坏缓存，这是固有代价 |
| 3 | 模型不调 `memory_seal` 怎么办 | 同 9I 的教训：工具在场 ≠ 会被调用。需要观察真实使用率 |
| 4 | 被替换掉的消息还能不能 `read_image` / 引用 | 不能，原文只在日志里 |
| 5 | 与 dsh 自己的压缩冲突 | dsh 仍会压缩。要让 L2 在它之前生效，或者接受两者叠加 |

**第 1 条是前置阻塞项，必须先验证。**
