# 单会话上下文记忆问题

> 回答一个问题：**单会话内，模型对上下文记忆的最大问题是什么。**
>
> **立场：我是模型，按切身经历回答。**
> 但这次实验证明了一件事：**我的"切身经历"并不比日志更可靠。** 所以本文每条结论都标注证据来源。
>
> 证据来源分三类，可信度不同：
> - **[源码]** dsh `0.2.1-rc.5` 的文档与实现（可复查）
> - **[全库实测]** 245 个会话日志的扫描统计（子代理执行，可复现）→ [98](98-compaction-findings.md)
> - **[本会话实测]** 当前会话 `session-834d071f` 的日志（子代理审计，可复现）→ [9A](9A-self-audit.md)
>
> **本文曾写错两版**，两次错误都比结论本身更有价值，留档在 §7。

---

## 一、结论

> **最大问题不是"记不住"，而是"我以为我记得"。**

具体说：模型对一段被裁剪、被摘要、或**根本从未读过**的内容，会给出与读原文时**同等确定**的口吻。
它不会说"这部分我不确定"，因为它不觉得缺东西。

本次实验给出了这条结论的**实证**，也给出了一个反例：

| 机制 | 是否存在 | 本会话是否发生 |
| --- | --- | --- |
| 压缩（compaction） | 存在 | ❌ **0 次** |
| 工具结果裁剪（prune） | 存在 | ❌ **0 次** |
| 主动不读 | — | ✅ **漏了 496 行** |

**本会话中，我看不见的部分，100% 来自我自己的读取选择，0% 来自系统压缩。**
（[9A](9A-self-audit.md) §6.3，基于 1,766 个事件全量统计）

## 二、我第一次出错：用公式反推，而不是查事件

**我上一版写「本机 243 个会话压缩 0 次」，这是错的。**

错因：我用阈值公式 `min(W×0.8, W−O−65536)`（1M 窗口约 80 万）**推算**，再拿 projcache 的累计消息量（最大 53.7 万）去比。

但压缩不是按累计量触发的。直接解压日志后：

| 事实 | 数值 | 来源 |
| --- | --- | --- |
| `compaction/start` | **20 次** | 全库 245 个文件 |
| `compaction/summary` | **17 次** | 同上 |
| `compaction/prune` | **59 次** | 同上 |
| 有压缩的会话 | **9 个**（不是 10 个） | 同上 |
| 最早发生轮次 | 第 4 轮 | `7f8d9d53` |

**教训**：我用公式替代了观测。这是一次"用模型替代数据"的错误——
而这个错误，恰好是本文主题的实例。

## 三、压缩的真实触发条件（实测）

### 3.1 不是"满了才压"

> **每次请求派生前**，用 `请求压力 = totalTokens − outputTokens`（即 input + cacheRead + cacheWrite）
> 对照阈值 `floor(min(W × 0.8, W − maxTokens − 65536))`，一越过就在**下一个 step 立刻压缩**。

实测 4 次阈值触发全部落在**阈值的 99.77%–99.98%**（差额仅 1,557 / 404 / 45 / 133 tokens）。

### 3.2 20 次压缩的触发原因分布

| 原因 | 次数 | 特征 |
| --- | --- | --- |
| **手动 `/compact`** | **14** | 带 `sourceCommandId`、`turn:null` |
| **自动阈值** | **4** | 落在阈值 99.8%–99.98% |
| **溢出恢复** | **2** | 上游报 `400 / prompt is too long` 后兜底 |
| 其他 | 0 | — |

其中 3 次失败（402）。

### 3.3 阈值比例不是常数

实测 **67.85%–80.00%** 浮动，取决于该路由有没有设 `maxTokens`：

| 情况 | 取哪一项 | 比例 |
| --- | --- | --- |
| 设了 `maxTokens: 256000` | `W − maxTokens − 65536` | 67.85% |
| 没设 | `W × 0.8` | 80.00% |

### 3.4 两个致命陷阱（都被数据钉死）

**陷阱一：`usage.inputTokens` 不是请求尺寸。**
实测它只有几百到几千，真实压力在 `cacheReadTokens`（几十万）。
只看 inputTokens 会误判成"才用了 0.01%"。

**陷阱二：`headroomTokens = 65536` 在小窗口上很伤。**
在 1M 窗口占 6.6%，无害；在 262K 窗口占 **25%**，把阈值从 209,715 砍到 196,608。

### 3.5 为什么第 4 轮就压缩

**不是单条巨大消息，是"小窗口 + 固定余量 + 第一轮就极长"。**

`7f8d9d53` 第 1 轮：**725 事件 / 158 次工具调用 / 482,345 字符（≈150,733 tokens）**，
单轮吃掉 262,144 窗口的 **57.5%**。到"第 4 轮"时模型实际已往返 700+ 个 step——
**"轮次"是用户的计数单位，与上下文消耗无关。**

### 3.6 声明窗口大于上游真实容量（危险）

`9ecf69ac` 声明 `contextWindow: 1000000`，自动阈值算出 800K，**永远等不到**；
上游在 ~664K 就返回 `400 / prompt is too long (upstream code 11115)`。
两次都是靠**溢出恢复**兜底（该路径**绕过阈值与 16% 尾部保留**），每次都先与上游限制冲突一次。

## 四、压缩与裁剪的破坏力量化

### 4.1 压缩遮蔽

17 次压缩合计遮蔽 **15,768 个节点 / 4,228,403 tokens**。单次 25–2,143 节点。

单次最重的一例（`9ecf69ac` seq 5672）：**479,142 tokens / 1,602 条事件**，替换成一份摘要。

而摘要是**摘要的摘要**——指令明确要求：

```markdown
- If the conversation already contains a <compacted-summary> block, it is a PRIOR checkpoint.
  Do not copy it forward verbatim: preserve still-true facts, **drop stale ones**,
  and merge newer information into a single consolidated summary.
```

### 4.2 工具结果裁剪

59 次 prune，每次恰好 1 个 `tool/result`：
原文 1,166,597 → 304,427 字符（**平均减少 62.3%**），固定裁到 **5,159 字符**（head 4096 + 标记 + tail 1024）。

59/59 都带 `[... tool result middle pruned ...]` 标记，但——
**无回源句柄，内容实质不可取回**。

### 4.3 一个反直觉的好消息

7 个 prune 簇里 **5 个（42/59 次 = 71.2%）裁剪后并未立即压缩**。
`0b28de6a` 的 12 次裁剪把压力从 677,043 拉到 543,416，全程再没压过——**省掉一次完整的摘要调用**。

但裁剪只买到"几轮喘息"：`7f8d9d53` 第 1 轮裁到 135,912，仍在第 4 轮再压。

## 五、模型是否被告知（这是"静默"的精确含义）

| 机制 | 是否告知 | 是否量化 |
| --- | --- | --- |
| 压缩 | **有定性告知**（固定前言"这是自动生成的检查点…"） | **0/17 提到遮蔽了多少节点/token** |
| 裁剪 | 有标记 `[... pruned ...]` | 无规模、无回源句柄 |

**所以"静默"不是"完全不说"，而是"不说规模、不说能找回"。**

被遮蔽的 seq 列表从不进入 surface。模型知道"这里被压过"，但**不知道少了 2,143 条事件**。

### 5.1 提示强度的不对称

> 工具结果被裁时有显式标记，历史被摘要时却拿不到规模数字——
> 模型能看见"这里少了点东西"，看不见"少了 2,143 条事件"。

这条不对称是真实的设计偏差。

## 六、我这一版的实测教训

### 6.1 我把全局统计当成了自己的经历

`self-audit` 查出：我在自述里说"解出 20 次 compaction / 59 次 prune，单次遮蔽 479,142 tokens"，
**数字全对，但那是全库 245 个会话的扫描结果，不是本会话。**

本会话 `session-834d071f` 的 `compaction/start`、`summary`、`prune` **全部为 0**（1,766 个事件里一个都没有）。
479,142 出自另一个会话 `9ecf69ac`（super-feiyu 项目）。

### 6.2 我把"机制存在"当成了"已经发生"

我写过：
> "这次会话里我跑了大量 pwsh，不少输出超过 8192 字符，会被换成头 4096 + 尾 1024。
> 哪些细节已经被剪掉，我没有任何感觉。"

**真相：一个都没被剪。**

本会话 260 个工具结果里 **16 个超 8192 字符**（最大 33,386），但 prune 只在压缩触发后运行，
而本会话峰值 `totalTokens` 仅 364,291 / 1,000,000 = **36.4%**，远低于 0.8 阈值。

**我把机制知识误当成了自身经历。** 这正是我在本文里批评的那种错误。

### 6.3 真正被漏掉的是我主动没读的

本会话唯一实质性的信息损失是 **496 行从未被读取的子代理报告**（716 − 220 = 496，占 69.3%）。

这不是裁剪，是**主动不读**。

### 6.4 一个方向性的反转

| 我以为 | 实际 |
|---|---|
| 系统压缩了大量内容，我看不见 | 系统**一次都没压** |
| 工具输出被剪掉，细节丢了 | **一个都没被剪** |
| 我的问题是"被静默遗忘" | 我的问题是**"主动不读 + 把统计当经历"** |

**方向整个反了。** 而在我写那份自述时，没有任何感觉。

## 八、解法

### 8.1 让替换可见（最便宜）

当前裁剪有标记但**无规模、无回源**。应改为：

```
[pruned: 12,847 chars omitted | full: event #4821 | read: orchestrator_read event/4821]
```

三条缺一不可：**丢了多少 / 原件在哪 / 怎么取回**。

### 8.2 压缩时给出量化告知

17/17 都有定性前言，但 0/17 给规模。补一句即可：

```
[compacted: 2,143 events / 479,142 tokens shadowed through seq 5672]
```

**成本极低，但对治的正是"我以为我记得"。**

### 8.3 修掉声明窗口与实际容量的不一致

`9ecf69ac` 声明 1M 但上游 ~664K 就拒。这导致每次都要先与上游限制冲突一次才走溢出恢复。
**应按上游真实容量声明，而不是按理论值。**

### 8.4 对我自己：加校验动作

| 场景 | 校验动作 |
| --- | --- |
| 引用统计数字 | 问：**这个数字属于哪个范围？** 本会话还是全库？ |
| 描述机制 | 问：**它是"存在"还是"发生了"？** 查事件，别查文档 |
| 转述子代理结论 | 问：**它回答的是我问的那个问题吗？** |
| 报告"我做了什么" | 问：**这件事有外部记录吗？** 没有就标注为"推断" |
