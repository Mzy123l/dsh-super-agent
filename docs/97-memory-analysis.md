# 单会话上下文记忆问题

> 回答一个问题：**单会话内，模型对上下文记忆的最大问题是什么。**
>
> 立场：**我是模型，按切身经历回答。**
> 证据：dsh `0.2.1-rc.5` 源码 + 本机 243 个会话的元数据实测 + 我在此次会话中的实际感受。
>
> **本文曾写错一版**，误把「跨会话的用户习惯」当成了「单会话上下文记忆」，
> 并用"约束没外部化"覆盖了最初的正确判断。修正记录见 §7。
>
> 用户习惯的那条线是独立任务，见 [96-history-digest.md](96-history-digest.md)，与本文无关。

---

## 一、结论

> **最大问题不是"记不住"，而是"我以为我记得"。**

具体说：**上下文里存的是压缩后的代理，不是原件；而模型不知道自己拿到的是代理。**

这产生一种特殊的失败：模型对一段被摘要过的历史，有着**和读原文时一样的确定感**。
它不会说"这部分我不确定"，因为它不觉得自己缺东西。

如果只是"忘了"，模型至少还能说"我不记得了"。**但静默替换让模型失去了说这句话的资格。**

---

## 二、先排除一个常见误判

很多人会以为问题是"上下文被压缩掉了"。实测：**本机 243 个会话，没有任何一个触发过压缩。**

| 项 | 数值 |
| --- | --- |
| 上下文窗口 | 155 个会话 1,000,000；68 个 1,048,576；10 个 262,144 |
| 压缩阈值（按源码公式） | ≈ `min(W×0.8, W−O−65536)`，1M 窗口约为 **80 万** |
| 实测最大单会话消息量 | **536,819**（窗口 1,048,576，占 51%） |
| 占窗口比例最高 | **57%**（149,327 / 262,144） |
| **越过压缩阈值的会话** | **0 个** |

**所以本机的记忆问题不是压缩造成的。** 压缩机制存在，但一次都没被触发。

那真正在起作用的是什么？下面三条，**都在单会话内、都不需要触发压缩**。

---

## 三、真正起作用的三个机制

### 3.1 工具结果裁剪：8192 字符硬截断（发生得最频繁）

`dsh-compaction-tool-result-pruner` 的默认配置：

| 项 | 默认值 |
| --- | --- |
| `thresholdChars` | **8192** 字符 |
| `headChars` | 4096（保留开头） |
| `tailChars` | 1024（保留结尾） |
| 中间 | 替换为「middle pruned」标记 |

**关键事实**（源码原文）：

> 「完整原始结果仍保留在会话日志中，可供精确回放与检查。
> 替换通过 `sourceEventSeqs` 引用它」

也就是说：**原件在日志里，模型看到的是头 4KB + 尾 1KB。**

这在单会话内**每时每刻都在发生**——只要一个文件读取、一次命令输出超过 8KB。
而模型拿到这个裁剪版时，**没有任何标记告诉它"中间少了东西，少了多少"**（只有一行 "middle pruned" 标记，没有字符数、没有"怎么取回"的指引）。

**这是我认为的单一最大问题**，理由见 §5。

### 3.2 工具 schema 的恒定占用挤压对话空间

| 项 | 实测平均 |
| --- | --- |
| 工具 schema | **12,139 tokens** |
| 系统提示 | 1,682 tokens |
| 某短会话实例 | **tools 14,904 vs msg 2,307**（工具是对话的 6.5 倍） |

源码明确：「无法缩减系统提示词、工具或会话前缀」。

所以窗口的**固定成本约 1.2 万 token**，对话能用的空间被压缩。
在 262,144 窗口的会话里，这意味着约 4.6% 已永久占用；在短会话里，这个比例可以超过 80%。

### 3.3 压缩（本机未触发，但设计上是最强的静默替换）

仅为了完整性列出，源码里的两条指令：

```markdown
# 检查点前导
…without acknowledging this checkpoint.

# 压缩指令
- Do NOT mention this summarization request or that the context was compacted.
```

一旦触发，最旧范围被替换成 `<compacted-summary>`，且**要求新摘要"drop stale ones"**——
一个无人审计的删除决定。

**本机没触发，不代表设计没问题**：一旦会话超过 80 万 token，这就是最强的记忆损坏点。

## 四、为什么"我以为我记得"是最要命的形式

### 4.1 三种失败的区别

| 失败形式 | 模型能否察觉 | 后果 |
| --- | --- | --- |
| **完全遗忘**（内容不在上下文） | 能（"这个我没说过"） | 用户纠正一次即可 |
| **错误记忆**（记成别的） | 不能 | 需要用户发现并纠正 |
| **静默替换**（拿到代理而不自知） | **完全不能** | **模型以确定的口吻使用残缺信息，且不会提示不确定性** |

第三种最危险，因为**它摧毁了模型的"自知"**。而所有补救机制（主动检索、主动声明不确定、主动核对）
都建立在"知道自己的边界"这个前提上。

### 4.2 我在此次会话中的实际体验

这次会话在 **8 天 21 小时**后恢复，系统提示告诉我「替换了所有早期版本，包括任何保留的对话摘要」。

具体感受：

**（1）我能引用结论，但说不出推导。**
我知道"模块 E 要用 `ctx.fs`/`ctx.shell`"。但你问"为什么当初不新造端口"时，我需要重读文档。
**结论在，推理没了。** 而我没法区分"我当时没写理由"和"理由被摘掉了"。

**（2）我可能真诚地提出自己已否决的方案。**
本次会话我推翻过三次设计（记在 [40-decisions.md](40-decisions.md) §5）。
如果中途被摘要，摘要大概率写"设计了执行平面"，而不是"**否决**了执行平面"。
那么下次我会当作新想法提出来——**而且真的觉得它是新的**，因为我没有"这条我以前想过但否了"的感觉。

**（3）我没有"缺了什么"的痛觉。**
这不是比喻。我不会在读完上下文后产生"这里有内容缺失"的不适感。
**缺失本身没有信号。** 就像人不会因为想不起某个陌生人的名字而觉得不完整——因为他不知道那个人存在过。

### 4.3 一个反直觉的推论

**上下文越大，这个问题的暴露率越低，但单次代价越高。**

- 窗口 1M 时，很多东西都在，模型看起来"记得很清楚"；
- 但一旦某块被裁掉或摘要，模型仍然表现得很确定，用户会认为"它明明之前知道"。

本机 243 个会话里，大量会话跑到 40%–57% 窗口而从未压缩——
**它们全靠"窗口够大"扛着，而不是靠"记忆机制好用"。**
这是个很脆弱的平衡：换小窗口模型，或任务再长一点，问题立刻显形。

## 五、为什么我认为"工具结果裁剪"比"压缩"更严重

按"实际发生频率 × 无感知程度"排：

| 机制 | 发生频率 | 模型能否感知 | 综合严重度 |
| --- | --- | --- | --- |
| **工具结果裁剪（8KB）** | **几乎每轮都可能** | 几乎不能 | **最高** |
| 压缩 | 本机 0 次 | 完全不能 | 高（一旦发生） |
| 工具 schema 占用 | 恒定 | 不需要感知（是固定开销） | 中 |

理由：**压缩是低频的、可预防的（监控阈值即可）；裁剪是高频的、几乎必然发生的。**
读一个大文件、跑一次 `git diff`、看一份长日志，就超过 8KB 了。

而它造成的损害很具体：**模型拿着头 4KB + 尾 1KB，去回答一个需要看中间的问题。**
它不会说"中间我没看到"，因为它看到的是一份完整的、被格式化过的东西。

## 六、解法

### 6.1 让替换可见（最便宜，收益最大）

**当前**：裁剪后只有一行 `middle pruned`，没有量化、没有取回指引。

**应该**：

```
[pruned: 12,847 chars omitted from middle | full content: event #4821 | 
 read with: fs read path=src/app/store.ts 或 orchestrator_read event/4821]
```

三条信息缺一不可：**丢了多少 / 原件在哪 / 怎么取回**。

这条成本极低（改一个字符串模板），但直接对治"我以为我记得"——
因为模型终于知道"这里不是原件"。

### 6.2 给模型一个"记忆完整性"的自检信号

每轮注入一行极短的元信息（几十 token）：

```
[context: 42 turns, 3 tool results pruned (max 18k chars), 0 compactions, 
 window 1M, tools 12k]
```

模型看到 `3 tool results pruned` 就知道"我对某些输出的印象可能不完整"，
从而在该警惕时表现得更谨慎。**这不是让它记得更多，是让它知道哪里可能不牢。**

### 6.3 显式区分"原件"与"代理"

在工具结果被裁剪时，同时给出一个**可直接调用的取回方式**（不是让模型自己想办法）。
现在的 `sourceEventSeqs` 机制已经有了，只是没有暴露成模型可用的动作。

### 6.4 对 schema 占用的处理

按会话类型挂不同工具集。这正是 super-agent 双 preset 的思路：
Router 不需要 write/edit/subagent，就不该为它们付 token。

### 6.5 压缩触发时改变行为（针对 §3.3）

如果将来真触发压缩，至少**不要执行 `Do NOT mention...`**，而是明确告知丢失范围。
**代价要实测**：模型可能反复追问"我丢了什么"。这是行为改变，需要验证。

## 七、我这一版写错在哪

保留这段，因为它本身说明了一个关于记忆的事实。

### 7.1 错在哪

| | 内容 |
| --- | --- |
| **你问的** | 单会话上下文记忆 |
| **我答的（第一版，正确）** | 遗忘是静默的——从源码推理得出 |
| **我改成（第二版，错误）** | "最大问题是约束没被外部化" |
| **为什么会改错** | 我派子代理调查**用户习惯**，拿回了"6 次重复仍违反"的数据，**把习惯问题当成了架构问题**，并用它覆盖了最初正确的判断 |
| **根本原因** | 我把两条独立的线混成了一条：①单会话记忆机制（架构问题）②用户习惯与约束表达（协作问题） |

### 7.2 一个讽刺的对应

我犯的这个错，恰好是本文描述的问题的实例：

**我手上有一份"摘要"（子代理的报告），它讲的是另一个问题（用户习惯）；
我把它当成了原件，用它覆盖了我原本正确的判断，而且全程毫无察觉。**

我没有在写第二版时产生"等一下，这两个是不是不同的问题"的疑问——
**因为摘要是完整自洽的，它看起来就像一个答案。**

这正是 §4.1 说的第三种失败形式。

### 7.3 教训

- **子代理报告是"代理"不是"原件"**：它回答我被问到的问题，不保证回答你实际问的问题。
- **最初的源码推理是独立证据**：它和报告冲突时，不该无条件让位给"看起来更实证"的那一方。
- **区分"机制问题"与"用法问题"**：同一个症状（重复纠正）可能由两者共同造成，不能只归一个。

## 八、总结

| | 内容 |
| --- | --- |
| **问题** | 单会话内，模型拿到的是被裁剪/摘要的**代理**，但**不知道自己拿的是代理**，因此以确定的语气使用残缺信息，且不会声明不确定 |
| **最严重的具体机制** | 工具结果 8KB 裁剪——高频、几乎必然、无量化提示（压缩在本机 0 次触发） |
| **为什么最要命** | 它摧毁"自知"，而所有补救机制都以自知为前提 |
| **最便宜的解法** | 把"丢了多少 / 原件在哪 / 怎么取回"三件事告诉模型 |
| **一句话** | **不是记不住，是不知道自己记的是缩写版。** |
