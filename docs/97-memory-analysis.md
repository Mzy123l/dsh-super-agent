# 记忆问题的分析与解法（最终版）

> 这份文档回答一个问题：**当前 dsh 与缓存架构的最大记忆问题是什么，怎么解。**
>
> 三类证据：
> ① dsh `0.2.1-rc.5` 源码与文档（压缩、检索、注入机制）
> ② 本机 243 个会话**全量实测**（见 [96-history-digest.md](96-history-digest.md)，下称"历史报告"）
> ③ 我作为模型在此次会话中的切身经历（8 天 21 小时后恢复，中间上下文已被替换）
>
> **本文的结论经过一次修正。** 最初的判断是"遗忘是静默的"，基于源码推理；
> 读完真实数据后，这个判断**只对了一半**——真实的主导问题不是"模型忘了"，而是**"约束从未被外部化"**。
> 修正过程见 §4，这是本文最有价值的部分。

---

## 一、结论

### 1.1 一句话

> **最大问题不是"记不住"，而是"该记住的东西从来没有被写到模型之外的地方"。**

压缩只是**暴露**了这个缺陷，不是**造成**它。

### 1.2 三个层次

| 层 | 问题 | 严重度 | 能否只靠记忆解决 |
| --- | --- | --- | --- |
| **L-A 约束外部化缺失** | 用户说过的硬约束（"禁止开思考""丢弃第一次结果"）只活在该轮对话里 | **最高** | **不能**，必须外部化 |
| **L-B 目标/让步不区分** | 需求里混着"目标"与"可接受的让步"，模型当成了目标 | 高 | 部分，靠强制复述 |
| **L-C 遗忘静默** | 压缩后模型不知道自己丢了什么 | 中（是本问题的放大器，非主因） | 部分，靠系统告知 |

**修正的核心**：原以为 L-C 是主因，实测发现 L-A 才是。`fb985b49` 会话里
"禁止给子代理开思考"被**重复 6 次**仍被违反——**这发生在同一个会话、没有跨压缩的情况下**。
它不是"忘了"，是**约束从未离开过某一条消息**，模型每次从头开始都要重新"记得"。

## 三、机制层面为什么会放大

### 3.1 源码明确要求不要告诉模型"你被压缩了"

```markdown
# 检查点前导
…without acknowledging this checkpoint.

# 压缩指令
- Do NOT mention this summarization request or that the context was compacted.
```

**这是设计，不是疏忽。** 目的是让模型自然接着干。代价是模型永远不知道自己的记忆有缺口。

### 3.2 四个放大器

| # | 机制 | 源码原文 | 后果 |
| --- | --- | --- | --- |
| 1 | 替换而非追加 | 「它是替换，而非仅追加」 | 旧检查点从模型视野消失 |
| 2 | 摘要的摘要 | 「preserve still-true facts, **drop stale ones**」 | 逐次衰减；"drop stale" 是无人审计的删除 |
| 3 | 前缀不可缩减 | 「无法缩减系统提示词、工具或会话前缀」 | 恒定开销挤压历史 |
| 4 | 只保近期尾部 | `retainRatio: 0.16` | 95%+ 被抽象化 |

### 3.3 工具 schema 是被忽视的恒定开销

实测：工具 schema 平均 **12,139 tokens**，系统提示仅 1,682。
某个短会话（`你好，你是谁`）：**tools 14,904 vs msg 2,307**——工具比对话大 6 倍。

按源码，「无法缩减系统提示词、工具或会话前缀」，这部分**永不压缩**。
为做一件小事，先付 1.2 万 token 的"入场费"。

**建议**：按会话类型挂不同工具集（这正是 super-agent 双 preset 的思路）。

**好消息**：dsh 把原始摘要保留在 `compaction/summary` 事件上——**数据没丢，只是模型看不见**。
这使"只追加、可回溯"的实现成本很低。

## 四、我的判断错在哪（修正记录）

保留这一段，因为它是这份分析里最有信息量的部分。

### 4.1 我原来的推理链

```
压缩是替换 → 旧检查点消失 → 被否决的方案会被重新提出
→ 所以关键是"让遗忘可见" + "决策结构化"
```

这个推理**在源码层面完全成立**，但它是**从机制倒推行为**，没有验证。

### 4.2 实测推翻的部分

| 我的假设 | 实测结果 | 判定 |
| --- | --- | --- |
| 主要问题是"跨压缩遗忘" | `fb985b49` 的 6 次违反**发生在同一会话内**，与压缩无关 | ❌ **假设错了** |
| 否决项会重新提出 | 确有（`120809f4`「不要再给我提这个自托管载体了」） | ✅ 成立，但频率不高 |
| 检索救不了它 | 成立，且当前 `web` profile 连 `session-search` 都没挂 | ✅ 成立 |
| 决策外部化是关键 | **成立，而且比我预想的更根本** | ✅ 但范围更大 |

### 4.3 修正后的因果

```
真实因果：
  用户把硬约束写在某条消息里
      ↓
  模型在那一轮响应了它
      ↓
  但约束从未离开那条消息，没有变成"可检视的载体"
      ↓
  下一轮（甚至同一轮的后半段）就要重新"记得"
      ↓
  压缩只是让这件事更严重——因为连那条消息本身都消失了
```

**所以：压缩不是病因，是并发症。** 真正的病是**约束没有外部化**。

## 五、解法

### 5.1 第一优先：把约束外部化（零代码，立刻可做）

历史报告 §6 已给出可直接粘贴的规则。核心不是"记性更好"，是**把约束落到上下文之外的载体上**——
用户反复说「**记录下来**」的真实含义就是这个。

分五组（完整版见 [96-history-digest.md](96-history-digest.md) §6）：

| 组 | 关键条目 | 对治 |
| --- | --- | --- |
| **需求理解** | 含指示代词时必须先复述成具体对象；看到"不是 A，是 B"先回头核对 | ① 没听懂意图 |
| **动手边界** | 排查任务默认只读；全局配置一律不写；"只读"没有例外 | ② 越界 |
| **不要猜** | 可测量的问题必须跑命令/读源码；结论要指到证据 | ② 猜测 |
| **交付形态** | 先判断交给谁看再定格式；交付严格等于清单 | ② 加戏 |
| **返工规则** | "还是不行"时禁止在同一假设上微调；2 次失败就推翻重来 | ③ 假修复 |

### 5.2 第二优先：强制复述（对治目标/让步混淆）

用户其实已经给出了解法原型：「**你给我复述一遍来**」「**完整重读一遍历史**」。

规则化：需求里出现**弹性词**（可以/允许/至少/尽量/最好）或**判据词**（就是/才/即）时，
先输出四段再动手：

```
目标 = …
约束 = …
可接受让步 = …     ← 这类词最容易把"让步"误读成"目标"
验收判据 = …
```

### 5.3 第三优先：决策层结构化（对治跨压缩衰减）

```ts
interface DecisionRecord {
  readonly id: string
  readonly kind: 'decided' | 'rejected'   // 否决与决定同等重要
  readonly subject: string
  readonly rationale: string
  readonly supersedes?: string            // 取代而非覆盖
  readonly derivedFrom: { sessionId: string; fromSeq: number; toSeq: number }
  readonly owner: 'human' | 'agent'       // human 的不可被自动 supersede
}
```

注入成短行（几十 token，每轮重注入，压缩碰不到）：

```
[x2] 否决: 新造 ExecutionPlane 端口 — 理由: dsh 已有 ctx.fs/ctx.shell seam
[d3] 不许运行时更新状态 — 理由: 前缀稳定/行为可预测
```

### 5.4 第四优先：让遗忘可观测

压缩时告知模型丢失的 seq 范围。**需要推翻 dsh 那句"不要承认检查点"**——
改动小，但会改变模型行为（可能引发反复追问），需实测副作用。

### 5.5 四层模型（按「是否会被静默删除」分层）

| 层 | 存什么 | 存活保证 |
| --- | --- | --- |
| L0 不变量层 | 硬约束（禁止/必须/一律） | **永久重注入，永不压缩** |
| L1 决策层 | 决定 + **否决** + 理由 | **只追加，带 id** |
| L2 事实层 | 项目知识、约定 | 可衰减，带证据 |
| L3 轨迹层 | 过程细节 | **可丢弃** |

**为什么按这个维度分**：一条 90 天前的决策可能比 3 分钟前的闲聊更重要。按时间远近分层回答不了"哪条不能丢"。

## 六、验收标准

| # | 标准 | 测法 | 目标 |
| --- | --- | --- | --- |
| 1 | 硬约束被违反的次数 | 统计"禁止/必须"类指令的重复下达率 | **0**（当前最高 6 次） |
| 2 | 连续压缩 5 次后 L0/L1 一条不少 | 对比压缩前后注入内容 | 100% |
| 3 | 被否决方案不重提 | 构造回放 | 0 次 |
| 4 | L1 注入成本 | 测量 | < 前缀 5% |
| 5 | 用户纠正率 | 纠正语句 / 总输入 | 下降（当前基线见历史报告） |

**第 1 条是真正的核心指标**——它直接测"约束有没有被外部化"。

## 七、⚠️ 附带发现：AGENTS.md 里有明文凭据

`~/.dsh/AGENTS.md` 末尾「结束」一节包含一个**明文 SMTP 授权码**和两个邮箱地址。

这个文件**每轮注入模型上下文**，意味着：

- 每轮模型都能看到它
- 它被写进 Session Log（本机 223,513 条记录里可能有）
- 若 `dsh_session_log` 上传开关开启，还会随请求上传

**建议立即改为环境变量**（如 `SMTP_PASS`），AGENTS.md 只写"用环境变量 `SMTP_PASS`"。
这符合你自己写的安全习惯："敏感信息必须通过环境变量或 .env 注入"。

## 九、一句话

> **这套架构能给文件加 git，能给副作用加 WAL，却没有给"约束"加一个永不被压缩的位置。**
>
> 而真正的发现是：**压缩只是让这件事显形**。
> 即使完全不压缩，一条说过一次的约束，下一轮也未必还在——
> 因为它从来没有离开过那条消息。
>
> 解法不是"记得更多"，是**让该忘不掉的有一个载体，让该守住的有一个清单**。
