# 其他方面

> 你让我"也多想一想其他方面"。这里收拢对话中没被问过、但会决定项目成败的六件事：
> 防糊弄的落地、配置分层、可观测性、升级兼容、测试策略、以及一个反向问题——**这套东西什么时候该被砍掉**。

## 1. 防糊弄：从"更仔细审阅"改成"可判定谓词"

### 1.1 为什么不能靠审阅

官方原型的克制是：Router **不许看实现细节**（`dispatch.md` 明写 "Do not independently investigate the remaining problems"）。所以把控不可能靠 Router 逐条审查 Worker 的代码。

而 Report 六态、ready 都是**自述**。"着急"会让模型跳过验证然后报 ready——这不是恶意，是训练出来的效率倾向。

### 1.2 三个独立证据源

关键是把"完成"变成可判定的谓词，而不是更仔细地读它的话：

| 证据源 | 能回答 | 谁提供 |
| --- | --- | --- |
| **git 对象** | 到底改了哪些文件、什么内容（含未提交） | 私有目录仓库 |
| **文件调度者的 apply 账** | 有没有真的发布产物 | 只追加日志 |
| **Session 轨迹** | 声称跑过的测试是否真跑过 | dsh Session Log |

三者交叉，模型撒的谎要通过三次查询。

```ts
/** report(ready) 必须带证据，host 反查。 */
interface ReadyReport {
  summary: string
  evidence: {
    testCommandId: string  // 反查：该 id 是否真实存在于本 Session 轨迹
    diffSha: string        // 反查：git 里是否存在该 diff
    artifactIds: string[]  // 反查：日志里是否有对应 apply
  }
}
```

### 1.3 Ticket 结束时必须落库的三样

```
git status --porcelain   ← 未提交的修改也算「改动」
git diff
git stash list           ← 别把用户的东西留在 stash 里而无人知晓
```

**未提交的修改必须被记录**，因为下一个人接手时它们就在那儿。

### 1.4 越权检测

`git diff --name-only` vs `Mandate.scope`。不一致就是越权，追加一条事实。

> **待你定**：ready 的证据要求要多严？越严越防糊弄，也越容易让正常任务卡在"证据不全"上。我倾向**代码类任务强制，文档类任务宽松**。

## 2. 配置分层：Few settings 的具体落实

官方的立场很硬：

> **Few settings.** 一个默认值能适合几乎所有团队时，就不该做成 setting。团队用文字描述的**行为**是提示词，不是 setting。

理由是三条乘起来的负担：每个 setting = 一次认知负担 + 一个测试维度 + 一个升级兼容成本。

### 2.1 四层

| 层 | 内容 | 形式 | 能不能配 |
| --- | --- | --- | --- |
| **代码强制** | 权限、Gate、Mandate、工具集差异、隔离 | 代码 | **不给配**（配错就是事故） |
| **提示词** | 语气、何时说话、什么算完成、评审习惯 | 自然语言 | 自由改，需版本与 diff |
| **枚举** | accept mode、并发数、预算、日志保留 | 三档/数字 | 少量 |
| **技能包** | 团队知识（谁是谁、仓库约定） | 按需加载的文件 | 可加 |

**提示词这一层是习惯的主要载体。** 用自然语言而不是表单，是因为"什么时候该说话"这种事无法枚举成选项。

### 2.2 一个值得抄的细节：override 记基线

官方原型做了：**override 记录它是基于哪一版默认文本**。默认变了就标 "Default updated" 并显示新旧对比，让用户选保留还是跟新。

没有这个机制，升级一次就会覆盖或错乱用户的自定义。**这是"可升级的定制"与"不可升级的定制"的分水岭。**

### 2.3 从行为推断偏好，而不是让用户填表

"根据习惯定制"的正确形式是**记录并建议**：

| 观察 | 推断 | 动作 |
| --- | --- | --- |
| 用户连续三次把某类报告缩短 | 不想要详细报告 | 建议改提示词 |
| 用户总是手动 stop 某类主动任务 | 那条 rule 太宽 | 建议收窄 |
| 用户连续三次对同类任务点闪电 | 这类该默认分层 | 提示一次「以后默认并行？」 |

**只提示，不静默改默认。** 静默改默认是另一类"糊弄"——用户不知道自己被系统改了行为。

## 3. 可观测性

没有度量就无法优化，也无法证明"这系统在工作"。

### 3.1 面板的三个问题

官方面板的设计标准值得直接抄——打开面板按顺序回答：

1. **现在有什么需要我？**
2. **系统健康吗、在做对的事吗？**
3. **某件工作的历史是什么**（Trigger → Eval → Ticket）？

配合"安静是默认"：健康状态不占空间；问题必须可行动；一次性网络错误不足以上报。

### 3.2 必须有的指标

| 指标 | 为什么 |
| --- | --- |
| 待人工决定数 | 这是唯一真正的 KPI（每个决定换来多少 Agent 工作量） |
| 每 Ticket 的 token / 墙钟 / 工具调用 | 发现异常任务与空转 |
| **缓存命中率** | 唯一能验证前缀策略是否生效 |
| **每决定分摊推理时间** | 判断 Router 是否健康的唯一信号 |
| 磁盘占用（按数据类别） | 判断归档是否及时 |
| 峰值内存（按任务类型） | 下一轮 reservation 的依据 |

### 3.3 健康条目的纪律

官方原型：**连续失败三次才报错**，避免偶发故障刷屏。每个部件一个健康条目，**每个条目只有一个写者**（`HealthBoard` 拒绝第二次认领）。

`delivery` 是例外——它的失败显示在自己的 Ticket 上，不占健康条目。这个例外很合理：**有些失败应该贴着它影响的对象显示，而不是变成全局告警。**

### 3.4 一个容易被忽略的指标：打扰率

"每个 Ticket 平均打扰人的次数"。目标 ≤ 1。

这个指标重要是因为**它直接对应产品的核心承诺**（尽可能少占用人的注意力）。如果它上升，说明系统在退化，即使任务都完成了。

## 4. 升级与兼容

dsh 仍是 `rc`，官方明说会有破坏兼容的变更。这是最现实的风险。

### 4.1 三层隔离

| 层 | 策略 |
| --- | --- |
| 依赖版本 | **锁定**具体版本（`0.2.1-rc.5`），不用 `^` |
| 接缝 | 只用 `ctx.*` 公开接缝，不 import 内部模块 |
| 自己的抽象 | `src/core` 不 import 外部（官方已经这样，继续守） |

### 4.2 必须写的哨兵测试

**每次升级前跑，作为回归的哨兵：**

| 测试 | 验证什么 |
| --- | --- |
| `ctx.fs` / `ctx.shell` 抽象基类的形状 | 签名有没有变 |
| `isolate` 的 realm 语义 | 同进程两种后端还能不能分开 |
| 预设机制 | 能否仍为不同角色配置不同工具集 |
| `agent/*` 事件 | `steer` / `inject` 语义有没有变 |
| Session 格式版本 | 旧日志还能不能读 |

**第一条和第二条最关键**：它们是整个执行平面设计的地基。

### 4.3 数据格式的迁移

官方原型的做法值得抄：**`SCHEMA_VERSION` 只增不减**；数据库版本更新则拒绝启动；迁移在启动时一次完成；迁移本身有测试（`migration.spec.ts` 覆盖"每条存储记录都转成当前形状"）。

对这个项目，额外要加：**只追加日志的段格式版本**。段一旦封印就不能改，所以格式版本必须在段头里。

## 5. 测试策略

官方原型有 59 个 spec 文件、约 1.44 万行测试代码，覆盖方式值得借鉴。

### 5.1 五类测试

| 类 | 覆盖 | 为什么必须 |
| --- | --- | --- |
| **领域测试** | 纯内存仓储上跑 Engine 规则 | 规则最多变，必须最快反馈 |
| **契约测试** | 两种 Wire（本地/远程）跑同一套用例 | 这是"单机=集群"的证明 |
| **并发测试** | 事件在 pass 期间到达、Ticket 在投递期间变化 | 这类 bug 只在特定时序出现 |
| **崩溃测试** | 在每个可能的中断点注入失败 | 恢复逻辑只能这样验证 |
| **模型面测试** | 工具 schema、提示词、技能、预算 | 防止"改了 prompt 但忘了测试" |

### 5.2 崩溃注入：这是本项目的核心测试

因为整个设计依赖"先存后做"，**必须在每个中断点注入失败**。

```
[1] 写日志前崩溃 → 无影响
[2] 写完日志、未 apply → 重放
[3] apply 中崩溃 → pre/post 判定
[4] apply 后、标记前崩溃 → post 匹配则标记完成
[5] 外部路径 apply 中崩溃 → 必须交人
```

官方原型有一个测试专门验证"effect 队列的合并、上限、退避、健康与关闭"，思路一样。

### 5.3 误报回放集（Watchdog 专用）

Watchdog 最难做对，因为要先回答"什么叫有进展"。没有回放集，阈值调参就是盲调。

需要一组标注过的历史轨迹：正常长任务 / 真空转 / 方向偏离。**精确率 ≥ 0.8、召回率 ≥ 0.6 才算达标**；不达标就继续只观察。

### 5.4 文档即测试

官方原型有两个测试值得抄：

| 测试 | 做什么 |
| --- | --- |
| `docs.spec.ts` | 编号文档只链接更早的文档、每个本地链接能解析、没有合并冲突标记、架构文档的表格列全了每个模块和每个测试 |
| `class-docs.spec.ts` | `src` 里每个类前面都有 JSDoc |

第一个尤其聪明：**它让"文档陈旧"变成构建失败**。

## 6. 什么时候该砍掉这套东西

官方长文的判断标准只有一条：

> **是否存在人在不同渠道之间搬运上下文的工作。**

客服、工单、单次报告生成这类请求响应型场景，一个会话一件事就够。**上双层架构是给自行车装货车底盘。**

### 6.1 不值得用的信号

| 信号 | 说明 |
| --- | --- |
| 任务都是"问一句答一句" | 没有跨渠道连续性需求 |
| 没有环境事件源 | 不需要主动，只是被动执行 |
| 同时只有 1 个未完成任务 | 分层净亏（多一条前缀） |
| 人的判断比 Agent 快 | 自动化只是增加一层 |

### 6.2 值得用的信号

| 信号 | 说明 |
| --- | --- |
| 消息来自 ≥3 个渠道 | 人在搬运上下文的成本明显 |
| 多任务并行且互不阻塞 | 串行会明显拖慢 |
| 有 CI / PR / 工单这类环境事件 | 主动性有价值 |
| 任务跨天、跨周 | 上下文保持有价值 |

### 6.3 一个反过来的自我约束

这条设计**必须**写进文档，否则项目会为了"做得更完整"而无限膨胀：

> 本文档里的六个增强模块（执行平面、凭据代理、任务级 Watchdog、投机执行、记忆分层、多仓库），
> **每一个都应该按"是否存在人在搬运上下文"这条标准裁剪，而不是全做。**

新增一个机制的门槛应该是：**它能减少一个人的一个决定，或者防止一次会到人面前的事故。** 否则就是给自行车装货车底盘。
