## 0. 总纲

**每个独立单位一个线性编号（#N）。**

三层信息保真，逐级下推，每级都从**原文**生成（绝不链式摘要）：

| 层 | 内容 | 何时 | 生成方式 |
| --- | --- | --- | --- |
| **L0** | 完整原文 | 永远在库里 | 原始记录 |
| **L1** | summary（提炼） | 长单位产生后串行 | 模型，从 L0 生成 |
| **L2** | 折叠摘要 | 任务完成 / 超窗预算 | 模型，从 **L0** 生成（不是从 L1） |

**发送视图的两级展示**：近程 L1+L0 全发；远程只发 L1。
**折叠**：任务边界处，一段连续单位收成一条 `#x~#y [折叠摘要]`，可按需展开。

**旁路模块**（§6/§7）不占编号序列，是独立台账。

## 1. 编号单位

### 1.1 单位划分（每个独立单元都标号）

| 单位 | kind | 来源 | summary |
| --- | --- | --- | --- |
| 用户消息 | `user` | user 消息 | 无（永不衰减） |
| 模型思考 | `thinking` | assistant 的 reasoning 块 | 长必有；短可选 |
| 工具调用+结果 | `tool` | assistant 的 tool-call 块 + 对应 tool 消息 | 同上 |
| 模型正文 | `reply` | assistant 的 text 块 | 同上 |
| system / developer | — | 框架内容 | 不占编号、不索引 |

- **一次工具调用和它的结果属于一个单位**。内部标签：
  `<tool-call name="bash">参数</tool-call>` + `<tool-result isError="false">输出</tool-result>`。
  关联键：tool-call 块 `id` ↔ tool 消息 `toolCallId`。
- 同一条 assistant 消息的思考、各工具调用、正文**拆成多个单位，各占一号**。
- 空块不产生单位。

### 1.2 编号规则

- 会话内**完全线性**：0, 1, 2, 3 … 连续无空洞，不复用、不跳号。
- `#0` = 该会话第一个 user prompt；system 不占号。
- **不使用 (sessionId, seq, kind) 三元组**。一条单位一个编号，编号即身份。
- 编号永不改变：总结后不变、老化后不变、**折叠后不变**、仍可检索。
- **不使用 token 作为衡量单位**（用户明确要求）；唯一的例外是 §5.4 的折叠预算兜底。
- 各会话独立一套。

### 1.3 一次性产物（不占编号）

两类消息**完全不占编号**：

1. **提炼指令**（`source.kind = 'memory-summary-prompt'`）
2. **提炼回复**（收割后登记文本指纹，下轮同步时识别）

理由：它们是一次性产物，若占编号会按"user 永不衰减"永久留存。

## 2. 总结机制（串行、即时、与窗口无关）

### 2.1 触发：长必须，短可选

- **长单位（content ≥ 4000 字符）：必须总结。** 产生后紧接着注入提炼指令。
- **短单位：可选。** 由模型在提炼流程里自行判断（回复 `none` 表示不值得提炼）。
- 阈值 4000 为程序初值，可调（`MEMORY_SUMMARY_THRESHOLD`）。

### 2.2 时序（串行，即时）

```
模型产出单位
  → 下一步 pre-step：注入提炼指令（user 消息，引用 #N，整条英文）
  → 模型回复提炼结果
  → 程序收下：summary 挂到单位
  → 撤掉指令与回复的发送视图（日志保留）
  → 工作继续
```

- **没有事后总结、没有轮末批量、没有老化时补写**。
- 模型**不写 `<summary>` 标签**。标签是程序组装发送文本时加的。
- 这一步**就是总结本身**：注入指令 → 模型回复 → 挂接，串行插入对话流。

### 2.3 总结完成后发生什么

**什么都不发生。** 发送视图不变：summary 与 content 并存，全量照发。
总结为两件事服务：
1. 单位老化后只剩 `#N + summary` 时仍有信息可用；
2. `memory_search` 能返回要点 + 全量原文。

### 2.4 提炼指令（整条英文，实现见 `src/projection/render.ts`）

必须包含的要点：

- 这是**提炼，不是压缩**：保留否决路径与否决理由，再给最终结论
  （`rejected option: X — because Y` / `chosen option: Z`）
- **summary 是后续取回这段内容的唯一途径**，务必认真填写，否则会永久丢失
- 保留具体事实（路径、数值、错误信息、名字）；重复试错去重
- 长度约为原文 10%–20%
- 简短无价值内容回 `none`
- 只输出提炼结果

### 2.5 防漂移铁律

**L2 折叠摘要必须从 L0 原文生成，绝不能从 L1 summary 再摘要。**
依据：递归摘要会系统性语义衰减（[Synaptic Drift](https://zenodo.org/records/20810208)），
且 agent 读自己写的摘要时信任度等同原话，错误会被继承。

## 3. 发送投影（两级展示）

### 3.1 近程（窗口内）：L1 + L0 全发

```
#0 帮我xxx                                        ← user：纯文本全发

#1 <summary>思考总结</summary>                     ← thinking（有 summary）
<content>思考内容</content>

#2 <summary>调用工具、编辑文件的总结</summary>       ← tool（有 summary）
<tool-call name="bash">{"command":"ls"}</tool-call>
<tool-result isError="false">输出…</tool-result>

#3 正文，回复用户结果                               ← reply：纯文本
```

### 3.2 远程（窗口外）：只发 L1

```
#1 <summary>思考总结</summary>
#2 <summary>调用工具、编辑文件的总结</summary>
#4 原文（短单位无 summary，原样保留——地位与 summary 等同）
```

- 有 summary 的单位剥掉 content。
- **未总结的单位老化后原样保留**（内容短，保留即最优展示）。
- user 单位永不衰减（唯一例外是提炼指令，它不占编号）。

### 3.3 窗口

- **按单位数量**：`最新 idx − 该单位 idx < 32` 算近程。
- 默认 **32 个单位**（≈5~7 轮），`MEMORY_WINDOW` 可调。
- 文献区间 3–6 轮，32 单位落在其换算后的重叠区（工具对 3 ≈ 8 单位；6 轮 ≈ 24–42 单位）。

### 3.4 投影是纯函数

发送文本 = `f(单位集合, 窗口, 折叠状态)`。不调模型、不生成文本、不改库。

## 4. 检索

### 4.1 工具

`memory_search`：关键词 → 返回单位**全量**（`#N`、kind、summary、完整 content、便签）。
全量历史，含已老化、已折叠、已压缩的单位。

### 4.2 通道

- FTS5 + 中文逐字分词。
- **thinking 的 content 只进向量不进 FTS**（避免搜索命中过多）；thinking 的 summary 进 FTS。
- 向量：SqliteVectorStore（余弦暴力扫描）+ HashingEmbedding 兜底；RRF k=60。

## 5. 折叠压缩（L2）

### 5.1 这是什么

**按任务边界**把一段连续单位收成一条**可展开的摘要**，而不是按时间/条数硬切。

有正式研究对应：[Context-Folding (ICML 2026)](https://proceedings.mlr.press/v306/sun26x.html)。
agent 分叉出子轨迹处理子任务，完成后折叠，收起中间步骤只留结果摘要。

### 5.2 触发（四种，用户已明确）

| 触发 | 条件 | 谁发起 |
| --- | --- | --- |
| **任务边界（主动）** | 模型完成模块 a、开始模块 b 时声明折叠 | 模型 |
| **多任务拆分** | 一开始被要求做 2 个模块，完成第一个后折叠 | 模型 |
| **预算兜底（被动）** | 投影后总 token 超过上下文窗口的一定比例 | 程序 |
| **手动 `/compact`** | 用户显式输入 `/compact` 命令 | **用户** |

- 前两种是**模型主动**（唯一允许模型自动触发的地方，因为这是它的任务判断）。
- 第三种是**程序自动**兜底（必须自动，否则超窗就崩）。
- **第四种是用户手动**：用户输入 `/compact` 即立刻折叠。

### 5.2.1 手动 `/compact` 命令

用户在任何时刻输入 `/compact`，立即触发一次折叠压缩：

```
/compact               折叠最近一段未折叠的历史
/compact #4~#9         折叠指定区间
/compact --dry-run     只预览会被折叠成什么，不落库
```

规则：

- **优先级最高**：跳过模型主动判断，直接执行。
- 折叠范围默认：**最近一段「未折叠的连续单位」**（从当前窗口边界往回取）。
- 折叠摘要仍由模型从 **L0 原文**生成（§2.5 铁律不因手动触发而放宽）。
- 用户可连续 `/compact` 多次，逐段折叠。
- `/compact` 本身**不占编号**（它是一条命令，不是对话内容）。
- 折叠完成后返回给用户一行确认：`已折叠 #4~#9：[摘要首行]…（可 memory_expand #4~#9 展开）`

**为什么需要手动触发**：模型判断不准任务边界时会漏折叠或过早折叠；
预算是滞后的（超了才动）；用户知道自己已经切换了话题——所以必须留一个
用户直接控制的开关。这也与 dsh 的 `/compact` 惯例一致。

### 5.3 折叠体形态

```
#4~#9 已完成模块 a：[折叠摘要]
```

- 占据区间**第一个编号**（`#4`），区间内其余编号（`#5`–`#9`）在发送视图中消失
  （库中保留，仍可检索、仍可展开）。
- **编号不变**——`#4` 仍是 `#4`，身份连续性不破。
- 折叠体本身是一等公民：占一个发送位置，模型能看到它、能展开它。

### 5.4 两级取回（严格按用户要求）

**必须先 L1，再 L0。不能一步跳到原文。**

```
memory_expand(#4~#9)   → 返回这些单位的 L1（各自的 summary）
memory_expand(#7)      → 返回 #7 的 L0（完整原文）
```

- 第一级：展开折叠体 → 拿到区间内各单位的 summary（L1）。
- 第二级：定位到具体单位 → 拿到该单位原文（L0）。
- 每级都要经过一次工具调用。**不允许 `memory_expand(#4~#9, full)` 一步到位。**

理由（用户设计意图）：两级取回强制模型先看概览、再决定深入哪里，
避免一次性把几十条原文拉回上下文——那等于取消了折叠。

### 5.5 折叠摘要的生成

- **输入给模型的是 L0 原文**，不是 L1 summary（§2.5 防漂移铁律）。
- 由正在运行的模型生成，串行触发（折叠动作本身就是一次注入指令）。
- 质量要求同 §2.4：保留否决路径、保留事实细节、去重试错。
- 额外要求：**说明这个模块完成了什么、留下了什么、有没有遗留问题**。

### 5.6 与 dsh 自带压缩的关系

**dsh 自带压缩不挂载。** 上下文大小完全由本模块的投影 + 折叠控制。

### 5.7 增长特性

- 折叠后上下文**阶梯式下降**（一次折叠掉一整段）。
- 无第三级（不对折叠摘要再折叠）——用户架构就是两级（L0/L1）+ 折叠。
- 超长会话的最终兜底是检索。

### 5.8 缓存代价（诚实记录）

- 折叠发生时刻，该位置之后的 KV cache 失效一次。
- 但折叠是**稀疏事件**（按任务边界，不是每轮），远比逐轮切窗便宜。
- 实测（9 系列）：压缩类失效只占未命中输入的 3.8%，可接受。

## 6. 旁路模块·待办（Todo）

### 6.1 解决什么问题

**用户只记得"有待办"，不知道到底还剩下什么。**

真实场景：长会话里用户说过"记成待办，回头处理"，几小时后回来只记得有个事没做，
但想不起来是什么、做到哪了。模型如果只靠检索，需要用户给关键词——而用户恰恰没有关键词。

### 6.2 设计

**独立台账，不占编号序列。** 表结构：

```sql
todo(
  todo_no    INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId  TEXT NOT NULL,
  title      TEXT NOT NULL,        -- 一句话：做什么
  detail     TEXT NOT NULL,        -- 为什么、约束、验收标准
  status     TEXT NOT NULL,        -- open | done | dropped
  from_idx   INTEGER,              -- 来源单位编号（可回溯原文）
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
)
```

### 6.3 录入（谁来写）

- **模型主动登记**：用户说"记成待办"、或明确提到"回头再做"时，模型调
  `memory_todo` 登记。
- **不许程序规则识别**：不做关键词匹配自动登记（9I 的教训：规则不可靠，
  且规则产出的待办质量差）。

### 6.4 查询（核心价值）

`memory_todo` 工具支持：

| 操作 | 返回 |
| --- | --- |
| `list` | **所有 open 待办**（标题 + 详情 + 来源编号） |
| `list --all` | 含 done / dropped（带状态） |
| `done <no>` | 标记完成 |
| `drop <no>` | 放弃（带原因） |

**关键：`list` 不需要关键词**——用户说"我还有什么事没做"时，
模型直接 `memory_todo list` 拿到全部 open 项。这正是"用户不知道剩下什么"的解法。

### 6.5 与其他模块的关系

- 待办项带 `from_idx`，可跳转到来源单位（先看 L1，再按需 L0）。
- **待办不参与折叠**：折叠掉的历史里如果有 open 待办，待办本身仍在台账里可见。
  这保证折叠不会"藏起"未完成的事。
- 待办不占编号、不进 FTS（它是结构化台账，不是对话内容）。

## 7. 旁路模块·覆写（Override）

### 7.1 解决什么问题

**用户后来推翻自己先前的判断，或承认模型的结论才是对的。**

真实场景：

- 用户先说"用方案 A"，做完发现不行，改口"其实方案 B 才对"
- 用户先否定模型的建议，后来发现模型是对的
- 用户纠正自己先说错的事实（"我刚才说错了，不是 300 是 600"）

如果只是普通追加，上下文里会**同时存在两个互相矛盾的"事实"**，
模型无法判断哪个是当前的。检索也会同时返回两条。

### 7.2 设计

**覆写表 + 原文保留。** 表结构：

```sql
override_log(
  override_no  INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId    TEXT NOT NULL,
  target_idx   INTEGER NOT NULL,   -- 被覆写的单位编号
  old_summary  TEXT NOT NULL,      -- 覆写前的 summary
  new_summary  TEXT NOT NULL,      -- 覆写后的 summary
  reason       TEXT NOT NULL,      -- 为什么推翻
  by_user      INTEGER NOT NULL,   -- 1 = 用户推翻自己；0 = 用户承认模型对
  created_at   TEXT NOT NULL
)
```

### 7.3 机制

**覆写改的是 summary（L1），不动 content（L0）。**

```
原状：  #7 <summary>方案 A 最优</summary> <content>…论证 A…</content>
覆写后：#7 <summary>[已覆写] 方案 B 才对（原判断 A 有误）</summary>
        <content>…论证 A…</content>   ← 原文不动，保留推翻痕迹
```

- **L0 原文永不改**——这是审计与防漂移的基础。
- 发送视图中 `#7` 的 summary 换成新版本，并标注 `[已覆写]`。
- `override_log` 记录完整历史：被覆写前的 summary、原因、是谁推翻的。
- 检索时同时返回新 summary 与覆写记录，模型知道"这条被推翻过"。

### 7.4 触发

- **模型主动调** `memory_override`：当用户明确表达"我之前说错了 / 其实应该是 X /
  你是对的"时。
- 需要 `target_idx`（被覆写的单位）+ `new_summary` + `reason`。
- **不做自动检测**——语义判断交给模型，规则检测不可靠。

### 7.5 为什么不做"删除旧内容"

删除会破坏：
1. **审计链**（无法回放"用户曾经这么认为"）
2. **防漂移**（原文是唯一锚点）
3. **检索完整性**（旧内容可能是有效的历史事实，只是不再是当前结论）

所以覆写 = **叠加新解释 + 保留旧记录**，不是替换。

## 8. 规划模块（Plan）

### 8.1 三个概念必须分清

| 概念 | 回答什么 | 形态 | 生命周期 |
| --- | --- | --- | --- |
| **goal** | 什么算成功 | 验收条件 | 会话级，很少变 |
| **规划** | **怎么干**：架构、顺序、依赖 | 步骤 + 架构决策 + 版本 | **可覆写、可重建、可削弱** |
| **待办** | 现在**不做**、留到以后 | 挂起项 | 挂起 → 恢复/放弃 |

关键区别：**规划步骤是"当前正在做的事"；待办是"主动推迟的事"。**
两者不共用存储（此前设计稿曾提议复用 todo 表，已作废）。

### 8.2 模型的通病与本文的对策

**通病**：模型倾向于"快速干完活"而不做完整规划——先动手，边做边想。
文献侧面印证：ReAct 式逐步反应的成功率随任务长度**平方衰减**，
而 plan-then-execute 只**线性衰减**；在 0.9 单次可靠性目标下，
后者的可行任务长度是前者的**近 5 倍**
（[Planner's Dividend, 2026](https://huggingface.co/datasets/thaki-AI/daily-paper-2026-09-26-planning-vs-reactive-cost-frontier/commit/59a2496143f2e7a7b997d113359ca1512421e2f0)）。

**但对策不是"逼模型先规划"，而是"先问它要多久"。**

### 8.3 准入：只问时间，不问要不要规划

**程序在任务开始时只问一个问题：**

```
你估计完成这个任务需要多长时间？（分钟）
```

**不问"是否需要规划"**——问那句话等于把架构决策交给模型的自我评估，
而模型在被问"要不要规划"时会倾向说"不用"（省事）。

**不问"大概几步"**——步数对模型没有意义（它无法从步数推断工作量）；
时间有直觉锚点，**模型更可能在时间上诚实，而不是在步数上**
（用户判断）。

**文献对自评的警示与本文的应对**：
[Do LLMs Know What They Are Capable Of? (ICLR 2026)](https://arxiv.org/html/2512.24661)
实测所有模型在"事前预测能否完成"上**系统性过度自信**，且不随模型变强而改善。
但同一研究指出：**判别力优于随机，且模型风险厌恶**。

因此本设计：

- **过度自信是模型缺陷，不是架构问题**（用户判断）——所以不为它设计复杂的补偿机制
- 但**阈值取不对称**：把"该规划"的门槛压低，让边界地带的判断偏向规划。
  代价不对称——漏规划的代价远大于多规划一次。

**时间阈值（默认值，可调）**：

| 自估时间 | 处理 |
| --- | --- |
| < 5 分钟 | 直接干，不规划 |
| ≥ 5 分钟 | **建规划** |

5 分钟是保守取值：宁可多规划，不可漏规划。

### 8.4 规划是一个独立、版本化的对象

**一个会话一个当前计划**，不是每个子任务一个。计划**带版本**演进。

```sql
-- 当前快照：每会话一行，读取快
plan(
  sessionId    TEXT PRIMARY KEY,
  version      INTEGER NOT NULL,       -- 当前版本号，只增不减
  name         TEXT NOT NULL,          -- 当前版本名（强制命名，见 8.4.1）
  goal         TEXT NOT NULL,          -- 什么算成功
  estimate_min INTEGER,                -- 模型自估时间（分钟）
  steps        TEXT NOT NULL,          -- JSON：步骤数组（见 8.5）
  decisions    TEXT NOT NULL DEFAULT '[]', -- JSON：架构决策数组（见 8.6）
  status       TEXT NOT NULL,          -- active | done | abandoned
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
)

-- 版本历史：每次变更加一行，永不删、永不覆盖
plan_version(
  plan_no      INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId    TEXT NOT NULL,
  version      INTEGER NOT NULL,
  name         TEXT NOT NULL,          -- 版本名（强制，见 8.4.1）
  snapshot     TEXT NOT NULL,          -- 该版完整 JSON（goal + steps + decisions）
  change_kind  TEXT NOT NULL,          -- init | extend | revise | rebuild | revert | step-update
  reason       TEXT NOT NULL,          -- 为什么变
  created_at   TEXT NOT NULL,
  UNIQUE(sessionId, version)
)
```

**为什么拆成两张表**：

- 读取快：当前计划只有一行，pre-step 注入时不必扫描历史
- 审计全：每次变更都留完整快照，可回放计划演进
- 与既有原则一致：`override_log` 保留旧 summary、L0 永不删——**一切变更都是追加，不是覆盖**

#### 8.4.1 版本名强制必填

**每个版本都必须有名字**，像 git commit 一样——名字是给人看的一句话，
说明"这一版为什么变成这样"。

规则：

| 项 | 规则 |
| --- | --- |
| 格式 | 自由文本，**1–60 字符**，不允许纯空白 |
| 语义 | 描述**本次变更**做了什么，不是重复 goal |
| 强制 | `memory_plan` 任何写操作（create/update/replan/revert/step）都**必须带 name**，缺失则拒绝执行 |
| 唯一 | 版本内不要求唯一，但同一 `version` 号必定对应唯一一行 |

**好的命名**（说明变更）：

```
"初始计划：先读鉴权代码再改 TTL"
"追加模块b：用户要求加导出功能"
"b-1 卡住：改用流式读取"
"回滚到 v2：v3 的流式方案引入新问题"
```

**不好的命名**（无信息量，应被拒绝）：

```
"更新"   "修改"   "v3"   "调整计划"
```

理由：版本名是**审计的第一入口**。`memory_plan history` 输出时，
用户和模型首先看到的就是这一列；名字含糊等于没有审计。

#### 8.4.2 旧版本的使用

不只是留档，还要能用：

| 操作 | 效果 |
| --- | --- |
| `memory_plan history` | 列出所有版本：`v1 「初始计划…」→ v2 「追加模块b…」…` |
| `memory_plan show --version N` | 查看某一版完整内容（goal/steps/decisions） |
| `memory_plan revert --to N --name "…"` | 回滚：**产生新版本**（内容等于 vN），旧版本全部保留 |

**回滚是追加，不是删除**：`revert --to 2` 在 v3 之后产生 v4，
v4 的 `change_kind = 'revert'`、`reason` 里写"回滚到 v2"。
版本号**永远只增不减、永不复用**。

**旧版本不进发送上下文**——只注入当前版。历史按需用工具查。

### 8.5 步骤的形态

```json
{
  "id": "a-1",
  "text": "读现有鉴权代码，确认 token 刷新路径",
  "status": "done",          // pending | in_progress | done | blocked | dropped
  "weight": 1.0,             // 在当前计划中的权重（见 8.7）
  "note": "确认了 ttl=300"
}
```

### 8.6 架构决策随计划走

**"我们决定用 X 方案、因为 Y"这类元决策存在 plan.decisions 里，不挂到单位上**
（用户选定方案 A）。

```json
{
  "id": "d-1",
  "decision": "token 刷新改为提前 5 分钟",
  "reason": "现网 300 秒 TTL 不足以覆盖重试窗口",
  "status": "active",         // active | superseded
  "superseded_by": null
}
```

架构决策被推翻时，标 `superseded` 并指向新决策——**不删除**（与 §7 覆写同一条原则）。

### 8.7 追加任务：削弱前面的规划，增强后面的

用户中途追加模块 b 时（用户明确要求：**追加应该削弱前面的规划，增强后面的规划**）：

```
执行前（v1）：a-1(w=1.0) a-2(w=1.0) a-3(w=1.0)
追加模块 b（v2）：
  a-1(w=0.3) a-2(w=0.3) a-3(w=0.3)   ← 权重削弱（除非未完成）
  b-1(w=1.0) b-2(w=1.0) b-3(w=1.0)   ← 新任务权重拉满
```

- **已完成的 a 步骤**：权重归零、折叠时机提前（它们可以尽快被折叠压缩）
- **未完成的 a 步骤**：权重降级但不为零（仍可能影响 b）
- **新增的 b 步骤**：权重 1.0

**权重的作用**：决定发送视图里"哪些步骤的细节保留得更久"、
以及折叠压缩时**优先折叠低权重区间**。它不是装饰性字段。

### 8.8 覆写与重建

**三种变更，都必须带状态（不推倒重来）**：

| 场景 | 操作 | 已完成的步骤 |
| --- | --- | --- |
| 用户追加模块 b | **扩展**：保留全部，追加新步骤，前面的权重削弱 | 保留，标记 done |
| 模型在某步卡住 | **局部修订**：只改那一步（拆细/换路线），其余不动 | 保留 |
| 整个方向错了 | **重建**：新版本，旧步骤标 dropped 并给原因 | 保留记录（审计） |

**铁律：任何变更都是 version+1，已完成步骤绝不作废。**
从零重规划会让已完成工作全部作废、token 爆炸
（[重规划必须带状态](https://bbs.huaweicloud.com/blogs/488108)）。

**没有重规划次数上限**（用户明确：3 次毫无理由，规划是必要的）。
但每次变更必须写 `version` 与变更原因，便于事后审计。

### 8.9 卡点处理

模型在某一步卡住时的处理顺序：

1. **先改写该步骤**（拆成更小的步骤，或换实现路线）
2. 若改步骤仍不行，**标记 blocked** 并在 `decisions` 里记录「为什么这条路走不通」
3. 若 blocked 步骤是后续步骤的前提，**局部重建后续步骤**
4. 全程不由程序判定"卡住了"——**由模型判断并主动调用**

### 8.10 规划不占编号

- 规划是元层面对象，**不占 #N 编号**、不进 FTS、不参与发送投影的单位序列。
- 但规划**会出现在发送视图中**——作为一段独立注入的上下文（类似系统提示），
  让模型随时知道"当前计划是什么、做到哪了"。
- 规划注入的形态待实现时定（倾向于每次 pre-step 注入当前计划的紧凑视图）。

## 9. 存储

```sql
message(
  row_id INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId TEXT NOT NULL,
  idx INTEGER NOT NULL,                  -- 会话内线性编号
  kind TEXT NOT NULL,                    -- user | thinking | tool | reply
  summary TEXT NOT NULL DEFAULT '',      -- L1（可被覆写）
  content TEXT NOT NULL,                 -- L0，永不删、永不改
  at TEXT NOT NULL,
  in_context INTEGER NOT NULL DEFAULT 1,
  tags TEXT NOT NULL DEFAULT '[]',
  folded_into INTEGER,                   -- 若已折叠，指向折叠体编号
  UNIQUE(sessionId, idx)
)
message_fts     -- summary + content（thinking 的 content 除外）
message_vector  -- 向量
fold(           -- 折叠体
  fold_no INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId TEXT NOT NULL,
  from_idx INTEGER NOT NULL,
  to_idx INTEGER NOT NULL,
  fold_summary TEXT NOT NULL,           -- L2
  created_at TEXT NOT NULL
)
todo(...)        -- §6.2
override_log(...)-- §7.2
plan(...)        -- §8.4 当前快照（每会话一行）
plan_version(...)-- §8.4 版本历史（每次变更一行，含强制 name 与完整 snapshot）
pending_summary  -- 待总结状态
summary_reply_fp -- 提炼回复指纹
meta
```

**数据源**：唯一来源是 `llm/stream` 拿到的实际发送消息。
**同步**：请求路径上同步（已有单位复用编号，新单位分配 MAX+1）。
**无自动索引**（定时/轮末批量建索引被禁止）。

## 10. 工具与命令清单

### 10.1 模型工具

| 工具 | 作用 |
| --- | --- |
| `memory_search` | 关键词检索，返回单位全量（含折叠/压缩的） |
| `memory_expand` | 展开折叠体：一级返回 L1，二级返回 L0 |
| `memory_todo` | 待办台账：list / done / drop |
| `memory_override` | 覆写某单位的 summary（保留原文与覆写记录） |
| `memory_plan` | 规划：create / update / step / blocked / replan / history / show / revert（**任何写操作必须带版本名**） |

**没有**总结类工具（总结由注入指令驱动，不是工具）。

### 10.2 用户命令

| 命令 | 作用 |
| --- | --- |
| `/compact` | 立即折叠最近一段未折叠的历史 |
| `/compact #x~#y` | 折叠指定区间 |
| `/compact --dry-run` | 只预览折叠结果，不落库 |

`/compact` 是**用户直接控制折叠的开关**，优先级高于模型判断与预算兜底。
它不占编号、不进入对话历史（作为命令处理，不是 user 单位）。

## 11. 端到端流程

```
用户发言
  → pre-step：同步入库（编号分配）
  → 模型产出：思考 + 工具调用 + 正文
  → pre-step：长单位无 summary → 注入提炼指令（引用 #N）【总结】
  → 模型回复提炼结果 → 挂接 summary → 撤掉指令与回复
  → 发送视图不变（L1 + L0 并存）

模块 a 完成，开始模块 b
  → 模型声明折叠（或程序按预算兜底触发）
  → 注入折叠指令（输入区间 L0 原文）
  → 模型回复折叠摘要
  → 写 fold 表，区间内单位标 folded_into
  → 发送视图：#4~#9 已完成模块 a：[折叠摘要]【折叠】

任意时刻
  → memory_expand(#4~#9) → L1 列表
  → memory_expand(#7)    → #7 的 L0 原文
  → memory_search("xxx") → 单位全量
  → memory_todo list     → 还剩什么没做
  → memory_override(#7, "方案 B 才对", "用户改口") → 覆写 summary
  → /compact             → 用户手动触发折叠（最高优先级）
```

## 12. 验收标准

1. 近程上下文形如 §3.1；各单位按最优格式，`#N` 开头。
2. 单位老化后只发 `#N` + summary；未总结单位原样保留。
3. user 消息永不衰减；提炼指令与回复不占编号、不出现在发送视图。
4. 总结完成后发送视图不变（L1 与 L0 并存）。
5. 折叠后发送视图是 `#x~#y [折叠摘要]`，编号不变，区间内单位不可见但可展开。
6. **`memory_expand` 严格两级**：一次调用只给一级结果。
7. 折叠摘要从 L0 生成，不是从 L1 再摘要。
8. 待办：用户说"我还剩什么"时，`memory_todo list` 无需关键词即可回答。
9. 待办不因折叠而消失（台账独立于发送视图）。
10. 覆写：L0 原文不变，summary 更新并标 `[已覆写]`，override_log 有完整记录。
11. **`/compact` 能手动触发折叠**：立即生效，返回折叠区间与摘要首行；`--dry-run` 不落库。
12. 编号多轮稳定、会话内连续无空洞、从 0 开始。
13. 工具调用与结果同一编号，内部标签区分。
14. 思考、正文、每个工具调用各占一号；system 不占号。
15. 模型输出从不出现 `<summary>` 标签。
16. dsh 自带压缩未挂载；无自动索引触发器。
17. **规划准入只问时间**：程序只问"预计多少分钟"，不问是否需要规划、不问步数。
18. 自估 ≥ 5 分钟即建规划；< 5 分钟直接执行。
19. **规划独立、版本化**：一个会话一个当前计划，每次变更 version+1。
20. **追加任务削弱前、增强后**：已完成步骤权重归零，新步骤权重 1.0。
21. **任何规划变更都不作废已完成步骤**；重建时旧步骤标 dropped 并保留原因。
22. **每个版本强制命名**：1–60 字符自由文本，描述本次变更；缺失则写操作被拒绝。
23. **版本历史永不覆盖**：每次变更加一行 `plan_version`（含完整 snapshot），可回放。
24. **回滚是追加**：`revert --to N` 产生新版本，旧版本全部保留；版本号只增不减、永不复用。
25. 架构决策存在 `plan.decisions`，被推翻时标 `superseded` 而非删除。
26. 规划不占 #N 编号，但以紧凑视图注入发送上下文；旧版本只在工具查询时出现。
27. 全部行为有测试覆盖，并在真实 dsh（WSL）验证加载与真实对话。

## 13. 作废清单（防回流）

| 作废项 | 原因 |
| --- | --- |
| pending_inject / awaiting / harvest 状态机（v3 以前） | 总结串行即时，无跨轮状态 |
| memory_summarize / memory_spans 工具 | 总结由注入指令驱动 |
| segment 表 / recent-slot / summary-slot 双槽 | summary 挂在 message.summary 列 |
| surfaceOp 遮蔽旧历史再注入合并体 | 改为发送投影纯函数 |
| 「总结=衰减」混同（v2） | 总结与压缩/折叠是不同机制 |
| 老化时提炼 | 总结串行即时 |
| 用 token 衡量窗口 | 用户明确禁止；token 仅用于折叠预算兜底 |
| 规则/小模型摘要 | 正在运行的模型生成 |
| dsh-compaction-basic | 压缩由本模块负责 |
| 轮末/定时自动索引 | 索引只在请求路径同步 |
| 从 L1 生成 L2 | 防漂移铁律：必须从 L0 |
| 覆写时删除旧内容 | 破坏审计链与防漂移锚点 |
| 规划复用 todo 表 | 规划是元层面、有版本；待办是挂起项，生命周期不同 |
| 规划挂到某单位 summary 上 | 版本演进无处安放；架构决策不属于任何单位 |
| 问模型"是否需要规划" | 等于把架构决策交给模型自我评估，它倾向说"不用" |
| 用步数做规划准入 | 步数对模型无意义，无法从步数推断工作量 |
| 重规划次数上限 3 次 | 用户明确否决：规划是必要的，次数不设限 |
| 旧版本被覆盖/删除 | 版本历史永久保留，回滚产生新版本而非删除 |
| 版本可匿名 | 版本名强制必填，缺失拒绝写操作 |

| --- | --- |
| L0 | 单位完整原文，入库永不删、永不改 |
| L1 | 单位的 summary（模型串行提炼，可被覆写） |
| L2 | 折叠摘要（模型从 L0 生成） |
| 单位 | 一个 #N：user / thinking / tool(调用+结果) / reply |
| 折叠 | 把连续单位收成一条 `#x~#y [摘要]`，按任务边界触发 |
| 展开 | `memory_expand` 两级取回：先 L1，再 L0 |
| 旁路模块 | 不占编号序列的独立台账：待办、覆写、规划 |
| 覆写 | 用新 summary 替换旧 summary，L0 原文不动 |
| **goal** | 什么算成功（验收条件），会话级、很少变 |
| **规划** | 怎么干：步骤 + 架构决策 + 版本；可覆写、可重建、可削弱 |
| **待办** | 现在不做、留到以后的挂起项 |
| 计划权重 | 步骤在发送/折叠中的重要性，追加任务时前削后增 |
| 带状态重规划 | 变更时保留已完成步骤，version+1，绝不从零开始 |
| 版本名 | 每版强制的 1–60 字符描述，说明本次变更做了什么（类似 commit message） |
| plan_version | 版本历史表，每次变更一行完整快照，永不覆盖 |
