## 0. 总纲（只有总结，没有压缩）

**每个独立单位一个线性编号（#N）。**

- **近几条**：`#N` 下 summary 与 content 并存，全发。
- **更远的**：只发 `#N` + summary。
- **这是发送投影的两级展示，跟压缩没有任何关系。** content 从发送视图消失
  不叫压缩——库里的原文一个字不丢，检索随时返回全量。

**总结的产生**：串行。长单位产生后，程序紧接着注入一段 user 提炼指令，
模型回复提炼结果，程序挂接并把指令与回复从发送视图撤掉。
**长单位必须总结；短单位可选**（由模型在提炼时自行判断要不要给短单位也写一句）。

**压缩：本文不涉及。** 后续单独设计，且压缩必须有模型参与。

---

## 1. 编号单位

### 1.1 单位划分（每个独立单元都标号）

| 单位 | kind | 来源 | summary |
| --- | --- | --- | --- |
| 用户消息 | `user` | user 消息 | 无 |
| 模型思考 | `thinking` | assistant 消息的 reasoning 块 | 长单位必有；短单位可选 |
| 工具调用+结果 | `tool` | assistant 的 tool-call 块 + 对应 tool 消息 | 同上 |
| 模型正文 | `reply` | assistant 消息的 text 块 | 同上 |
| system / developer | — | 框架内容 | 不占编号、不索引 |

- **一次工具调用和它的结果属于一个单位**。内部标签区分：
  `<tool-call name="bash">参数</tool-call>` + `<tool-result isError="false">输出</tool-result>`。
  关联键：tool-call 块 `id` ↔ tool 消息 `toolCallId`。
  没等到结果的调用独立成单位（只有 tool-call 标签），不丢。
- 同一条 assistant 消息的思考、各工具调用、正文**拆成多个单位，各占一号**。
- 空块不产生单位。

### 1.2 编号规则

- 会话内**完全线性**：0, 1, 2, 3 … 连续无空洞，不复用、不跳号。
- `#0` = 该会话第一个 user prompt；system 不占号。
- **不使用 (sessionId, seq, kind) 三元组**。一条单位一个编号，编号即身份。
- 编号永不改变，被撤掉发送视图的单位编号不变，仍可检索。
- 各会话独立一套。

## 2. 总结机制（本文唯一主题）

### 2.1 触发：长必须，短可选

- **长单位（content ≥ 4000 字符）：必须总结。** 产生后紧接着注入提炼指令。
- **短单位：可选。** 是否总结由模型在提炼流程里自行判断
  （见 §2.4 指令模板——模型可以选择"该单位不值得提炼"）。
- 阈值 4000 字符为程序初值，可调。

### 2.2 时序（串行，即时）

```
模型产出单位
  → 下一步 pre-step：注入提炼指令（user 消息，引用 #N）
  → 模型回复提炼结果
  → 程序收下：summary 挂到单位
  → 撤掉指令与回复的发送视图（日志保留）
  → 工作继续
```

- **没有事后总结、没有轮末批量、没有老化时补写**。
- 模型**不写 `<summary>` 标签**。标签是程序组装发送文本时加的。
- 这一步**就是总结本身**（Q1 定论）：注入指令 → 模型回复 → 挂接，
  串行插入对话流，没有"专职/混排"之分——那一步的全部产出就是总结。

### 2.3 总结完成后发生什么

**什么都不发生。** 发送视图不变：summary 与 content 并存，全量照发。
总结不为省空间服务，它为两件事服务：

1. 单位老化后（窗口外）只剩 `#N + summary` 仍有信息可用；
2. `memory_search` 能返回提炼过的要点 + 全量原文。

### 2.4 提炼指令模板

```
你需要提炼出 #N 那一段的有效信息，丢弃噪音。
注意不是压缩，而是提炼出有效信息。期望的形态：
  否决方案：xxx 因为：xxx
  ...
  最终方案：xxx
如果该段内容简短、没有值得提炼的东西，直接回复"无"。
只输出 #N 的提炼结果。
```

- 指令**只出现一次**：完成后指令与回复都从发送视图撤掉
  （用户原话：「不回传，只出现一次，不要上下文中全是这一条信息」）。
- 质量要求：保留否决路径（不是只留最终结论）、保留事实细节、试错去重、
  长度为原文 10%–20%。
- 短单位的"可选"由「直接回复无」实现：模型判断不值得提炼时给"无"，
  程序挂空 summary（该单位老化后只剩 `#N`，信息靠检索兜底）。

## 3. 发送投影（两级展示，不是压缩）

### 3.1 近几条（窗口内）：summary + content 全发

```
#0 帮我xxx                                        ← user：纯文本全发

#1 <summary>思考总结</summary>                     ← thinking（有 summary）
<content>思考内容</content>

#2 <summary>调用工具、编辑文件的总结</summary>       ← tool（有 summary）
<tool-call name="bash">{"command":"ls"}</tool-call>
<tool-result isError="false">输出…</tool-result>

#3 正文，回复用户结果                               ← reply：纯文本

#4 （短单位无 summary，直接正文）
```

### 3.2 更远的（窗口外）：只发 summary

```
#1 <summary>思考总结</summary>
#2 <summary>调用工具、编辑文件的总结</summary>
#4 原文（短单位无 summary，原样保留——地位与 summary 等同）
#0 帮我xxx                                        ← user：仍全发
```

- **未总结的单位老化后原样保留**（Q2 定论：地位等同于 summary）——
  它们内容短，保留即是最优展示。
- 有 summary 的单位老化后剥掉 content。
- `#N` 永远第一行开头；编号永不改变。

### 3.3 投影是纯函数

发送文本 = `f(单位集合, 窗口)`。不调模型、不生成文本。
窗口 W 默认 **20 个单位**（只按数量，完全不用 token），环境变量可调。

## 4. 存储与同步

### 4.1 表结构（已按此重写 schema.sql）

```sql
message(
  row_id INTEGER PRIMARY KEY AUTOINCREMENT,
  sessionId TEXT NOT NULL,
  idx INTEGER NOT NULL,             -- 会话内线性编号，0 = 第一个 user prompt
  kind TEXT NOT NULL,               -- user | thinking | tool | reply
  summary TEXT NOT NULL DEFAULT '', -- 模型提炼结果；空 = 未总结
  content TEXT NOT NULL,            -- 完整原文，永不删
  at TEXT NOT NULL,
  in_context INTEGER NOT NULL DEFAULT 1,
  tags TEXT NOT NULL DEFAULT '[]',
  UNIQUE(sessionId, idx)
)
message_fts  -- summary + content 拼接（thinking 的 content 只进向量）
message_vector
meta
```

### 4.2 数据源与同步

- 唯一数据源：`llm/stream` 拿到的本次实际发送消息。
- 请求路径上同步：已有单位复用编号，新单位分配 `MAX(idx)+1`，
  消失的编号标记已离开上下文（编号保留，可检索）。
- **无自动索引**（定时/轮末批量建索引被禁止；请求路径同步是编号机制的伴生行为）。

### 4.3 发送载体

模型可见历史的变更通道是 dsh 的 surface 投影（`session.append` + `surfaceOp`）。
硬约束（已实测）：`{op:'replace', startSeq, endSeq}` 恰好 3 键；
`sourceEventSeqs` 完整列出被遮蔽节点、去重升序。
每单位独立 replace。撤掉提炼指令/回复的载体首日实测定。

## 5. 检索

### 5.1 工具

只保留 **`memory_search`**：命中返回单位**全量**——`#N`、kind、summary、
**完整 content**（不截断）、便签、是否在窗口内。模型拿到 `#N` 可直接引用。

### 5.2 范围与通道

- **全量搜索**：不管单位是否老化（既定决策）。
- 默认当前会话，可选跨会话。
- FTS 收录：summary + 非思考单位 content；**thinking 的 content 只进向量**
  （既定决策：思考别索引，只向量化，避免命中过多；thinking 的 summary 参与 FTS）。
- 向量：SqliteVectorStore + HashingEmbedding（保留）。RRF k=60。

---

## 6. 便签（tags）

- 程序内部维护，模型只读。用途：`已老化` 等。
- 不参与编号、不参与总结逻辑。

## 7. 端到端流程

```
用户发言
  → pre-step：同步入库（编号分配）
  → 模型产出：思考 + 工具调用 + 正文
  → pre-step：新单位需要总结 → 注入提炼指令（引用 #N）
  → 模型回复提炼结果（或"无"）
  → 程序：挂接 summary → 撤掉指令与回复的发送视图
  → 发送视图不变（summary + content 并存，全量）
  ……若干轮后……
  → 单位滑出窗口：有 summary → 只发 #N + summary；无 summary → 原样保留
  → 任意时刻：模型调 memory_search 取回任意 #N 全量
```

## 8. 验收标准

1. 近程上下文形如 §3.1：每单位 `#N` 开头，有 summary 的带 `<summary>` 标签。
2. 单位滑出窗口后只发 `#N`（+summary 或原文），**编号不变**。
3. 未总结单位老化后原样保留（与 summary 地位等同）。
4. 总结完成后发送视图不变。
5. 老化单位仍能被 `memory_search` 搜到并返回**全量** content。
6. 编号多轮稳定、会话内连续无空洞、从 0 开始。
7. 工具调用与结果同一编号，`<tool-call>`/`<tool-result>` 标签区分。
8. 思考、正文、每个工具调用各占一号；system 不占号。
9. 提炼指令与回复完成后不再出现在发送视图（日志保留）。
10. 模型输出从不出现 `<summary>` 标签。
11. 长单位必有 summary；短单位可"无"。
12. 无自动索引触发器；模型无总结类工具。
13. 全部行为有测试覆盖，并在真实 dsh（WSL）验证加载与真实对话。

## 11. 术语

| 词 | 含义 |
| --- | --- |
| 单位 | 一个 #N：user / thinking / tool(调用+结果) / reply |
| 总结 | 串行提炼：注入指令 → 模型回复 → 挂接；完成后发送不变 |
| summary | 模型提炼结果（程序加 `<summary>` 标签展示）；空 = 未总结 |
| content | 单位完整原文，入库永不删 |
| 近程 / 远程 | 窗口内 / 外；前者 summary+content 全发，后者只发 summary（无 summary 则原文） |
| 投影 | 发送视图纯函数 f(单位, 窗口) |
| 提炼指令 | 程序注入的 user 消息，驱动模型产出 summary |
| 撤除 | 提炼指令与回复完成使命后从发送视图移除（日志保留） |
