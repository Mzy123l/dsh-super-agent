# 设计：工具调用的「概要 + 可展开」

> 提议：**每次工具调用在上下文里默认只保留概要；模型需要细节时，用一个工具展开取回。**
>
> 这是「记忆」这条线的第三环的解法。前两环：
> - 压缩（历史丢失）→ [98](98-compaction-findings.md)
> - 裁剪（单条结果丢失）→ 同上 §6
>
> 本环解决的是：**数据全在上下文里，模型也未必能准确回答"我刚才干了什么、返回了什么"**。
> 而且即使数据全在，也不该全在——见 §1。

---

## 1. 为什么需要（数据支撑）

### 1.1 体积分布：极少数结果占了一半体积

本会话实测（260 个工具结果，来自 [9A](9A-self-audit.md) §6.2/§7.1）：

| 指标 | 数值 |
| --- | --- |
| 工具结果总数 | **260** |
| 全部结果合计 | **503,438 字符**（≈157K tokens，按 1:3.2） |
| 超 8192 字符的结果 | **16 个**（6.2%） |
| 这 16 个合计 | **250,576 字符**（**占总量 49.8%**） |
| 最大单条 | **33,386 字符**（≈10.4K tokens） |

**6.2% 的结果占了 49.8% 的体积。** 它们多数是"读文件的前 260 行""grep 的完整输出"——
**当时有用，之后只需要记得"读过、结论是什么"。**

### 1.2 注意力问题：在场 ≠ 被利用

`memory-survey`（[9C](9C-memory-survey.md)）引用的 context rot 研究：

> **相关**与**无关**的长上下文失败率相同（各 3/10，对比干净上下文的 8/10）。
> **伤害来自长度本身**，不是"相关性不够"。

也就是说：**那些 500 行的历史工具输出，即使内容与当前问题相关，也在稀释注意力。**
"数据全在上下文里"不是资产，很可能是负债。

### 1.3 我的亲历（自我认知的失败）

本会话里我跑过 139 次 `pwsh`。当我回答"你之前干了什么"时（你问的那次）：

- **能答上的**：我写进文档里的数字（提交号、统计值）
- **答不上的**：具体某个命令的完整输出、某次 read 读到的文件内容
- **且无察觉**：我不知道自己漏了哪些

而审计证明（[9A](9A-self-audit.md) §6）：**本会话没有被压缩、没有被裁剪**，
这些信息**理论上全都在上下文里**——但我答不出细节，且**意识不到自己答不出**。

**结论：让模型"知道自己干过什么"，不能靠把原始输出留在上下文里，必须换一种表征。**

## 2. 设计

### 2.1 核心想法

```
现在：
  tool_call → tool_result（完整 500 行，永驻上下文）

改成：
  tool_call → tool_result（概要版，≤ 800 字符）
            + [full: spill 路径 · expandable via tool_expand(seq)]
```

**概要要包含三类信息**（这是设计的关键，不是"截断"）：

1. **动作**：做了什么（命令的前 120 字符 / 读的哪个文件）
2. **结果**：返回的核心内容（条数、退出码、关键行、结论性摘要）
3. **取回**：完整内容在哪、怎么展开

### 2.2 概要格式

```markdown
[tool#7731 pwsh] git log --oneline -8
→ 8 commits, HEAD=6ce0c6e "docs: 完整上下文对比示例"
→ 退出码 0 · 完整输出 3.2KB 已落盘
  expand: tool_expand(seq=7731) · spill: /…/…-7731.txt
```

```markdown
[tool#7732 read] src/fish.memory.cppm
→ 620 行 / 19,006 字符；要点：3-layer memory; WorkingMemory(keep_rounds)
   NotesStore(IndexStore/Consolidator); MemorySystem(gather/compact/search)
  expand: tool_expand(seq=7732) · spill: /…/…-7732.txt
```

**注意**：概要不是简单截断。头 4096 字符常常是 import 语句和类型定义，
**最有信息量的部分（函数体、错误信息）往往在中段**。
所以概要应该**按内容类型取要点**，而不是按位置切片。

### 2.3 概要的生成方式

三种方案，按成本排：

| 方案 | 做法 | 成本 | 质量 |
| --- | --- | --- | --- |
| **规则式**（推荐起步） | 按工具类型给固定模板：`pwsh` 取退出码+最后 5 行；`read` 取行数+标题行；`grep` 取命中数+前 3 命中 | **零模型调用** | 够用 |
| 模型式 | 让小模型生成一句话摘要 | 每次一次调用 | 更准但贵 |
| 混合 | 超过阈值才用模型 | 中 | 中 |

**推荐规则式起步**，理由：
- `9G` 的实测结论"压缩的缓存代价只有 3.8%"提醒我们：**别为省 token 引入更大的成本**（每结果一次模型调用）
- 规则式的概要**确定性**，对缓存友好（见 §4）

### 2.4 展开工具

新增一个工具 `tool_expand`：

```ts
{
  name: 'tool_expand',
  description: '取回某次工具调用的完整原始结果。默认上下文里只有概要；'
    + '当你需要上一步命令的完整输出、某次读过的文件的中间部分时使用。',
  input: {
    seq: { type: 'number', description: '工具结果的事件 seq（概要行里已给出）' },
    offset?: number,   // 可选：从第几字符开始
    limit?: number,    // 可选：取多长，默认完整
  }
}
```

**实现路径**：这就是现成的 `dsh-spill` 契约——`SpillStore.saveText()` 已返回
`{locator, bytes, retrievalHint}`，`dsh-spill-local` 已把完整内容落盘。
**缺的只是把"落盘的文件"和一个可枚举的 seq 关联起来，并注册一个读它的工具。**

### 2.5 阈值

不是所有结果都需要折叠。参考现有配置：

| 现有机制 | 阈值 | 行为 |
| --- | --- | --- |
| `spill-policy` | maxInlineTokens **12,500** | 超 → 整体落盘，上下文留预览 |
| `tool-result-pruner` | 8,192 字符 | 压缩触发后，裁到 5,159 |

**建议**：概要化的阈值远低于这两个——**2,000 字符**。
理由：

- 本会话 260 个结果里，超过 2,000 字符的比例远高于超 8192 的（16 个）。
  早期用统计工具查过分布，但未留档 `[推断]`：**多数工具结果在 500–3,000 字符之间**，
  折叠阈值定在 2,000 能覆盖大部分
- 短结果（`git status` 一行、`ls` 几行）保持原样，零开销

### 2.6 与现有机制的关系

| 机制 | 关系 |
| --- | --- |
| `spill-policy`（12,500） | **保留**。它处理"单条大到必须立刻处理"的场景，且有取回。概要化在其**之下**运行 |
| `tool-result-pruner`（压缩后裁剪） | **被取代**。如果结果已经在写入时就概要化了，压缩时就不用裁——**省掉 prune 的 59 次** |
| `tool_expand`（新） | 与 `spill` 共用存储，但按 seq 索引（spill 按文件路径索引） |

**一句话**：把"压缩后才被动裁剪"改为"写入时就主动概要化"，prune 就失去了存在意义。

## 3. 对"我之前干了什么"的改善

| 问题 | 现在 | 概要化后 |
| --- | --- | --- |
| 我上一步跑了什么命令 | 命令原文在上下文里（长） | 概要第一行就是命令 + 编号 |
| 那次输出说了什么 | 500 行原文，注意力稀释 | 概要给结论 + 可展开 |
| 我读过哪些文件 | 散落在 500 行结果里 | 每条概要都是一行，可扫读 |
| 展开某次的细节 | 无机制（除非 spill） | `tool_expand(seq)` |

**关键改善**：概要行是**紧凑的、带编号的、可扫读的**。
模型要回忆"我做过什么"，扫 50 行概要比在 15 万字符的原文里翻找**容易得多**。

---

## 4. 对缓存命中（专题四）的影响

这是本设计的**隐藏收益**，也必须诚实说明风险。

### 4.1 收益

当前：每条工具结果全量进上下文 → 历史前缀越长，每个请求的 prefill 越贵（即使 cache 命中，读缓存也要付钱）。
概要化后：**历史部分体积大幅缩小**（粗估本会话可省 157K → 约 40K tokens）。

`9G` 实测：全库命中率 99.19%，压缩只占未命中 3.8%。
**也就是说缓存的瓶颈不在"失效"，而在"前缀本身太长"。** 概要化直接缩小前缀。

### 4.2 风险：概要本身必须稳定

如果概要在**每次请求时重新生成**且内容不稳定（例如包含时间戳、随机 id），
**每次都会破坏前缀** → 缓存全 miss。

**规避**：概要在**工具结果产生时一次性生成并固化**，存入日志，
之后每轮只是**回放**（不重算）。这与 dsh 的"日志态"哲学一致
（`tool/result` 本来就是日志事件，回放不重算）。

---

## 5. 对"压缩"问题的连锁收益

如果写入时就概要化：

1. **压缩的"原料"变小**：`selectCompactableRange` 切的范围里都是概要，
   摘要模型读的是概要而非 500 行原文 → **摘要质量提高**
2. **prune 消失**：没有"超大结果"需要压缩后再裁
3. **"我之前干了什么"在压缩后仍然可答**：概要行留在上下文里的时间更长
   （它们小，`retainTokens` 尾部能保住更多轮次）

**一句话：概要化是"让历史更稠密"——同样的 token 预算装下更多轮次。**

## 6. 验收标准

| # | 标准 | 测法 |
| --- | --- | --- |
| 1 | 概要化后，"我上一步干了什么"的准确率**不低于**现在 | 同一组问题，A/B 对照 |
| 2 | 上下文中工具结果体积下降 ≥ 60% | 统计 260 条的概要版合计字符 |
| 3 | 展开取回成功率 100% | 对每个被折叠的结果跑 `tool_expand` |
| 4 | 概要确定性：同一结果两次生成的概要逐字节相同 | 对拍 |
| 5 | 缓存命中不下降 | 对比改造前后 `cacheReadTokens` 比例 |
| 6 | 模型不再需要读原文的场景，**不会**去展开 | 统计展开调用的比例（应 < 20%） |

## 7. 风险与诚实标注

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **概要丢掉了模型当时注意到的细节** | 模型在原始结果里看到的某些细节，概要里没有；后续轮次想用时要展开 | 展开工具 + 阈值别太激进（2,000 而非 500） |
| **规则式概要对非标准输出不友好** | 例如二进制、表格、图片引用 | 按工具类型分模板；兜底用首行 + 字节数 |
| **本设计未经验证** | "概要化后准确率不低于现在"是假设，**没有 A/B 实验** | 建议照 9I 的方法跑一轮 |
| **9I 的教训** | 那次实验证明"把信息放进视野 ≠ 改变行为"。本设计同样可能"概要在场但模型不去展开" | 把展开做成**廉价且显式**（概要行里直接给命令） |
| **工具 schema 再加一个** | 工具 schema 已占 12,139 tokens，再加一个 `tool_expand` 的 schema | 概要行的取回提示可以内联说明，schema 可极简 |

### 与「压缩」问题的边界

| | 压缩问题 | 本设计 |
| --- | --- | --- |
| 何时发生 | 上下文将满（被动） | 每次工具调用（主动） |
| 丢什么 | 旧历史 | **不丢**（完整内容落盘可取回） |
| 模型是否被告知 | 定性有、量化无 | 概要行自带规模 + 取回命令 |

**两者互补，不冲突。** 概要化甚至减轻压缩的压力（历史更稠密）。

---

## 8. 最小可行实现

如果只做一版验证效果：

1. **不动 dsh**：写一个插件，挂在 `tools/post-execute`（`spill-policy` 同款挂点）
2. 阈值 2,000 字符：超过 → 生成概要（规则式）+ `saveText()` 落盘 + 替换结果
3. 概要行里内联取回提示（先用 `read(path)`，暂不新增 `tool_expand` 工具）
4. 用 9I 的方法跑 A/B：同一组"我上一步干了什么"的问题，对照概要化前后

**预估工作量**：一个下午。**因为它就是把 `spill-policy` 的阈值从 12,500 降到 2,000、
再加一个规则式概要生成器。**
