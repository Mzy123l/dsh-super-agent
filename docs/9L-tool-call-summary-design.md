# 设计：工具调用的「概要 + 可展开」

> 提议：**每次工具调用在上下文里默认只保留概要；模型需要细节时，用一个工具展开取回。**
>
> 这是「记忆」这条线的第三环的解法。前两环：
> - 压缩（历史丢失）→ [98](98-compaction-findings.md)
> - 裁剪（单条结果丢失）→ 同上 §6
>
> 本环解决的是：**数据全在上下文里，模型也未必能准确回答"我刚才干了什么、返回了什么"**。
> 而且即使数据全在，也不该全在——见 §1。

---

## 1. 为什么需要（数据支撑）

### 1.1 体积分布：极少数结果占了一半体积

本会话实测（260 个工具结果，来自 [9A](9A-self-audit.md) §6.2/§7.1）：

| 指标 | 数值 |
| --- | --- |
| 工具结果总数 | **260** |
| 全部结果合计 | **503,438 字符**（≈157K tokens，按 1:3.2） |
| 超 8192 字符的结果 | **16 个**（6.2%） |
| 这 16 个合计 | **250,576 字符**（**占总量 49.8%**） |
| 最大单条 | **33,386 字符**（≈10.4K tokens） |

**6.2% 的结果占了 49.8% 的体积。** 它们多数是"读文件的前 260 行""grep 的完整输出"——
**当时有用，之后只需要记得"读过、结论是什么"。**

### 1.2 注意力问题：在场 ≠ 被利用

`memory-survey`（[9C](9C-memory-survey.md)）引用的 context rot 研究：

> **相关**与**无关**的长上下文失败率相同（各 3/10，对比干净上下文的 8/10）。
> **伤害来自长度本身**，不是"相关性不够"。

也就是说：**那些 500 行的历史工具输出，即使内容与当前问题相关，也在稀释注意力。**
"数据全在上下文里"不是资产，很可能是负债。

### 1.3 我的亲历（自我认知的失败）

本会话里我跑过 139 次 `pwsh`。当我回答"你之前干了什么"时（你问的那次）：

- **能答上的**：我写进文档里的数字（提交号、统计值）
- **答不上的**：具体某个命令的完整输出、某次 read 读到的文件内容
- **且无察觉**：我不知道自己漏了哪些

而审计证明（[9A](9A-self-audit.md) §6）：**本会话没有被压缩、没有被裁剪**，
这些信息**理论上全都在上下文里**——但我答不出细节，且**意识不到自己答不出**。

**结论：让模型"知道自己干过什么"，不能靠把原始输出留在上下文里，必须换一种表征。**

## 2. 设计

### 2.1 核心想法

```
现在：
  tool_call → tool_result（完整 500 行，永驻上下文）

改成：
  tool_call → tool_result（概要版，≤ 800 字符）
            + [full: spill 路径 · expandable via tool_expand(seq)]
```

**概要要包含三类信息**（这是设计的关键，不是"截断"）：

1. **动作**：做了什么（命令的前 120 字符 / 读的哪个文件）
2. **结果**：返回的核心内容（条数、退出码、关键行、结论性摘要）
3. **取回**：完整内容在哪、怎么展开

### 2.2 概要格式

```markdown
[tool#7731 pwsh] git log --oneline -8
→ 8 commits, HEAD=6ce0c6e "docs: 完整上下文对比示例"
→ 退出码 0 · 完整输出 3.2KB 已落盘
  expand: tool_expand(seq=7731) · spill: /…/…-7731.txt
```

```markdown
[tool#7732 read] src/fish.memory.cppm
→ 620 行 / 19,006 字符；要点：3-layer memory; WorkingMemory(keep_rounds)
   NotesStore(IndexStore/Consolidator); MemorySystem(gather/compact/search)
  expand: tool_expand(seq=7732) · spill: /…/…-7732.txt
```

**注意**：概要不是简单截断。头 4096 字符常常是 import 语句和类型定义，
**最有信息量的部分（函数体、错误信息）往往在中段**。
所以概要应该**按内容类型取要点**，而不是按位置切片。

### 2.3 概要的生成方式

> **修订（2026-11-14）**：本节原推荐"规则式起步（零模型调用）"。用户否决了这个判断：
> **"我不认为有什么规则可以获得高质量的概要。"**
> 重新审视后同意，规则式只能做"定位信息"，做不了"压缩信息"。分析见 §2.3.1，
> 修订后的方案是"规则式定位 + 模型式压缩"分层（§2.3.2），成本论证见 §2.3.3。

#### 2.3.1 为什么规则式得不到高质量概要

规则式（按工具类型套模板：pwsh 取退出码+末 5 行、read 取行数+标题行、grep 取命中数）能产出的只有**形状信息**：

| 规则式能给 | 规则式不能给 |
| --- | --- |
| 命令是什么、退出码几 | **输出里哪一段是"结论"**（结论可能在任何位置：开头一行、中段报错、末尾统计） |
| 文件多少行、多大 | **这份内容与当前任务的关联**（读到的东西哪个部分回答了当时的问题） |
| 有多少条命中 | **哪个细节后来会被用到**（当时看似平常的一行，可能就是后续决策的依据） |

根本原因：**"这条结果里重要的是什么"取决于提问的语境，而规则没有语境。**
同一个 `pwsh` 输出，在"排查启动失败"的会话里重要的是报错行，在"统计代码量"的会话里重要的是统计行。
固定模板无法区分这两种情形——**而区分它们，恰恰是"概要"区别于"截断"的全部价值。**

规则式概要的真实身份是**带元数据的切片**：它告诉模型"这里有个结果、多大、去哪取"，
但不告诉模型"这里说了什么值得记住的事"。

**结论：要"高质量概要"，必须让理解过语境的模型来生成。这是成本，不是可选优化。**

#### 2.3.2 修订后的方案：由主模型同步自评

> **二次修订（2026-11-14）**：用户否决了"小模型异步 gist"方案，理由有二：
> **① 同步——否则某一步可能拿到空摘要；② 摘要必须由正在运行的模型自己生成——只有自己知道自己需要什么。**
> 两条都成立，方案重写如下。原"定位层 + 异步 gist"两层的分析保留在 §2.3.4 供对照。

**新方案：主模型在获得工具结果的同一步内，自己产出概要，同步写进上下文。**

实现形态不是"外挂小模型"，而是**给主模型加一个自我概要的义务**：

```markdown
[tool#7732 read] src/fish.memory.cppm · 620 行
  self-gist: 读它是为了实现 MemorySystem 的分层；关键发现是 WorkingMemory 的
  keep_rounds<=0 会跳过截断——这影响我后面 compact() 的实现方式。
  expand: tool_expand(seq=7732) · spill: /…/…-7732.txt
```

**`self-gist` 与 `gist` 的本质差别**：

| | 外挂小模型的 gist | 主模型自己的 self-gist |
| --- | --- | --- |
| 知道当时为什么要读吗 | ❌ 只有"任务简述" | ✅ **完整语境：我在修什么、卡在哪、预期看到什么** |
| 能判断"哪些细节与我的下一步相关"吗 | ❌ 猜 | ✅ **它本来就要决定下一步** |
| 时机 | 异步，可能空缺 | ✅ 同步，永不空缺 |
| 成本 | 额外一次小模型调用 | **并入主模型同一步的输出**（几十 tokens） |
| 失败模式 | 抓错重点（旁观者视角） | 偷懒/敷衍（见 §2.3.5 的强制措施） |

**为什么"只有自己知道自己需要什么"是对的**：工具结果的"重点"不是结果的客观属性，
而是**它与当前推理链的关系**。同一个 500 行输出，我在"找 bug"时关注报错栈，
在"抄配置格式"时关注字段名。**这个关联只存在于正在推理的那个模型的注意力里**，
外挂模型拿到再多上下文，也只能重建"任务的骨架"，重建不了"当时的意图"。

**同步解决的另一个问题**：异步方案里"gist 到位前上下文是空的"，
同步方案下**概要与结果同帧出现，永不空缺**——这正是你要求同步的理由。

#### 2.3.3 落地机制：两步合并为一步

**实现路径**：改造结果返回的封装，让超阈值的工具结果在同一步内变成：

```
<result head=2000 chars of fish.memory.cppm>
…（原文前 2000 字符，满足"当时就要看细节"的需求）…
</result>

[self-summary required] 以上结果被截断（620 行，完整 19,006 字符已落盘）。
在继续下一步之前，先用一行写出：①你为什么读它 ②你从中得到的、会影响后续动作的结论。
写完后继续。如无有价值结论，写"无"并说明原因。
```

**关键设计**：

1. **不是额外一次模型调用**——是把"自我概要"作为**同一步输出的一部分**，模型在看完截断内容的同一步里顺手写出
2. **用"要求下一步先写概要"的指令实现**，而不是硬拦（拦会破坏 agent loop 的 tool-call/result 配对）
3. **强制语气的来源**：`post-execute` 在截断时注入 `[self-summary required]` 指令（复用 `additionalContexts` 通道，`9B` §2 表第 9 行）
4. **原文照旧落盘**（spill），`tool_expand` 取回机制不变
5. **拒答兜底**：模型若不写 self-gist，下一步注入一句提醒（复用 `dsh-repeat-tool-reminder` 的模式）；不硬失败

#### 2.3.4 原两层方案的存留价值（对照，已废弃为默认方案）

原方案（规则定位层 + 异步小模型 gist）的分析保留：规则式只能给形状信息（§2.3.1 依然成立），
但"异步 + 外挂"两个特性被否决。它的**定位层**部分被新方案吸收（截断头的规模与取回命令仍是规则式生成），
**压缩层**改为同步自评。

#### 2.3.5 新方案的失效模式（诚实标注）

| 失效 | 说明 | 缓解 |
| --- | --- | --- |
| **模型敷衍** | "读了文件，有内容"这种废话概要 | 指令里给反例；连续两次敷衍升级为提醒；抽检（同 §6 验收 4） |
| **概要与原文不符** | 模型概括出错，后续轮次被误导 | self-gist 强制中性措辞；展开取原文；验收抽检 ≥80% |
| **每步多几十 tokens** | self-gist 是主输出的一部分，挤占输出预算 | 单条 ≤80 字符；超阈值结果本来就少（27%） |
| **仍然无法预知未来需求** | 写时不知道哪个细节将来有用——这条局限与异步方案相同，**是概要化的根本局限，不是同步/异步的选择问题** | 检索层兜底（原文都在日志里） |
| **打断推理流** | 要求"先写概要再继续"会改变模型的输出节奏 | 只对超阈值结果触发（27%），且摘要本身就是推理的一部分 |

#### 2.3.6 成本论证（按新方案重算）

| 项 | 数值（本会话实测） |
| --- | --- |
| 工具结果总数 | 260 |
| 超过 2,000 字符（触发 self-summary 义务） | 约 70 条（27%），按分布推算 `[推断]` |
| **小模型调用** | **0**（不再有外挂 gist） |
| **主模型增量** | 每条 self-gist ≤80 字符 ≈ 40 tokens 输出；70 条合计 **~2,800 输出 tokens** |
| 上下文节省 | 历史体积降 ≥60%（503K → 约 200K 字符），每请求 prefill 相应下降 |
| 换得 | 历史体积降 ≥60%；摘要与结果同帧、永不空缺；"我之前干了什么"可扫读 |

**与旧账对比**：异步 gist 是"15 万 tokens 额外调用"；同步自评是"~2,800 输出 tokens + 0 次额外调用"。
同步方案不仅消除了空摘要窗口，**成本还低了一个数量级**——因为 self-gist 不需要重新输入原文
（主模型刚读完它），而外挂 gist 要把原文整个再喂一遍。

**代价的真正形态**：不是 token，而是**每条截断结果多一轮"写概要"的输出义务**，
以及由此带来的敷衍风险（§2.3.5）。这是行为设计问题，不是算力问题。

### 2.4 展开工具

新增一个工具 `tool_expand`：

```ts
{
  name: 'tool_expand',
  description: '取回某次工具调用的完整原始结果。默认上下文里只有概要；'
    + '当你需要上一步命令的完整输出、某次读过的文件的中间部分时使用。',
  input: {
    seq: { type: 'number', description: '工具结果的事件 seq（概要行里已给出）' },
    offset?: number,   // 可选：从第几字符开始
    limit?: number,    // 可选：取多长，默认完整
  }
}
```

**实现路径**：这就是现成的 `dsh-spill` 契约——`SpillStore.saveText()` 已返回
`{locator, bytes, retrievalHint}`，`dsh-spill-local` 已把完整内容落盘。
**缺的只是把"落盘的文件"和一个可枚举的 seq 关联起来，并注册一个读它的工具。**

### 2.5 阈值

不是所有结果都需要折叠。参考现有配置：

| 现有机制 | 阈值 | 行为 |
| --- | --- | --- |
| `spill-policy` | maxInlineTokens **12,500** | 超 → 整体落盘，上下文留预览 |
| `tool-result-pruner` | 8,192 字符 | 压缩触发后，裁到 5,159 |

**建议**：概要化的阈值远低于这两个——**2,000 字符**。
理由：

- 本会话 260 个结果里，超过 2,000 字符的比例远高于超 8192 的（16 个）。
  早期用统计工具查过分布，但未留档 `[推断]`：**多数工具结果在 500–3,000 字符之间**，
  折叠阈值定在 2,000 能覆盖大部分
- 短结果（`git status` 一行、`ls` 几行）保持原样，零开销

### 2.6 与现有机制的关系

| 机制 | 关系 |
| --- | --- |
| `spill-policy`（12,500） | **保留**。它处理"单条大到必须立刻处理"的场景，且有取回。概要化在其**之下**运行 |
| `tool-result-pruner`（压缩后裁剪） | **被取代**。如果结果已经在写入时就概要化了，压缩时就不用裁——**省掉 prune 的 59 次** |
| `tool_expand`（新） | 与 `spill` 共用存储，但按 seq 索引（spill 按文件路径索引） |

**一句话**：把"压缩后才被动裁剪"改为"写入时就主动概要化"，prune 就失去了存在意义。

## 3. 对"我之前干了什么"的改善

| 问题 | 现在 | 概要化后 |
| --- | --- | --- |
| 我上一步跑了什么命令 | 命令原文在上下文里（长） | 概要第一行就是命令 + 编号 |
| 那次输出说了什么 | 500 行原文，注意力稀释 | 概要给结论 + 可展开 |
| 我读过哪些文件 | 散落在 500 行结果里 | 每条概要都是一行，可扫读 |
| 展开某次的细节 | 无机制（除非 spill） | `tool_expand(seq)` |

**关键改善**：概要行是**紧凑的、带编号的、可扫读的**。
模型要回忆"我做过什么"，扫 50 行概要比在 15 万字符的原文里翻找**容易得多**。

## 4. 对缓存命中（专题四）的影响

这是本设计的**隐藏收益**，也必须诚实说明风险。

### 4.1 收益

当前：每条工具结果全量进上下文 → 历史前缀越长，每个请求的 prefill 越贵（即使 cache 命中，读缓存也要付钱）。
概要化后：**历史部分体积大幅缩小**（粗估本会话可省 157K → 约 40K tokens）。

`9G` 实测：全库命中率 99.19%，压缩只占未命中 3.8%。
**也就是说缓存的瓶颈不在"失效"，而在"前缀本身太长"。** 概要化直接缩小前缀。

### 4.2 风险：概要本身必须稳定

如果概要在**每次请求时重新生成**且内容不稳定（例如包含时间戳、随机 id），
**每次都会破坏前缀** → 缓存全 miss。

**规避**：概要在**产生时一次性生成并固化**，存入日志，
之后每轮只是**回放**（不重算）。这与 dsh 的"日志态"哲学一致
（`tool/result` 本来就是日志事件，回放不重算）。

**同步方案让这个风险消失了一半**：self-gist 是主模型在同一步的输出里写出的，
**产生即固化**，不存在"异步到位后替换"的时序问题（旧方案为此设计的三个选项 a/b/c 已随异步方案废弃）。

**剩下一半的风险**：self-gist 是**模型输出**，同一条结果两次自评可能产出不同措辞。
但这与"回放不重算"不冲突——**日志里存的是什么，回放的就是什么**，前缀逐字节稳定。
风险只在"对拍测试"（验收 4 的确定性检查）上：同一结果重跑，概要措辞可能不同。
**这不是缓存问题，是可复现性问题**，对线上缓存无影响。

## 5. 对"压缩"问题的连锁收益

如果写入时就概要化：

1. **压缩的"原料"变小**：`selectCompactableRange` 切的范围里都是概要，
   摘要模型读的是概要而非 500 行原文 → **摘要质量提高**
2. **prune 消失**：没有"超大结果"需要压缩后再裁
3. **"我之前干了什么"在压缩后仍然可答**：概要行留在上下文里的时间更长
   （它们小，`retainTokens` 尾部能保住更多轮次）

**一句话：概要化是"让历史更稠密"——同样的 token 预算装下更多轮次。**

## 6. 验收标准

| # | 标准 | 测法 |
| # | 标准 | 测法 |
| --- | --- | --- |
| 1 | 概要化后，"我上一步干了什么"的准确率**不低于**现在 | 同一组问题，A/B 对照 |
| 2 | 上下文中工具结果体积下降 ≥ 60% | 统计 260 条的概要版合计字符 |
| 3 | 展开取回成功率 100% | 对每个被折叠的结果跑 `tool_expand` |
| 4 | **self-gist 质量**：抽样 30 条，人工判"是否抓住了该结果的关键"≥ 80% | 人工标注（无自动判据） |
| 5 | 缓存命中不下降 | 对比改造前后 `cacheReadTokens` 比例 |
| 6 | 模型不再需要读原文的场景，**不会**去展开 | 统计展开调用的比例（应 < 20%） |
| 7 | self-gist 写出率 ≥ 95% | 统计超阈值结果中下一步实际带概要的比例；不足则提醒机制升级 |

## 7. 风险与诚实标注

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **self-gist 抓错重点** | 模型概括出错，后续轮次被误导 | 措辞强制中性描述、禁价值判断；展开永远取原文；验收标准 4（人工判 ≥80%） |
| **模型敷衍** | "读了文件，有内容"这种废话概要 | 指令给反例；连续两次敷衍注入提醒（复用 repeat-tool-reminder 模式）；验收标准 7 |
| **无法预知未来需求** | 写时不知道哪个细节将来有用；**这是概要化的根本局限，同步/异步都一样** | 检索层兜底（原文都在日志里） |
| **概要丢掉了模型当时注意到的细节** | 模型在原始结果里看到的某些细节，概要里没有；后续轮次想用时要展开 | 展开工具 + 阈值别太激进（2,000 而非 500） |
| **每步多几十 tokens 输出** | self-gist 挤占输出预算 | 单条 ≤80 字符；触发面只有 27% |
| **打断推理流** | 要求"先写概要再继续"改变输出节奏 | 只对超阈值结果触发；摘要本身就是推理的一部分 |
| **本设计未经验证** | "概要化后准确率不低于现在"是假设，**没有 A/B 实验** | 建议照 9I 的方法跑一轮 |
| **9I 的教训** | 那次实验证明"把信息放进视野 ≠ 改变行为"。本设计同样可能"概要在场但模型不去展开" | 把展开做成**廉价且显式**（概要行里直接给命令） |
| **工具 schema 再加一个** | 工具 schema 已占 12,139 tokens，再加一个 `tool_expand` 的 schema | 概要行的取回提示可以内联说明，schema 可极简 |

### 与「压缩」问题的边界

| | 压缩问题 | 本设计 |
| --- | --- | --- |
| 何时发生 | 上下文将满（被动） | 每次工具调用（主动） |
| 丢什么 | 旧历史 | **不丢**（完整内容落盘可取回） |
| 模型是否被告知 | 定性有、量化无 | 概要行自带规模 + 取回命令 |

**两者互补，不冲突。** 概要化甚至减轻压缩的压力（历史更稠密）。

## 8. 最小可行实现

如果只做一版验证效果：

1. **不动 dsh**：写一个插件，挂在 `tools/post-execute`（`spill-policy` 同款挂点）
2. 阈值 2,000 字符：超过 → 截断保留前 2,000 字符 + `saveText()` 落盘 + 注入 `[self-summary required]` 指令（复用 `additionalContexts`）
3. 概要行里内联取回提示（先用 `read(path)`，暂不新增 `tool_expand` 工具）
4. 下一步注入时检查模型是否写了 self-gist，未写则注入一句提醒
5. 用 9I 的方法跑 A/B：同一组"我上一步干了什么"的问题，对照概要化前后

**预估工作量**：约一个下午。**比异步方案更简单**——不需要小模型接入、并发队列和追加事件注入，
`post-execute` 一处注入 + 一处提醒检查就完成。

**注意这个方案的诚实边界**：self-gist 依赖模型**自愿服从**指令。它没有硬约束力——
模型完全可以略过不写。这继承了 9I 的教训（"在场 ≠ 遵守"），所以验收标准 7（写出率 ≥95%）
是整个设计能否成立的关键指标；若写出率不达标，唯一升级路径是把"确认后才能提交下一步"
做成 loop 层的硬拦截（`agent/turn-stopping` 或 `agent/pre-step` 检查），那是更大的改动。
