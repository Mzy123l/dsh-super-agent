§三条原理依据

一、指针优于告知。MemGPT 的 70% 压力警告、Claude Code 的 Referenced file，都采用「指针」形式而非「你被裁了」的自我告知 —— 同样 token 预算，前者买到能力，后者只买到焦虑。所以写 session_query(seq_from=41, …)，而不是「你的上下文被压缩了，请小心」。

二、重注入是唯一扛得住压缩的原语。Claude Code 的 What survives compaction 表证明：CLAUDE.md、auto memory、skill 描述全部从磁盘重新注入，而路径作用域规则会被摘要掉。

三、检索是 pull 模式，前提是「知道自己缺」。即使打开 session_query，模型也不会主动去搜一个它不知道缺的东西 —— 所以指针必须在上下文里。

5必须诚实说明的局限

!版本 B 不能防止模型无视 R1

它只是让 R1 在视野里、可核对、有优先级。模型仍可能：判断错了（认为 50% 不是上限）、图省事跳过确认、被其他内容分散注意力。

改进的是「信息可得性」，不是「遵从度」。与 9D 的结论一致：架构能保证「在场」，不能保证「遵守」。后者需要别的机制，例如把确认动作做成工具层的强制前置。

6诚实标注

这份材料里，哪些是实测、哪些是重建、哪些是推演

  • 实测上下文结构、节点顺序、标记文本格式来自源码常量与日志：node 0 是 system/message 且永不被遮蔽； CHECKPOINT_PREAMBLE 原文；<compacted-summary> 开闭标签 17/17 存在； PRUNE_MARKER = "\n\n[... tool result middle pruned ...]\n\n"。
  • 实测所有数字来自 98 与 9B：压缩遮蔽 2,143 事件 / 479,142 tokens（seq 41–2184）； 59 次 prune，原文合计 1,166,597 字符，替换后典型长度 5,159 字符；系统提示 1,682 tokens；工具 schema 12,139 tokens。
  • 重建摘要正文是示意。它是按摘要 prompt 要求的 8 个固定小节重建的，措辞非原文； 实测摘要模型每次输出 2,333–4,348 tokens，此处为节选式重建，用于让读者看见「一条硬规则在 12 条 bullet 中间」是什么手感。
  • 推演模型的行为反应未实测。「A 直接改代码」「B 先确认」都是基于 preamble 措辞与规则形态的推演。 目前没有任何对照实验证明加上 R1 后遵从率会上升 —— memory-survey 也明确指出， 「结构化更抗压缩」是机制推理 + 间接证据。
  • 已修正口径混用已在本版修正。此前示例把 1,166,597（59 次 prune 的原文合计） 与 5,159（单条替换后的固定长度 = head 4096 + 标记 35 + tail 1024）相减，得到一个不成立的 −99.6%。 现改为按单条口径表述：原文 18,006 → 裁后 5,159，省略 12,847，减幅 −71.3%； 合计层面则是 1,166,597 → 304,427（−73.9%）。两处比例接近并非巧合，但分母不同，不可混算。
  • 局限本方案只做「信息可得性」，不做「遵从度」；且它假设 session_query 类工具可用 —— 当前 web profile 里 tool-session-query 并未挂载（全文搜索后端 openAt: never）， 所以声明里的取回命令在今天是无效指针，需要与工具挂载一起做。

7如果你要验证这个示例：实验设计建议

1构造

造一个含硬约束的长会话（>阈值），让压缩真实发生。约束要写在很早的位置，且后续有多轮无关工作把它挤出视野。

2分组

A 组：用当前格式，问一个会触发该约束的请求，记录是否违反。
B 组：加上 Hard rules 区 + 完整性声明，问完全相同的问题。

3计量

每组跑 10 次，统计违反率；同时记录模型是否主动调用取回命令（这能验证「指针是否被用上」）。 再跑一个 B′ 组（只加 25 tokens 的单行声明），分离「量化」与「规则重注入」各自的贡献。

这个实验目前没人做过。所以本页的方案是有原理支撑的假设，不是已验证的结论 —— 在拿数据之前，请把它当作「值得一试的最小改动」，而不是「已知有效的修复」。
